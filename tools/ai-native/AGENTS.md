# @repo/ai-native

## このパッケージが守るもの

複数のエージェントと人間が同じマシンで並列に働いても、2 つの有限な資源が壊れない。重いコマンドの同時実行数に上限を課すことでホストの CPU・メモリ・ディスク帯域を守り、コマンドの出力を全量ログへ逃がして固定量の要約だけを返すことで呼び出し元の context window を守る。

包むコマンドは 2 つで、どちらも「自分のオプション」と「包む対象」を `--` で区切り、区切り以降は解釈せずそのまま渡す。

- `throttle [--timeout <seconds>]` — 同一ホスト × 同一名前空間で、包んだコマンドの同時実行数を上限以下に保つ。上限の既定は 1 で、`MST_THROTTLE_LIMIT` から上書きできる。空きが無ければ待ち、待機は有界。保持 process が終了すれば OS がスロットを解放し、生きている保持者はコマンドが終わるか打ち切られるまで保持する。`--timeout` は process tree 全体を打ち切る。POSIX は穏当な終了要求 → 猶予 → 強制終了、Windows は `taskkill /T /F` による即時強制終了を使う。0 は打ち切らない
- `spool` — 包んだコマンドの出力を全量ログファイルへ逃がし、呼び出し元には固定行数の要約だけを返す。記録は package.json を目印にした上方探索で決まる `.spool/` に置かれ、端末制御のエスケープ列は除去される。CI（環境変数 `CI`）ではジョブログ自体が耐久的な記録なので素通しに切り替わる

`spool` が包んだコマンドは計測の対象でもある。包んだ 1 件がスパンになり、所要時間が分布として出て、記録した本文が LogRecord として出る。子プロセスへは trace の文脈を環境変数で渡すので、子が自分を計測していれば同じトレースの中に入れ子で並ぶ。

計測を立ち上げる口はこのパッケージが持ち、`@repo/ai-native/telemetry` として公開する。provider を組むのは 1 プロセスで 1 回だけで、最初に求めた入口が `service.name` を決める。有効化は `MST_TELEMETRY`、送信先は `OTEL_EXPORTER_OTLP_ENDPOINT`、停止は `OTEL_SDK_DISABLED` が決める。

- IF: 計測を仕込む; THEN
  - MUST: 時間を使っている当人に仕込む
  - PROHIBIT: 計測のためだけにコマンドを包む
    - 包み忘れた経路は、計測結果の上では速い経路と同じ見た目になる
- IF: プロセスの終了前に片付けたいものがある; THEN
  - MUST: `beforeExit` に自分で登録する
  - PROHIBIT: 送信の停止処理より先に登録されることを前提にする
    - 停止はマイクロタスクへ回してあり、登録順に関わらず全ての片付けの後で始まる

3 つ目の `unabridged` は包まない。Claude Code の `PreToolUse` hook として標準入力から JSON を読み、Bash に渡されたコマンド行のコマンド位置に `head` / `tail` があれば `deny` を返す。通す判断のときは何も出さない。配線は採用するリポジトリの `.claude/settings.json` で `matcher` を `Bash` にして行う。hook を書くときの規律は [hook の書き方](docs/hooks.md) が持つ。

実行可能な契約は各コマンドのヘルプ本文とテストの 2 つである。振る舞いを変えるときは両方を同時に変える。

## 使い方の境界

- `throttle` を入れ子にしない。内側は独立した競合者としてスロットをもう 1 つ消費し、上限の意味が壊れる。合成の順序は `throttle` が外、`spool` が内
- `throttle` のスロット領域はローカルファイルシステム上の OS 一時領域に置く。NFS・SMB などのネットワークファイルシステムでは排他保証を持たない
- `throttle` が使う `slot-*.lock` は active process がある間に削除・改名・置換しない。スロット領域を一時ファイル清掃の対象にしない
- 対話が要るコマンドを `spool` で包まない。プロンプトが記録へ行き、端末には何も出ないまま入力待ちで止まる。進捗を見ながら人間が判断する実行にも向かない。進行中の出力を見たいときは、実行中の記録ファイルを別の端末から読む
- 終了コードだけでは「ラッパー自身が仕事を果たせなかった」と「子が同じ値で終了した」を区別できない。区別の手掛かりは要約が出たチャネルと文言である
- スロットの取得または解放に失敗した実行は、子が成功していても失敗として返る。ラッパー自身の失敗理由は stderr に出る
- 記録に失敗した実行は、子が成功していても失敗として返る。この経路では子自身の結末は終了コードから復元できない
- 記録は削除されない。退避先は作業ツリーの中の版管理対象外に置かれ、作業ツリーを捨てると記録も消える。それまでは実行のたびに 1 ファイル増え続ける
- `unabridged` が見るのはコマンド行のコマンド位置だけである。`bash -c '... | tail'` の内側は 1 個の文字列トークンにしかならず、`xargs head` の `head` はコマンド位置に来ない。どちらも通る。ここを広げるには入れ子のシェル解釈が要り、正当な記述と違反を区別する基準を作れていない
- `unabridged` は代替の手段が使えるかを確かめない。案内した `spool` がその作業ツリーに無ければ、拒否だけが残って出口が塞がる

## 読み手の規律

要約が指す記録ファイルを開くこと。同じコマンドをフィルタ付きで再実行しない。再実行はコストを二重に払う上に、非決定的な失敗を取り逃がす。
