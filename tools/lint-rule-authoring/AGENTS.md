# @template/lint-rule-authoring

## このパッケージが守るもの

lint による強制が、書かれた時点でも、時間が経った後でも、実際に効いている。

採用者は「このリポジトリで独自の lint ルールを書く人」である。ルールを 1 本も書かない利用者にも、抑制の作法を強制するルールは効く。逆にルールを書く人向けのルールは、ルールが 1 本も無ければ違反が発生しないので空振りするだけで害がない。だから採否を分けず、全部入りの config を 1 つだけ出す。

## 全体を貫く不変条件

- ルールの出所が ID から一意に決まる
  - oxlint プラグイン名をパッケージ名（スコープなし）にする。ID は長くなるが、短縮して出所が消えるコストの方が高い
- ルールと、その説明と、その検証が離れない
  - 1 本のルールについて実装・テスト・文書の 3 点が揃って初めて 1 単位になる
- 説明の権威が 1 箇所にある
  - ルールの散文は `docs/lint/` の文書ファイルだけが持つ。ルールのメタデータが持つのは、機械が索引や見出しを組み立てるために要る最小限の項目だけ
- 抑制の口が塞がれている
  - 広い範囲を一括で無効化するコメント 1 行でルールが骨抜きになる状態を作らない

## 提供するもの

- `@template/lint-rule-authoring` — factory・severity 語彙・テスト基盤・ルール索引の照合関数・このパッケージの oxlint config
- `@template/lint-rule-authoring/plugin` — oxlint が `jsPlugins` の指定子で読むエントリ
- `lint-rule-authoring check [--write]` — マニフェストの `lintRules` が宣言する置き場からルールを発見し、各ワークスペースの `packages/<workspace>/docs/lint/index.md`、skill を持つワークスペースの `skills/core/references/lint-rules.md`、リポジトリ直下の `docs/lint-rules-by-guideline.md` の生成領域を照合・再生成し、各ルールが根拠として名指しする規範文書を検査する CLI

出荷側の一覧を別に生成するのは、`docs/` が tarball に入らないためである。install した側が読めるのは skill だけで、`vp lint --print-config` は js plugin のルールを 1 本も出さない。出荷側の表は各ルールの文書へリポジトリの URL で繋ぐ。

## 規約

自前ルールを既定でどの重大度で入れるか、警告へ落とすことを誰が決めるかは [AGENTS.md](../../AGENTS.md) が持つ。

- IF: ルールを定義する; THEN
  - MUST: factory を通す
  - MUST: 自分のパスを渡した呼び出し結果を `src/create-rule.ts` から 1 つ named export する
    - ワークスペースごとの別名は関数ではなくファイルで持つ
  - PROHIBIT: 同じ変換を別名で 2 つ export する
    - どちらを使うべきかが設計上の曖昧さになる
- IF: ルール定義にメタデータを持たせる; THEN
  - MUST: 1 行の説明文と、根拠になっている規範文書の一覧と、出荷する preset に載るかの宣言だけにする
  - PROHIBIT: 詳しい例示や判断の背景を持たせる
    - メタデータと文書の両方に持たせると、別々に古くなる
- IF: ルールを出荷する preset に載せない; THEN
  - MUST: そのルールの meta に載せない宣言を書く
  - PROHIBIT: 宣言を書かずに preset の側だけで載せないでおく
    - 索引はルールの実装だけを読む。preset を読まないので、宣言が無いルールは配られているものとして並ぶ
  - 載せてよい条件と、文書に何を書くかは [AGENTS.md](../../AGENTS.md) が持つ
- IF: ルールを書く; THEN
  - MUST: そのルールが強制している規範文書を meta に名指しする
    - 規範を読んだ人が、そこまでのどこが機械に任されているかを `docs/lint-rules-by-guideline.md` から引ける
  - MUST: 名指しできる先を、リポジトリ直下か自分のワークスペースの `docs/guidelines/` の文書か `AGENTS.md` に限る
  - PROHIBIT: 決定の記録を根拠として名指しする
    - 決定の記録は誰も拘束しない。何を守るのかは規範文書の側にある
  - IF: 強制したい不変条件を持つ規範文書が無い; THEN
    - MUST: 規範文書の側を先に足す
    - PROHIBIT: 近い話題の文書を当てて済ませる
- IF: preset を束に分けて配る; THEN
  - MUST: ルールを束の名前のディレクトリに置く
    - 索引は、宣言されたルールディレクトリからの相対パスの先頭セグメントを束として読む。ルールの実装だけを読むという性質は変わらない
  - PROHIBIT: 束をルールの meta に宣言する
    - 束の名前は語彙として登録されることになり、同じ綴りの literal が全部違反になる。定数へ逃がすと、1 ファイルの構文解析では値が解決できない
  - 束のディレクトリを持たないワークスペースは、今までどおり 1 枚の表として並ぶ
- IF: 報告メッセージの本文を書く; THEN
  - MUST: 禁止の言い切りと、命令形の修正指示だけで構成する
    - 報告文は、違反した人が最初に読む修正指示である
  - MUST: 禁止を `must not` か `is forbidden` で述べる
    - 肯定形の `must` は満たすべき状態を述べるだけで、何が拒まれたかを名指ししない
  - MUST: 修正指示を命令動詞で始まる文にする
  - MUST: 英語で書く
  - PROHIBIT: 理由を書く
    - 理由を畳み込むと修正指示が後ろへ押し出され、長さに紛れて読まれない。理由は `docs/lint/` の文書が持つ
  - PROHIBIT: 条件で修正指示を分岐させる
    - 分岐は読み手に判断を戻す。場合分けは文書が持つ
  - PROHIBIT: 逃げ道を示す
    - 抑制の仕方や免除の申請先を書くと、それが最短の修正手段として読まれる
  - PROHIBIT: 文書への参照を手書きする
    - factory が末尾に付ける
- IF: ルールが閾値・語彙・例外といった判断材料を持つ; THEN
  - MUST: 既定値をルール本体の定数として持たせる
    - ルール単体を使う利用者には config が届かない。既定を config に置くと、その利用者には判断材料が無いままルールが動く
  - MUST: 上書きの口を `schema` に宣言したオプションとして開ける
  - MUST: 対象によって値を変えるなら、その判定もルールが持つ
    - 判定を config のファイル指定に出すと、ルールは自分がどの対象を見ているかを知らないまま動く。対象を条件にしたテストも書けなくなる
  - PROHIBIT: 配布する config に既定値を書く
    - config が持ってよいのは強制度と、このリポジトリ固有の事情に属する上書きだけである
- IF: ルールのテストを書く; THEN
  - MUST: 対象と同じディレクトリに、対象と同じ名前で `.test.ts` として置く
  - MUST: 通るべきコード片と落ちるべきコード片の 2 系統を持たせる
  - MUST: 通るべき側に、そのルールが誤検知しやすい境界を明示的に置く
  - MUST: 落ちるべき側に期待する報告メッセージ ID を添える
  - MUST: コード片に名前を付ける
  - PROHIBIT: `tests/` や `-spec/` のような隔離ディレクトリを作る
- IF: lint 設定を書く; THEN
  - MUST: ルートの `vite.config.ts` の `lint` ブロックに集約する
  - PROHIBIT: `oxlint.config.ts` / `.oxlintrc.json` / `.oxfmtrc.json` / `vitest.config.ts` を作る

## factory が足すもの

変換関数が足すものは 2 つ。

- `meta.docs.url` に、そのルールの文書の完全 URL
- すべての報告メッセージ本文の末尾に、リポジトリ相対の文書パス

文書の在り処はワークスペースの位置とルール名から機械的に決まる。ルールの作者がパスを書くことはない。
