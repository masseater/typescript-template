---
title: 置き場所と道具
description: 成果物をどこに置き、何で作り、どこから呼ぶかを決める基準
---

この文書が守るのは、成果物の置き場所と道具立てが、そのまま「誰に届くか」と「どの種類の失敗を受け入れたか」の宣言として読める状態である。読めなくなった時点で、次に同じ判断をする人は別の根拠で決めることになり、失敗の再現も修正も当て推量になる。

このリポジトリは、外部の利用者に配るパッケージを 1 つも持たない。ワークスペースはすべて `private` で、外へ届くのは Cloudflare Workers へデプロイされるアプリと、Alchemy が外部サービスに残す状態の 2 つだけである。節は外に出る面から内側へ並べてあり、外へ届く面と共有の取り決めが先に、置き場所と道具と版と入口が続き、最後に機械が判定できる性質を挙げる。

## 外に出る面と、それが名乗る責務

このリポジトリの成果物は 2 種類の面を持ちうる。他のワークスペースから import される面と、コマンドとして起動される面である。どちらも、宣言した時点で保守の対象になる。

- MUST: 取り込まれるパッケージが持つ責務を 1 つに保つ
- MUST: 公開するサブパスを、そのパッケージが所有する 1 つの責務の内側に収める
  - `@repo/observability` が `./browser`、`./sentry`、`./sentry-server`、`./sentry-browser` をサブパスで配っているのがこの形にあたる
- PROHIBIT: サブパスを分けたことを、影響の範囲が縮む根拠にする
  - 変更の影響はワークスペース間の依存の辺で判定され、どのサブパスを取り込んでいるかまでは見ない
- MUST: パッケージが宣言する面を、既定では 1 種類に保つ
- IF: 取り込まれるだけのパッケージにコマンド入口を足したくなった; THEN PROHIBIT: 足す
- IF: 取り込まれるパッケージに、その責務の外側にある実行体が要る; THEN MUST: コマンド入口とコマンド固有の依存を、その実行体を所有する別のワークスペースへ移す
- IF: 1 つのパッケージに両方の面を持たせる; THEN
  - MUST: 2 つの面が同じ 1 つの責務の別の現れであることを示す
    - `@repo/db` が、スキーマと接続を取り込まれる面として、migration の適用をコマンドとして持っているのがこの形にあたる
  - MUST: 宣言したそれぞれの面に、実際の利用者がいることを示す
- PROHIBIT: 薄いラッパーや別のスクリプトを経由して、閉じている側の面に到達させる

どの種類の宣言をどのパッケージへ集約するかは `AGENTS.md` のコードルールが決めている。

## 共有に踏み切る条件

共有には 2 つある。実装を切り出して複数の側から取り込む形と、独立して変わる側が同じ語彙を持ち続けるための取り決めを配る形である。取り決めにあたるのは、共有 tsconfig のプリセット、Nuxt の共通設定、検査が読む語彙と閾値の既定値で、実行できる実装は取り決めではない。切り出すかどうかは実際に使っている場所の数で決まり、取り決めをどこに置くかはそれが記述している領域で決まる。

- IF: あるワークスペースのコードを、別のワークスペースからも使いたくなった; THEN MUST: 実際に取り込むワークスペースが 2 つ以上になってから切り出す
- IF: 切り出したパッケージの取り込み元が 1 つに減った; THEN MUST: 残った 1 つの内側に畳み直す
- IF: 所有者も呼び出し元も 1 つのワークスペースに閉じている; THEN MAY: そのワークスペースの内側にスクリプトを置く
- IF: 呼び出し元が 2 つ目になった; THEN MUST: ワークスペースが所有するコマンドに移す
  - CI から呼ばれ始めた時点で、2 つ目の呼び出し元が現れている
- PROHIBIT: 実行できる実装を、取り決めの置き場所に入れる
- MUST: 取り決めを、それが記述している領域で束ねる
  - `tsconfig.base.json` が TypeScript の設定を持っているのがこの形にあたる
- PROHIBIT: 1 つのワークスペースの内側にしか関係しない設定を、共有される取り決めに置く
- IF: 新しい取り決めが既存のどの領域にも当てはまらない; THEN
  - MUST: 何を所有するかを名前にした新しい置き場所を作る
  - PROHIBIT: 近いという理由で既存の取り決めに相乗りさせる
- IF: 取り込む側の 1 つだけが持つ制約のために、取り込まれる側の形を変えたくなった; THEN
  - MUST: 回避策を、制約を持っている側に置く
  - PROHIBIT: 供給する側を全ての取り込み元ぶん変える

## 置き場所は届く相手で決める

- MUST: 誰に届くか、壊れたとき何が止まりどこまで影響するか、単独で起動と停止ができるか、取り込まれるのか実行されるのかで決める
  - 言語が同じでも道具立てが同じでも、これらが違えば別の場所に置く
- PROHIBIT: 実装の見た目を根拠に置き場所を決める
  - コマンド入口を持つことも、サーバーが立つことも、届く相手を決めていない

区分は候補を全部見比べて選ぶのではなく、順序を固定し、最初に当てはまったところで確定させる。

1. 外部サービスに状態を残す宣言。`infra/` に置く
2. デプロイされて外部の利用者からの要求を受ける実行対象。`apps/` に置く
3. 複数のワークスペースが取り込む共有物。`libs/` に置く
4. 上のどれでもないもの。それを使っている既存のワークスペースの内側に置く

- MUST: 上の順に照らし、最初に当てはまった区分で確定させる
- PROHIBIT: 外部サービスに状態を残すかどうかより先に、実行される形をしているかどうかで区分を決める
- IF: 新しい成果物が既存の区分の定義に収まる; THEN PROHIBIT: 並列の新しいトップレベルを作る
- IF: どの既存の区分に入れても、その区分の定義が偽になる; THEN
  - MUST: 区分を増やす
  - MUST: どの既存の区分もその成果物を所有しないことを、増やす前にコミットログに残す
- PROHIBIT: 中身の無い区分を宣言だけ先に置く
- PROHIBIT: 整理されて見えることや、今後増えそうであることを根拠に区分を増やす
- IF: どの区分にも当てはまらないものを受ける残余の区分を作る; THEN
  - MUST: 残余に置いたものを、所有者がまだ決まっていない印として扱う
  - MUST: 残余が増えたら、区分を増やすか所有者を決めるかで減らす
  - PROHIBIT: 置き場所に迷ったものの既定の行き先として残余を使う

## 道具は対象の構造で選ぶ

道具を選ぶときに見るのは、扱う対象が持っている構造を、その道具が表現できるかどうかである。

- IF: ソースコードを書き換える処理を書く; THEN MUST: 構文木の上でノードを編集し、整形を壊さない層を入力にする
- IF: ソースコードを読み取る処理を書く; THEN
  - MUST: 対象言語の公式コンパイラが提供する構文木を入力にする
  - PROHIBIT: 行やパターンのテキストマッチで構文を判定する
- IF: 取り出したい範囲がごく小さく、テキストマッチのほうが速い; THEN MUST: 構文木を入力にする
- IF: 依存が持つ能力を使う; THEN
  - MUST: 型付きの API があるならそれを使う
  - PROHIBIT: 型付きの API があるのに実行ファイルを子プロセスとして起こす
- IF: 依存が実行ファイルしか提供しない; THEN
  - MUST: 自分が所有する型付きの薄い層で包む
  - MUST: 受け取った出力を検証してから呼び出し側に渡す
  - PROHIBIT: 素の子プロセス呼び出しを呼び出し箇所に直接置く
- IF: 外部サービスにアクセスする; THEN MUST: リトライ・応答の解釈・認証を 1 つの型付き境界に集める
- IF: 外部サービスの設定を変える; THEN
  - MUST: Alchemy の宣言に書く
  - PROHIBIT: 管理画面での手作業や、その場限りの API 呼び出しで済ませる
    - 管理画面で入れた値は、誰がいつ何を変えたのかを追えない。宣言に置けば、実体とのずれを `alchemy plan` が毎回見つける
- IF: 公式のドキュメントに載っていない API しか無い; THEN MAY: その API を呼ぶ dynamic provider を書く
- PROHIBIT: 公式の実行ファイルが手近にあることを、型付きの境界を通さない理由にする

## 版の出どころを 1 点に保つ

守るのは 2 つで、どのプロセスも同じ版を見ていることと、活性化が二重に掛からないことである。

- IF: 道具の版を固定する; THEN MUST: 宣言的に固定でき、プロセスの環境へ 1 度だけ注入できる機構に寄せる
- IF: いまいる実行が、環境を用意する側か、用意された環境を継いだ側かを決める; THEN
  - MUST: 活性化を所有する境界がすでにあるかで決める
  - PROHIBIT: 呼び出し元が人か別プロセスかの見た目で決める
- IF: 用意された環境を継いだ側である; THEN
  - MUST: 継いだ環境からそのまま呼ぶ
  - PROHIBIT: 活性化をもう 1 度重ねる
- IF: 環境を用意する側である; THEN MUST: そこで 1 度だけ活性化し、以降を継承した環境で走らせる
  - 用意する側にあたるのは、人が対話的なシェルから始める場合と、フックや自動実行のジョブが準備を担う場合である

## 入口とコマンドの単位

要求は 2 つある。呼び出し側から見て正しい入口が 1 つに決まっていること。落ちたコマンドの名前だけで、壊れている不変条件と直す方向が決まっていること。

- IF: 実行可能物を作る; THEN MUST: それを所有するパッケージを 1 つ決める
- IF: リポジトリのルートから実行可能物を呼べるようにする; THEN
  - MUST: 所有パッケージへの薄い委譲だけを置く
  - PROHIBIT: 既存の入口へ委譲するためだけの別名や表記違いの入口を足す
- IF: git のフックのように、置き場所を外の仕組みが決めている起動口がある; THEN
  - MUST: 起動口には、ワークスペースが所有するコマンドの呼び出しだけを置く
  - PROHIBIT: 起動口に検査の中身を実装する
- PROHIBIT: リポジトリのルート直下に、自動化の実装の本体を置く
  - そこに置かれた実装はワークスペースのグラフの外にあり、依存の宣言も型検査もテストも未使用の検出も掛からない
- IF: 実行可能物を呼び出す; THEN
  - MUST: 正規の入口を使う
  - PROHIBIT: 内部のパッケージのバイナリを直接叩く
- PROHIBIT: テストからしか到達しない口を作る
- IF: 手元・フック・自動実行・文書から同じ処理を呼ぶ; THEN MUST: 同じ呼び方が通る状態を保つ
- MUST: 個別に呼ぶコマンドを、落ちたときに壊れている不変条件と直す方向が 1 つに決まる単位にする
- IF: 手元でまとめて走らせる入口が要る; THEN
  - MUST: 個別のコマンドを並べた入口として用意する
  - PROHIBIT: 個別のコマンドを 1 つに統合して入口を作る
- MUST: 手元で走らせる検査と CI が同じまとまりを起動することを、片方からの導出か、ずれを機械的に検出して落とす形で保つ

## 呼び出し側に選ばせる値を絞る

呼び出し側が本当に選ぶ値だけがオプションとして現れている状態を保つ。目的から一意に決まる値をオプションにすると、呼び出し箇所ごとに同じ値を書き写すことになり、書き写しの食い違いが設定ミスとして表面化する。

- IF: オプションを足そうとしている; THEN
  - MUST: その値が呼び出し側の選択なのか、コマンドの目的か実行時の文脈から決まるのかを先に確かめる
  - PROHIBIT: コマンドの目的から一意に決まる値をオプションにする
- IF: 実行時の文脈から取れる値を使う; THEN
  - MUST: その文脈を読む境界で受ける
  - PROHIBIT: 同じ値をオプションとしても受ける
- IF: 手元の実行と自動実行で挙動を変えたい; THEN
  - MUST: その差を実行時の文脈から導く
  - PROHIBIT: 呼び出し側が渡すモードや、自動実行専用の複製したスクリプトで表現する
- IF: 呼び出し側が本当に別の戦略を選ぶ; THEN
  - MUST: 目的ごとに分かれたサブコマンドにする
  - PROHIBIT: 挙動を切り替えるモードのフラグにする
- IF: 秘密の値を扱うコマンドを書く; THEN
  - MUST: 保管先のキーやパスという参照で受ける
  - PROHIBIT: 値そのものを普通のオプションで受ける

## 使い方の記述が受け口と一致している

使い方として表示される記述は、そのコマンドが外へ出す面である。実体とずれても何も落ちないので、ずれは次に使う人が試したときに初めて見つかる。

- MUST: 受け付ける引数と、使い方として表示される記述を、同じ変更で揃える
- IF: 引数か説明を変えた; THEN MUST: 表示される使い方と正常終了を実際に実行して確認する
- IF: オプションを定義する; THEN
  - MUST: そのオプションが値を取るかどうかで、使い方の記述に出すものを決める
  - MUST: 値を取るものについては、値の形と、指定しなかったときに実際に使われる値を読める形にする
  - PROHIBIT: 値を取らないものに、値の受け口があるように読める記述を付ける
- IF: コマンドの説明を書く; THEN
  - MUST: 目的を述べる 1 文に収める
  - PROHIBIT: 手順や環境の説明をそこに詰め込む
- IF: 説明に書きたい情報が多い; THEN MUST: 1 文に収まらないものを別の場所へ移す

## 標準出力と診断を別の系統に出す

既定の標準出力は、人が読むとは限らない面である。読み手が機械なら、結果に混ざったものはすべて雑音になる。

- IF: 既定の標準出力を別のプログラムや AI が消費する; THEN
  - MUST: 結果だけで構成する
  - PROHIBIT: 途中経過・デバッグ・進捗を混ぜる
- IF: 診断を出す; THEN MUST: 結果とは別の系統に出す
- IF: 子プロセスを包むコマンドが自動実行の中で動く; THEN MUST: 子の出力を捨てずに、そのまま記録へ流す

## 機械が判定できる性質

置き場所と道具の判断のうち、宣言とコードの構造だけを読んで真偽が決まるものは、機械が判定できる。上の節の順に挙げると次のものがこれにあたる。

- 宣言した公開面に、実際にそれを使っている場所があるか。`knip` がこれを見ている
- 各ワークスペースが共有された tsconfig のプリセットを指しているか、そこから外れた独立の設定になっているか
- 型付きの API が存在する依存に対して、実行ファイルを子プロセスとして起こしているか
- 子プロセスの出力を、検証を通さずそのまま呼び出し側の値として扱っているか
- 値を取らないオプションの宣言に、値の受け口を表す記述が付いているか
- 既存の入口へ委譲するだけの別名の入口が存在するか
- 内部のパッケージのバイナリが、正規の入口を飛ばして直接呼ばれているか
- テストからしか到達しない口が存在するか
- 実行時の文脈から取れる値が、オプションとしても受けられる二重の入口になっているか

判定できることと、その検査がこのリポジトリで動いていることは別である。いま動いているのは各 workspace の lifecycle タスクが依存させた検査だけで、残りは人が見る対象に戻る。宣言の形からは真偽が決まらないものもあり、1 つのパッケージが宣言する面の混ぜ方、個別に呼ぶコマンドの単位、取り決めの置き場所は、いずれも人が見る。使い方の記述と受け口が揃っているかは、コマンドを実行して確かめる。
