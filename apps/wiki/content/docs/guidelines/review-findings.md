---
title: レビューの指摘
description: 指摘を 2 つの問いに掛けて扱いを 1 つに決め、修正が閉じる時点までを固定する基準
---

このリポジトリには、指摘を出す側と直す側を分ける体制が無い。指摘はエージェントが出し、エージェントが直し、そのまま main に入る。分類が感想に変わったことに気付く第三者がいないので、扱いを先に固定しておくことがその代わりになる。

決める権限を持つのはオーナー 1 人である。エージェントに正しさが判定できない指摘ではなく、判定はできても決める資格が無い指摘が存在する。

統合は必ずマージコミットになり、その時点で `.githooks/pre-push` の検査が走る。機械が止められるものは分類を待たずに止まっているので、ここで決めるのは、機械が黙って通した範囲を main へ入れてよいかだけである。機械が黙って通す範囲がどこまでかは、`.githooks/pre-push` が実際に何を走らせているかで決まる。

## 指摘に当てる 2 つの問い

問いは 2 つしかない。解消を決める資格がオーナーの側にあるか。解消しないまま main へ入れたとき、この変更を受け入れてよいと言える材料が残るか。答えの組が扱いを 1 つに決める。

資格の問いを先に当てる。この体制では扱いがそのまま行動を決めるので、オーナーが決めるべき事柄を自分で直せるものとして置くと、エージェントは指摘どおりに直し、直した内容がオーナーの決定の代わりに残る。

- IF: 解消を決める資格がオーナーの側にある; THEN
  - MUST: オーナーの決定を待つものとして扱う
  - PROHIBIT: オーナーが扱いを決め直すまで main へ入れる
- IF: 決める資格がこちらにあり、解消しないまま main へ入れると受け入れてよいと言える材料が残らない; THEN
  - MUST: main へ入れる前に消すものとして扱う
  - PROHIBIT: 解消しないまま main へ入れる
- IF: 決める資格がこちらにあり、材料は残り、拘束力のある基準への実在する違反である; THEN
  - MUST: 出力に残したまま main へ入れてよいものとして扱う
  - MAY: 解消しないまま main へ入れる
  - MUST: 解消されるまでレビューの出力に残す
- IF: 決める資格がこちらにあり、材料は残り、拘束力のある基準に一切触れていない; THEN
  - MUST: 採否を書き手に委ねるものとして扱う
  - MAY: 採否を書き手の判断に委ねる
- PROHIBIT: 1 つの指摘に 2 つ以上の扱いを付ける
- PROHIBIT: 提案されている解決が先送りであることを理由に扱いを軽くする
  - 日程を指す言い回しも、スコープを指す言い回しも、段階を踏むという言い回しも、指摘そのものの影響を変えない
- PROHIBIT: 同じ違反が周りのコードにも残っていることを理由に扱いを軽くする
  - 分類が周囲の状態を入力に取ると、違反の密度がそのまま基準の緩さになる
- IF: 2 つの問いから決まる扱いと、既存の違反や先送りの提案が示す軽さが衝突する; THEN MUST: 問いから決まる扱いを採る

## 受け入れてよいと言える材料が残るか

材料を供給しているのは、機械の判定と、差分そのものと、書かれた記述と、外へ出た変更を受け取る側の 4 つである。どれかが供給を止めたら、その変更を受け入れてよいと後から言えなくなる。

**機械の判定が材料を出さなくなる。** 品質ゲートを下げる変更とは、検査の対象からファイルや範囲を外すもの、有効だった検査を無効にするもの、失敗を報告だけに落とすもの、通過の閾値を緩めるもの、検出結果を無視の一覧に載せるものを指す。実行の段に継続許可を付けることは、失敗を報告だけに落とす操作にあたる。

- IF: 変更が品質ゲートを下げている; THEN
  - IF: 下げる範囲と、下げたことで守られなくなるものを名指ししたオーナーの決定が記録されている; THEN MUST: 記録された範囲の内側については指摘の対象にしない
  - IF: 決定の記録が無い、または記録された範囲を超えている; THEN MUST: main へ入れる前に消すものとして扱う
- PROHIBIT: 検出されない書き方へ形を変えて報告を消す
  - 扱いは、回避された規範そのものに付く扱いに従う

**差分そのものが材料を出さなくなる。** 統合が必ずマージコミットになる以上、統合後の木は両方の親の効果の合成として読めなければならない。合成として読めなくなる形は 1 つで、両親の効果と統合後の木が一致しないことである。

- IF: 統合後の木が、両方の親の変更を効果として保っていない、またはどちらの親にも無かった振る舞いを持っている; THEN MUST: main へ入れる前に消すものとして扱う
- IF: 解消のついでに入った変更が振る舞いを変えていない; THEN MUST: マージの外で同じことをしたときと同じ扱いにする
  - 整形や改名を、マージの中だからという理由で重くしない
- IF: 変更が次のいずれかを起こしている; THEN MUST: main へ入れる前に消すものとして扱う
  - テストが無い
  - 責務の境界を越えている、または依存の向きが逆になっている
  - 深刻な性能の問題がある

**書かれた記述が材料を出さなくなる。**

- IF: 指摘が次のいずれかに当たる; THEN MUST: main へ入れる前に消すものとして扱う
  - 実装の振る舞いと、それを定めた文書が食い違っている
  - 要求されている文書が存在しない
  - 要約が、リンク先の所有元と食い違っている、または誤って表している
  - 変更が基準の文書に矛盾を作った、または矛盾の片側だけを直して残した
  - 外部サービスの実体を変えたのに、それを記録する台帳が更新されていない
- IF: 基準が特定の機構を名指ししているのに、変更が別の機構で置き換えた; THEN MUST: main へ入れる前に消すものとして扱う
  - 表面の振る舞いが同じであることは、置き換えた側が同じものを守っている証拠にならない

**外へ出た変更を受け取る側で取り返しがつかなくなる。**

このリポジトリが外へ出すのは、Cloudflare Workers へデプロイされるアプリと、Pulumi が外部サービスに残す状態である。どちらも main へ入った時点で自動的に適用される。

- IF: 変更が、利用者のデータを壊す、秘密を露出する、または回復できない失敗を起こす; THEN MUST: main へ入れる前に消すものとして扱う
- IF: 変更が、外に残る資源を削除する、または子を持つ階層を置き換える; THEN MUST: main へ入れる前に消すものとして扱う
- IF: 変更が、共有される境界で必須の型・スキーマ・フィールド・引数を省略可能にした; THEN MUST: main へ入れる前に消すものとして扱う
  - 緩めた側では何も壊れないまま、取り込み側が前提にしていた保証だけが外れる
- IF: 4 つのどれが供給を止めたのか迷う; THEN MUST: この変更を受け入れてよいと後から言えるか、という問いに戻して決める

## 材料が残った側の分かれ道

材料が残っている指摘は、拘束力のある基準への違反かどうかだけで 2 つに分かれる。

- IF: 指摘が、詳細の所有元が 1 つに決まっていないことに関わる; THEN MUST: 出力に残したまま main へ入れてよいものとして扱う
  - 所有元が読み取れない場合も、複数の文書が同じ詳細を独立に持っている場合も同じである
- IF: 機械可読なメタデータや注釈が誤っている; THEN
  - MUST: 受け入れてよいと言える材料が残るか、という同じ問いで判定する
  - IF: その誤りが、発見や影響範囲の解析に効きうる; THEN MUST: 出力に残したまま main へ入れてよいものとして扱う
  - IF: その誤りが、効かないと示せた純粋な文言だけの問題である; THEN MUST: 採否を書き手に委ねるものとして扱う
    - 効かないと示せたことが要件であって、効かなそうだから書き手に委ねるのではない
- IF: 詳細の所有元が別にあり、参照する側が所有元への明示的なリンクと 1 段落に収まる正確な要約しか持っていない; THEN PROHIBIT: その参照を重複として報告する
- IF: 要約と所有元の両方を読んで一致を確かめていない; THEN PROHIBIT: 一致しているものとして扱う
- IF: 重複を減らしたいことと、所有元への正確な要約とリンクを残すことが衝突する; THEN MUST: 要約とリンクを残す

## 決める資格がオーナーの側にあるとき

- IF: 決めるべき事柄が次のいずれかに当たる; THEN MUST: オーナーの決定を待つものとして扱う
  - 本物の例外として認めるかどうかがオーナーの判断に掛かる
  - 方針・公開範囲・外へ出す値の守り方・オーナーの意図の決定を要する
  - 拘束力のある 2 つの基準が衝突していて、その衝突についてのオーナーの決定が記録されていない
  - 実在の利用者に届く変更を適用してよいかの判断を要する
- IF: レビュー対象の差分が、その衝突を作った、または広げた; THEN MUST: 差分の側の指摘として同じ 2 つの問いに掛ける
- IF: 衝突している 2 つの基準のうち、片方が明らかに厳しい; THEN
  - MUST: 厳しい側でレビューする
  - MUST: 矛盾している文書自体を、別の指摘として同じ 2 つの問いに掛ける
- IF: オーナーの決定を待つものとして扱った; THEN
  - MUST: オーナーの応答を待つ
  - PROHIBIT: 自分で決めて先へ進める
- IF: オーナーが解決した; THEN
  - MUST: マージの扱いがどう決まったかを、main へ入れる前に恒久的な証跡へ記録する
  - MUST: その決定が既存の基準を変えるなら、拘束力のある文書か版の履歴に反映させる
- IF: 判断や証拠を恒久的な証跡として残す; THEN MUST: コミットメッセージの本文か、そこからリンクされたコミット済みの成果物に置く

## 修正が終わる時点

- IF: 欠陥を直す; THEN MUST: その失敗を成立させている条件が何かを、報告された場所から離して言葉にする
- IF: その条件が他の場所にも成り立ちうる; THEN
  - MUST: 探す範囲を先に決めてから探す
  - MUST: 見つかった箇所を、報告された欠陥と同じ変更の中で全部直す
  - PROHIBIT: 見つかった箇所を 1 つでも残したまま、その条件を閉じたと呼ぶ
  - PROHIBIT: 差分を小さく保ちたいことを理由に、残りを別の変更へ切り出す
    - 切り出しは完了の先送りなので、先送りを理由に扱いを軽くしないという規律がそのまま掛かる
  - PROHIBIT: 綴りの一致だけを頼りに探して、それで全部だとみなす
    - 同じ条件は、別の綴りでも、探している最中に新しく足された箇所でも成り立つ
- IF: 条件が成り立ちうる範囲に、この変更からは構造的に届かない場所がある; THEN
  - MUST: その範囲と、そこまで届いていないことを恒久的な証跡へ残す
  - PROHIBIT: 届いていない範囲を残したまま、その条件を閉じたと呼ぶ
- IF: 他の場所には成り立ちえないと判定した; THEN MUST: 成り立ちえない理由を、後から検証できる形で残す
- IF: 修正の完了を記録する; THEN
  - MUST: 何が同じ失敗を成立させるのかを、恒久的な証跡へ残す
  - MUST: 機械で止める側に回すかどうかの判断を、同じ証跡へ残す
  - MUST: 決めた範囲と、その中を実際に探した手順と結果を、後から再実行できる形で同じ証跡へ残す
- PROHIBIT: 証跡に残っていないものを、探索が済んだ証拠として扱う
- IF: 同じ条件が他の場所にも成り立ちうる修正をレビューする; THEN PROHIBIT: 再現できる探索の証拠と全箇所の解消なしに、main へ入れる前に消すものは無いと判定する
- PROHIBIT: 見つかった箇所の多さを、機械で止めるかどうかの判断の入力にする

## 機械が黙って通す側

このリポジトリで機械が拾うのは、Oxfmt が見る整形、Oxlint が JavaScript と TypeScript で見る書き方、`vp check` が見る型、`knip` が見る使われていない export と依存、`.githooks/` が見る平文の環境変数ファイルとコミットメッセージの形、`pulumi preview` が見る宣言と実体のずれである。

残りは人が見る側にある。統合後の木で効果を失った変更も、テストの不在も、探索が完了したかどうかも、起動の条件から外れて走らなかった検査もそこに入る。
