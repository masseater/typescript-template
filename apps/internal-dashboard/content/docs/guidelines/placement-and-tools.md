title: 置き場所と道具
description: 成果物をどこに置き、何で作り、どこから呼ぶかを決める基準
---

この文書が守るのは、成果物の置き場所と道具立てが、そのまま「誰に届くか」と「どの種類の失敗を受け入れたか」の宣言として読める状態です。読めなくなった時点で、次に同じ判断をする人は別の根拠で決めることになり、失敗の再現も修正も当て推量になる。

このリポジトリの外へ届く面は、Cloudflare Workers へデプロイされるアプリ、Alchemy が外部サービスに残す状態、および `tools/ai-native`・`tools/ai-native-telemetry`・`tools/dont-review-it` の npm 公開面（`private` を持たず `publishConfig.access: public`）です。節は外に出る面から内側へ並べてあり、外へ届く面と共有の取り決めが先に、置き場所と道具と版と入口が続き、最後に機械が判定できる性質を挙げる。

## 外に出る面と、それが名乗る責務

このリポジトリの成果物は 2 種類の面を持ちうる。他のワークスペースから import される面と、コマンドとして起動される面です。どちらも、宣言した時点で保守の対象になる。

- 取り込まれるパッケージが持つ責務を 1 つに保ちます。
- 公開するサブパスを、そのパッケージが所有する 1 つの責務の内側に収めること。
  - `@repo/observability` が `.`、`./browser`、`./testing` をサブパスで配っているのがこの形にあたる
- サブパスを分けたことを、影響の範囲が縮む根拠にしてはいけません。
  - 変更の影響はワークスペース間の依存の辺で判定され、どのサブパスを取り込んでいるかまでは見ない
- パッケージが宣言する面を、既定では 1 種類に保ちます。
- 取り込まれるだけのパッケージにコマンド入口を足したくなった場合は、足すことは禁止です。
- 取り込まれるパッケージに、その責務の外側にある実行体が要る場合は、コマンド入口とコマンド固有の依存を、その実行体を所有する別のワークスペースへ移します。
- 1 つのパッケージに両方の面を持たせる場合は、次のとおりです。
  - 2 つの面が同じ 1 つの責務の別の現れであることを示します。
    - `@repo/db` が、スキーマと接続を取り込まれる面として、migration の適用をコマンドとして持っているのがこの形にあたる
  - 宣言したそれぞれの面に、実際の利用者がいることを示します。
- 薄いラッパーや別のスクリプトを経由して、閉じている側の面に到達させることは禁止です。

## 共有に踏み切る条件

共有には 2 つある。実装を切り出して複数の側から取り込む形と、独立して変わる側が同じ語彙を持ち続けるための取り決めを配る形です。取り決めにあたるのは、共有 tsconfig のプリセット、検査が読む語彙と閾値の既定値で、実行できる実装は取り決めではありません。切り出すかどうかは実際に使っている場所の数で決まり、取り決めをどこに置くかはそれが記述している領域で決まる。

- あるワークスペースのコードを、別のワークスペースからも使いたくなった場合は、実際に取り込むワークスペースが 2 つ以上になってから切り出します。
- 切り出したパッケージの取り込み元が 1 つに減った場合は、残った 1 つの内側に畳み直すこと。
- 所有者も呼び出し元も 1 つのワークスペースに閉じている場合は、そのワークスペースの内側にスクリプトを置いても構いません。
- 呼び出し元が 2 つ目になった場合は、ワークスペースが所有するコマンドに移します。
  - CI から呼ばれ始めた時点で、2 つ目の呼び出し元が現れている
- 実行できる実装を、取り決めの置き場所に入れることは禁止です。
- 取り決めを、それが記述している領域で束ねること。
  - `tsconfig.base.json` が TypeScript の設定を持っているのがこの形にあたる
- 1 つのワークスペースの内側にしか関係しない設定を、共有される取り決めに置くことは禁止です。
- 新しい取り決めが既存のどの領域にも当てはまらない場合は、次のとおりです。
  - 何を所有するかを名前にした新しい置き場所を作ります。
  - 近いという理由で既存の取り決めに相乗りさせることは禁止です。
- 取り込む側の 1 つだけが持つ制約のために、取り込まれる側の形を変えたくなった場合は、次のとおりです。
  - 回避策を、制約を持っている側に置きます。
  - 供給する側を全ての取り込み元ぶん変えることは禁止です。

## 置き場所は届く相手で決める

- 誰に届くか、壊れたとき何が止まりどこまで影響するか、単独で起動と停止ができるか、取り込まれるのか実行されるのかで決めます。
  - 言語が同じでも道具立てが同じでも、これらが違えば別の場所に置く
- 実装の見た目を根拠に置き場所を決めることは禁止です。
  - コマンド入口を持つことも、サーバーが立つことも、届く相手を決めていない

区分は候補を全部見比べて選ぶのではなく、順序を固定し、最初に当てはまったところで確定させる。

1. 外部サービスに状態を残す宣言。`infra/` に置く
2. デプロイされて外部の利用者からの要求を受ける実行対象。`apps/` に置く
3. 複数のワークスペースが取り込む共有物。`libs/` に置く
4. 上のどれでもないもの。それを使っている既存のワークスペースの内側に置く

- 上の順に照らし、最初に当てはまった区分で確定させること。
- 外部サービスに状態を残すかどうかより先に、実行される形をしているかどうかで区分を決めることは禁止です。
- 新しい成果物が既存の区分の定義に収まる場合は、並列の新しいトップレベルを作ることは禁止です。
- どの既存の区分に入れても、その区分の定義が偽になる場合は、次のとおりです。
  - 区分を増やすこと。
  - どの既存の区分もその成果物を所有しないことを、増やす前にコミットログに残します。
- 中身の無い区分を宣言だけ先に置くことは禁止です。
- 整理されて見えることや、今後増えそうであることを根拠に区分を増やすことは禁止です。
- どの区分にも当てはまらないものを受ける残余の区分を作る場合は、次のとおりです。
  - 残余に置いたものを、所有者がまだ決まっていない印として扱います。
  - 残余が増えたら、区分を増やすか所有者を決めるかで減らすこと。
  - 置き場所に迷ったものの既定の行き先として残余を使うことは禁止です。

## 道具は対象の構造で選ぶ

道具を選ぶときに見るのは、扱う対象が持っている構造を、その道具が表現できるかどうかです。

- ソースコードを書き換える処理を書く場合は、構文木の上でノードを編集し、整形を壊さない層を入力にします。
- ソースコードを読み取る処理を書く場合は、次のとおりです。
  - 対象言語の公式コンパイラが提供する構文木を入力にします。
  - 行やパターンのテキストマッチで構文を判定してはいけません。
- 取り出したい範囲がごく小さく、テキストマッチのほうが速い場合は、構文木を入力にします。
- 依存が持つ能力を使う場合は、次のとおりです。
  - 型付きの API があるならそれを使います。
  - 型付きの API があるのに実行ファイルを子プロセスとして起こすことは禁止です。
- 依存が実行ファイルしか提供しない場合は、次のとおりです。
  - 自分が所有する型付きの薄い層で包むこと。
  - 受け取った出力を検証してから呼び出し側に渡すこと。
  - 素の子プロセス呼び出しを呼び出し箇所に直接置くことは禁止です。
- 外部サービスにアクセスする場合は、リトライ・応答の解釈・認証を 1 つの型付き境界に集めること。
- 外部サービスの設定を変える場合は、次のとおりです。
  - Alchemy の宣言に書きます。
  - 管理画面での手作業や、その場限りの API 呼び出しで済ませることは禁止です。
    - 管理画面で入れた値は、誰がいつ何を変えたのかを追えありません。宣言に置けば、実体とのずれを `alchemy plan` が毎回見つける
- 公式のドキュメントに載っていない API しか無い場合は、その API を呼ぶ dynamic provider を書いても構いません。
- 公式の実行ファイルが手近にあることを、型付きの境界を通さない理由にしてはいけません。

## 版の出どころを 1 点に保つ

守るのは 2 つで、どのプロセスも同じ版を見ていることと、活性化が二重に掛からないことです。

- 道具の版を固定する場合は、宣言的に固定でき、プロセスの環境へ 1 度だけ注入できる機構に寄せること。
- いまいる実行が、環境を用意する側か、用意された環境を継いだ側かを決める場合は、次のとおりです。
  - 活性化を所有する境界がすでにあるかで決めます。
  - 呼び出し元が人か別プロセスかの見た目で決めることは禁止です。
- 用意された環境を継いだ側である場合は、次のとおりです。
  - 継いだ環境からそのまま呼ぶこと。
  - 活性化をもう 1 度重ねることは禁止です。
- 環境を用意する側である場合は、そこで 1 度だけ活性化し、以降を継承した環境で走らせること。
  - 用意する側にあたるのは、人が対話的なシェルから始める場合と、フックや自動実行のジョブが準備を担う場合です

## 入口とコマンドの単位

要求は 2 つある。呼び出し側から見て正しい入口が 1 つに決まっていること。落ちたコマンドの名前だけで、壊れている不変条件と直す方向が決まっていること。

- 実行可能物を作る場合は、それを所有するパッケージを 1 つ決めます。
- リポジトリのルートから実行可能物を呼べるようにする場合は、次のとおりです。
  - 所有パッケージへの薄い委譲だけを置きます。
  - 既存の入口へ委譲するためだけの別名や表記違いの入口を足すことは禁止です。
- git のフックのように、置き場所を外の仕組みが決めている起動口がある場合は、次のとおりです。
  - 起動口には、ワークスペースが所有するコマンドの呼び出しだけを置きます。
  - 起動口に検査の中身を実装してはいけません。
- リポジトリのルート直下に、自動化の実装の本体を置くことは禁止です。
  - そこに置かれた実装はワークスペースのグラフの外にあり、依存の宣言も型検査もテストも未使用の検出も掛からない
- 実行可能物を呼び出す場合は、次のとおりです。
  - 正規の入口を使います。
  - 内部のパッケージのバイナリを直接叩くことは禁止です。
- テストからしか到達しない口を作ることは禁止です。
- 手元・フック・自動実行・文書から同じ処理を呼ぶ場合は、同じ呼び方が通る状態を保ちます。
- 個別に呼ぶコマンドを、落ちたときに壊れている不変条件と直す方向が 1 つに決まる単位にします。
- 手元でまとめて走らせる入口が要る場合は、次のとおりです。
  - 個別のコマンドを並べた入口として用意します。
  - 個別のコマンドを 1 つに統合して入口を作ることは禁止です。
- 手元で走らせる検査と CI が同じまとまりを起動することを、片方からの導出か、ずれを機械的に検出して落とす形で保ちます。

## 呼び出し側に選ばせる値を絞る

呼び出し側が本当に選ぶ値だけがオプションとして現れている状態を保つ。目的から一意に決まる値をオプションにすると、呼び出し箇所ごとに同じ値を書き写すことになり、書き写しの食い違いが設定ミスとして表面化する。

- オプションを足そうとしている場合は、次のとおりです。
  - その値が呼び出し側の選択なのか、コマンドの目的か実行時の文脈から決まるのかを先に確かめます。
  - コマンドの目的から一意に決まる値をオプションにしてはいけません。
- 実行時の文脈から取れる値を使う場合は、次のとおりです。
  - その文脈を読む境界で受けます。
  - 同じ値をオプションとしても受けることは禁止です。
- 手元の実行と自動実行で挙動を変えたい場合は、次のとおりです。
  - その差を実行時の文脈から導くこと。
  - 呼び出し側が渡すモードや、自動実行専用の複製したスクリプトで表現してはいけません。
- 呼び出し側が本当に別の戦略を選ぶ場合は、次のとおりです。
  - 目的ごとに分かれたサブコマンドにします。
  - 挙動を切り替えるモードのフラグにしてはいけません。
- 秘密の値を扱うコマンドを書く場合は、次のとおりです。
  - 保管先のキーやパスという参照で受けます。
  - 値そのものを普通のオプションで受けることは禁止です。

## 使い方の記述が受け口と一致している

使い方として表示される記述は、そのコマンドが外へ出す面です。実体とずれても何も落ちないので、ずれは次に使う人が試したときに初めて見つかる。

- 受け付ける引数と、使い方として表示される記述を、同じ変更で揃えること。
- 引数か説明を変えた場合は、表示される使い方と正常終了を実際に実行して確認します。
- オプションを定義する場合は、次のとおりです。
  - そのオプションが値を取るかどうかで、使い方の記述に出すものを決めます。
  - 値を取るものについては、値の形と、指定しなかったときに実際に使われる値を読める形にします。
  - 値を取らないものに、値の受け口があるように読める記述を付けることは禁止です。
- コマンドの説明を書く場合は、次のとおりです。
  - 目的を述べる 1 文に収めること。
  - 手順や環境の説明をそこに詰め込むことは禁止です。
- 説明に書きたい情報が多い場合は、1 文に収まらないものを別の場所へ移します。

## 標準出力と診断を別の系統に出す

既定の標準出力は、人が読むとは限らない面です。読み手が機械なら、結果に混ざったものはすべて雑音になる。

- 既定の標準出力を別のプログラムや AI が消費する場合は、次のとおりです。
  - 結果だけで構成します。
  - 途中経過・デバッグ・進捗を混ぜることは禁止です。
- 診断を出す場合は、結果とは別の系統に出します。
- 子プロセスを包むコマンドが自動実行の中で動く場合は、子の出力を捨てずに、そのまま記録へ流すこと。

## 機械が判定できる性質

置き場所と道具の判断のうち、宣言とコードの構造だけを読んで真偽が決まるものは、機械が判定できる。上の節の順に挙げると次のものがこれにあたる。

- 宣言した公開面に、実際にそれを使っている場所があるか。`knip` がこれを見ている
- 各ワークスペースが共有された tsconfig のプリセットを指しているか、そこから外れた独立の設定になっているか
- 型付きの API が存在する依存に対して、実行ファイルを子プロセスとして起こしているか
- 子プロセスの出力を、検証を通さずそのまま呼び出し側の値として扱っているか
- 値を取らないオプションの宣言に、値の受け口を表す記述が付いているか
- 既存の入口へ委譲するだけの別名の入口が存在するか
- 内部のパッケージのバイナリが、正規の入口を飛ばして直接呼ばれているか
- テストからしか到達しない口が存在するか
- 実行時の文脈から取れる値が、オプションとしても受けられる二重の入口になっているか

判定できることと、その検査がこのリポジトリで動いていることは別です。いま動いているのは各 workspace の lifecycle タスクが依存させた検査だけで、残りは人が見る対象に戻る。宣言の形からは真偽が決まらないものもあり、1 つのパッケージが宣言する面の混ぜ方、個別に呼ぶコマンドの単位、取り決めの置き場所は、いずれも人が見る。使い方の記述と受け口が揃っているかは、コマンドを実行して確かめる。
