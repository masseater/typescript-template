このリポジトリのコードは、外部の利用者からの要求を受けて動くアプリと、外部サービスの状態を書き換える宣言の 2 つです。守りたいのは、検査が緑であることと、検査された対象が実際にそこにあったことがずれない状態で、コードの書き方はその一点に効く。

ずれ方はどれも形が同じで、崩れた瞬間には何も起きありません。定義が二つに割れているとき、確かめずに型だけを強めたとき、失敗を代替値に潰したときにも、行き着く先は同じです。環境変数と外部 API の応答と DB の必須値に暗黙のフォールバックを置かないことは `.claude/skills/reviews/references/no-silent-fallback.md` が決めており、この文書はその周辺で残る判断を持つ。

ここに書かれた判断の一般形は [中核原則](/guidelines/principles) にある。

## 外部 I/O とその境界

この文書で外部 I/O と呼ぶのは、値がこのリポジトリのロジックの外側で決まる経路です。他の文書がこの語を使うときは、この定義を指す。いまの経路の所有者は `libs/config` の環境変数スキーマと `libs/runtime` の HTTP / Worker 契約が持ち、実体は TanStack Start と Elysia が受ける HTTP、Cloudflare D1、Workers AI、メール送信、Workers Observability への OTLP 送出、Alchemy の管理 API、CLI の引数と標準出力です。これに当たらない依存は、プロセス内の決定的な振る舞いとして扱う。

- ロジックが外部 I/O に触れる場合は、次のとおりです。
  - このリポジトリが所有する注入境界を経由します。
  - ロジックの中から外部 I/O を直接呼ぶことは禁止です。
- 注入境界を足す場合は、次のとおりです。
  - それが外部 I/O の位置にあるか、今それを呼んでいるテストではない経路があるかを先に示します。
  - どちらも示せない注入境界を足すことは禁止です。
- 外部 I/O の位置に注入境界を置いた場合は、向こう側を差し替えたときに、こちら側の分岐を全部通せる大きさに保ちます。
  - 判断は、差し替えるものの種類を増やさずに分岐を全部通せるかで見る
- 存在が任意のパスを読む場合は、次のとおりです。
  - 読む前に不在を判定します。
  - 読み取りの失敗をすべて不在として扱うことは禁止です。
- 存在が任意のディレクトリの下に書く場合は、次のとおりです。
  - 書く前にディレクトリを用意します。
  - 書き込みの失敗を存在確認の代わりに使うことは禁止です。
- 環境変数を読む場合は、次のとおりです。
  - `libs/config` の型付きの `env` を経由します。
  - `process.env` を直接参照してはいけません。

## 外から入った値を内側の型にする

静的な型は実行時に消えるので、外から入ってきた値について型が言っていることは、確かめた誰かがいて初めて事実になる。

- 外から来た値を内側の型として扱いたい場合は、次のとおりです。
  - その型へ移す位置を、値がこのリポジトリへ入ってくる境界に置きます。
  - 使う場所ごとに形を確かめることは禁止です。
- 境界で形が合わなかった場合は、内側の型を作らずに失敗として扱います。
  - `libs/config` が Effect Schema で環境変数を検証し、欠けていれば起動を失敗させるのがこの形にあたる
- 一つの判定を二つの概念に使いたくなった場合は、次のとおりです。
  - 概念ごとに別の判定を定義します。
  - いま構造が一致していることを理由に共有してはいけません。
- 判定を通った形を表す静的型を、その判定の定義から導出します。
- フィールドが人にとって何を意味するかを、同じ判定の定義に持たせます。
- 判定が受け入れる形を緩める場合は、次のとおりです。
  - 満たすべき形が文脈ごとに変わるなら、どの文脈かを決める値を先に読み、その文脈の判定を選びます。
  - 省略可能にするフィールドについて、実際に欠ける場面を挙げます。
  - 全文脈のフィールドを省略可能にして一つの判定へ畳むことは禁止です。
  - 欠ける場面を挙げられないまま省略可能にしてはいけません。
- 判定を書く手段を選ぶ場合は、次のとおりです。
  - このリポジトリで一つに保ちます。
  - 選んだ手段の外側で、条件を並べただけの検査を書くことは禁止です。

## 型が言えることと、確かめて初めて言えること

- その場で使える中で最も精密で健全な型を保ちます。
- 不正な状態を型のうえで表現不能にできる場合は、次のとおりです。
  - そこで制約を表現します。
  - 呼び出し側の規律に頼ることは禁止です。
- 関数の引数と戻り値の契約は、関数シグネチャを唯一の出所とします。
- 同じ型が関数の外でも要る場合は、次のとおりです。
  - 関数シグネチャから導出します。
  - 構造だけ同じ型を別に宣言して並行させることは禁止です。
- ある値を、その場の型検査が導けない型として扱わせる場合は、次のとおりです。
  - その値が主張どおりであることを実際に確かめる検査を、同じ境界に置きます。
  - 検査を通った値だけを主張の対象にします。
  - 検査を伴わない主張で、型検査器が出すはずだった拒否を消すことは禁止です。
    - 主張の綴りは問わありません。アサーションも、型述語を名乗る関数も、表明する関数も、中身が値を見ていなければ同じことをしている
- 依存を実行時のモジュールとして取り込む場合は、次のとおりです。
  - そのパッケージの実行時のモジュール形式が消費側と噛み合うことを確かめます。
  - 型解決が通ったことを、実行時に読めることの証拠として扱うことは禁止です。

## 既にある定義の上に書く

同じことを言う場所が二つに割れる経路は、書き足す位置を選ぶ時点にある。既にある定義を探さずに書けば所有者が二つになり、欠陥の原因から離れた位置で塞げば回避策が定義として残る。

- ある振る舞い・ルール・値に既に所有者がいる場合は、次のとおりです。
  - その所有者を再利用するか拡張します。
  - 等価なものをその場に作ることは禁止です。
- 実装しようとしている処理が既製のライブラリにある場合は、次のとおりです。
  - それを使います。
  - 自前実装してはいけません。
  - 既製の関数を包み直すだけのラッパーを作ることは禁止です。
- 欠陥を直す場合は、次のとおりです。
  - その欠陥を所有している境界で原因を直します。
  - 原因の外側に置いた分岐や迂回の経路を、修正として残すことは禁止です。
- 同じ規約を複数のもっともらしい書き方で表現できる状態を見つけた場合は、次のとおりです。
  - 型・境界・自動検査のいずれかを締めて、通る書き方が一つになるまで絞ること。
  - 規約を文書に書いたことで対処を終えることは禁止です。

## 失敗を型で表す

何を送出し、何を戻り値にするかは、呼び出し側がその失敗を予期できるかどうかで決まる。

- 失敗しうる関数を書く場合は、次のとおりです。
  - 予期した失敗と予期しない失敗を、呼び出し側がコードから区別できる形にします。
  - 同じリポジトリの中に失敗の伝わり方を二通り持つことは禁止です。
    - 予期しない失敗はどのみち送出で上へ伝わるので、予期した失敗も送出に寄せれば経路は一本で済む
- 予期した失敗や、外へ出す報告を定義する場合は、次のとおりです。
  - その同一性を、安定した識別子が持つ形にします。
    - 鍵になれるのは、報告の識別子や、実行環境が失敗に付ける `code` のように、言い回しでは変わらないものだけです
  - 同一性をメッセージ本文の一致で判定してはいけません。
- 下位の層や依存パッケージから来た失敗を包む場合は、次のとおりです。
  - 元の失敗を `cause` として保持します。
  - 文言だけを取り出して元の失敗を捨てることは禁止です。
    - 文脈を足すのはよいが、足すのであって置き換えるのではない

## 失敗を消さない

失敗が消える書き方は三つある。受け取らずに捨てる、書き出してから続ける、代替値に置き換える。どれも結果は同じで、失敗はその失敗自身の不在を表す値に化ける。

- 失敗を捕まえた場合は、次のとおりです。
  - 捕まえたものに名前を付けて受け取ること。
  - 受け取らずに捨てることは禁止です。
- 捕まえた失敗を出力先へ書き出す場合は、次のとおりです。
  - 書き出したうえで、止めるか、失敗したと分かる値を戻します。
  - 書き出してからそのまま続きへ進むことは禁止です。
- 失敗を別の綴りへ移したり、包む関数を挟んだりして、握り潰しの検出から外すことは禁止です。

三つ目の代替値は、失敗を一見成功した実行に変える操作です。許す線は握り潰しと同じところに引く。検査される対象の集合と、報告される箇所の集合が動かないことです。

- 失敗したときに代替値で続行したい場合は、次のとおりです。
  - その置換を許す明示的な仕様があることを確かめます。
  - その置換が、検査される対象の集合と報告される箇所の集合のどちらも変えないことを示します。
  - 置換後の値を受け取る側が、その値で成立することを確かめます。
  - 置換が起きたことを、実行の外から成功と区別できる形で残します。
  - 四つのうち示せていないものがあるまま続行してはいけません。
- 環境変数・外部 API の応答・DB の必須値・認証情報・課金や権限の判定に代替値を置くことは禁止です。

## 名前が伝えること

引数の名前と型は、呼び出す前に読まれる唯一の情報です。

- 受け付ける形を呼び出し側へ伝える位置がある場合は、次のとおりです。
  - その位置に、受け付ける形が判別できる情報を置きます。
  - 名前や役割を言い換えただけの記述を置くことは禁止です。
- 受け付ける値が有限の語彙である場合は、次のとおりです。
  - 型でその語彙を表します。
  - 説明の散文だけで語彙を伝えることは禁止です。
- 綴りがこのリポジトリの外で決められている値を扱う場合は、次のとおりです。
  - 決めた側を名前に含めます。
    - 外部サービスが定める識別子も、環境変数の名前も、綴りを決めた側が違えば別の語彙です
  - 決められた綴りのまま参照します。
  - 自分の側で言い換えた語を発明してはいけません。
  - 決めた側を特定できない場合は、特定できるまで名前を付けません。

## 取り込まれる面に足すもの

取り込む側のワークスペースから見れば公開した面は契約です。`tools/ai-native`・`tools/dont-review-it`・`tools/lint-rule-authoring`・`tools/stop-ai-slop` は `publishConfig.access: public` で npm へ出せる形を保っており、それ以外もワークスペース間の import 面は契約と同じ重さで扱います。畳むには取り込み側の変更が要るので、何を載せるかの判断は内部の宣言より一段厳しい。問われるのは二つで、既に公開しているものから導けないことと、いま実際に呼んでいる経路があることです。

- 公開する面に何かを足す場合は、次のとおりです。
  - 同じ面が既に公開しているものと、取り込み側が既に依存している契約だけでは導出できないことを確かめます。
  - 導出できるものを足すことは禁止です。
- パッケージの公開エクスポートを変える場合は、エントリと消費側を同じ変更で更新します。
- 呼び出し側から使える口をインターフェースに足す場合は、次のとおりです。
  - 今それを呼んでいる、テストではない経路を示します。
  - 将来使う見込みを利用者の提示として扱うことは禁止です。
- テストからしか import されていない export がある場合は、次のとおりです。
  - 消します。
  - 消せない場合は、その振る舞いを、利用者が実際に通る経路越しに検証する形へ書き換えます。

## 実行が外へ出す面に載せるもの

実行が外へ出すのは、HTTP の応答と、CLI が標準出力に出す形です。どちらも読み手が機械であることがあり、そこに載せた値の形と、その値をどう見せるかを誰が決めるかが、別々に問われる。

- 特定の利用者に向けてまとめた面を作る場合は、次のとおりです。
  - 載せる事実とその粒度を選んでも構いません。
  - 利用者の側の見せ方まで決めることは禁止です。
- 出力の見せ方を契約に載せることは禁止です。
  - 契約になれるのは、報告の識別子や状態コードのように、言い回しを変えても同じものを指す綴りだけです
- 失敗や結果を外向きの表現へ移す場合は、次のとおりです。
  - 終了コード・状態コード・報告の書式・利用者に見せる文言への変換を、ちょうど一箇所の境界で行います。
  - 失敗そのものに外向きの表現を持たせることは禁止です。
- ある値の解決に、利用者から到達できない状態が要る場合は、解決した後の値を載せます。
- 解決した後の値と、その材料の両方が利用者に要る場合は、両方載せても構いません。

## コードの傍に残したい記述

コードにコメントを書かないこと、変更の経緯と理由をコミットログに残すことは `AGENTS.md` が決めている。ここで決めるのは、それでも書き残したい内容が出たときの行き先です。

- 書き残したい内容がある場合は、それが現在の姿と一度きりの決定のどちらを述べているかを先に判定します。
  - 現在の姿はコードが変われば一緒に変わり、一度きりの決定は決めた時点に固定されて動かない
- 内容が現在の姿を述べている場合は、次のとおりです。
  - 識別子・型・テストのいずれかで表現します。
  - 三つのどれでも表現できない不変条件である場合は、それを所有する規範文書へ置きます。
- 内容が判断の根拠である場合は、次のとおりです。
  - 根拠を、それが説明している判断と同じ変更の単位に入れます。
  - 複数の判断の根拠を、対象から離れた一箇所へまとめることは禁止です。
- 根拠に書きたいのが、その作業をしている最中に分かったことである場合は、次のとおりです。
  - 分かった制約の側を書きます。
  - どうやって気付いたかを根拠に置くことは禁止です。
- なぜそうしているか分からない記述に出会った場合は、次のとおりです。
  - `git log` と `git blame` でその行のコミットログを読みます。
  - 意図を推測したまま変更してはいけません。

## 定数と前処理を置く位置

- 定数・設定値・前処理を関数の最上部にまとめようとしている場合は、次のとおりです。
  - 使用箇所の直前に置けないかを先に検討します。
  - そこでしか使わない値を、使用箇所から離れた位置に宣言してはいけません。

## 生成器が吐くコード

ここで決めるのは、生成器が何を担い、何を担わないかです。

- 生成器がコミット対象のソースを吐く場合は、次のとおりです。
  - 生成器には意味のある出力だけを担わせます。
  - 体裁の正規化をリポジトリのフォーマッタに任せます。
- 再生成した出力とコミット済みの出力を比べる場合は、比較の前に両方を同じ整形の契約で正規化します。
- 生成物が、このリポジトリの別の場所にある宣言をそのまま書き出したものである場合は、生成物の側に、コードの傍に残す記述の規則を課さないても構いません。

## 判断が割れたとき

- 拡張点を先に用意したい要求と、今の呼び出し元を示す規則が衝突する場合は、後者を採ります。
- 失敗を表に出すことと、代替値で続けることが衝突する場合は、表に出す側を採ります。
- 単一の定義とテストの読みやすさが衝突する場合は、次のとおりです。
  - テストの側の基準に従います。
  - 独立した仕様どうしに単一の定義を当てることは禁止です。
- 記録の完全性と機微な値を落とすことが衝突する場合は、[秘密と権限](/guidelines/secrets-and-permissions) の順位に従います。
- 特定の利用者向けにまとめた面と、見せ方を契約に載せない規則が衝突する場合は、面が事実を選び、利用者がその表し方を選ぶ形に切り分けること。
- 記録の経路を一本に保つことと、記録を増やすことが衝突する場合は、経路を一本に保つ側を採ります。

どちらとも決められないときは、後から戻せる側へ倒す。足さなかったものは後から足せるが、公開した面と付けてしまった名前は畳むのに取り込み側の変更が要る。

- 型の精度を落とすか境界で検証を足すかを判断できない場合は、検証を足す側へ倒すこと。
- その値の綴りを決めた側を特定できているかどうかを判断できない場合は、名前を付けずに保留します。
- その注入境界が正当かどうかを判断できない場合は、足さない側へ倒すこと。
- そのフィールドが欠けるケースを挙げられるかどうかを判断できない場合は、必須の側へ倒すこと。
- 足そうとしている値が既存の公開物から導出できるかどうかを判断できない場合は、載せない側へ倒すこと。

## 機械が判定できる形

この領域で機械が判定できるのは、書き方の違いが構文の違いとして現れる性質です。使われていない export と依存、型が通らない参照が、いずれもその形をしている。いま判定しているのは Oxfmt と Oxlint と `tsc` と `knip` です。

落とせるのは形であって判断ではありません。どの型がその場で最も精密かも、名前がその値の綴りを決めた側を含んでいるかも、代替値を置いてよい明示的な仕様があるかも、構文を見る検査では決まらありません。
