---
title: 秘密と権限
description: 秘密の値が残る場所と、実行に与える権限の幅についての判断基準
---

この文書が守るのは 2 つある。秘密の値が、置いた場所の外に残らないこと。実行に許すことの幅が、宣言の側から読めること。前者が要るのは、値がリポジトリの内容と履歴に残り、実行が出す内容にも一緒に入るからです。後者が要るのは、資格情報が外へ出たときの被害の上限を決めるのが、起きたことそのものではなく平時に敷いてある設定だからです。

どちらも、起きた後に打てる手がありません。平文で一度出た値について、複写が何部できたかを数える手段はありません。間に合う操作は、出す前にしかありません。

このリポジトリで秘密が動く場所は 4 つある。開発者の手元、Cloudflare Workers の実行環境、Cloudflare の Secrets Store、Alchemy の state store です。手元の開発用の値は `apps/<app>/.dev.vars` に置き、デプロイの入力はリポジトリの外の owner だけが読めるファイルに置く。本番の実行環境が読む値は Worker の secret binding が持ち、Alchemy が state を暗号化する鍵とその認証トークンは Secrets Store にある。4 つ目は、宣言に渡した秘密と、宣言が発行した資格情報の実値です。Alchemy はそれらを state に載せ、state store の Durable Object が暗号化して保管する。宣言の入力である `TEMPLATE_AUTH_SECRET` と、`infra/cloudflare` が発行するアカウントトークンの値がこれにあたる。ここで見るのは、その実行に何を持たせるかだけです。

## 秘密の値を平文でこのリポジトリに置かない

秘密として扱うのは、それを持っていること自体が「誰かとして振る舞ってよい」根拠になる値です。鍵でもトークンでも署名の材料でも、受け取る側が本人性の証拠として使うなら同じに扱う。接続先のアカウントを名指しする識別子も分けありません。その識別子だけで通ってしまうかどうかを決めるのは繋ぎ先の実装で、こちら側には安全な方へ分類する材料がありません。

- 資格情報にあたる値は、実行を起こした側から実行時に渡ってくる形にします。
- 秘密の値を、平文のままこのリポジトリが追跡するファイルへ書き込むことは禁止です。
  - ファイルの種類では分けありません。一度コミットに入れば、いま見えている内容から消しても履歴から読める
- 開発用の値が手元に要る場合は、次のとおりです。
  - 追跡しない `apps/<app>/.dev.vars` に生成し、その生成を手順ではなく実行できる形で持ちます。
  - 開発用の値を、暗号化したものも含めてリポジトリが追跡するファイルに置くことは禁止です。
- どこから資格情報を取るかを設定として書き留めたい場合は、次のとおりです。
  - 書き留める対象を、保管先の指し方だけに留めること。
  - 値の実体をそこへ置くことは禁止です。
- 資格情報の形をした値を、文書やテストの中に書く必要がある場合は、そのままでは何の相手にも通らないと読み取れる値を選びます。

平文の環境変数ファイルがコミットに入ることは `.vite-hooks/pre-commit` が見ている。この判定が何も言っていない状態は、そこに置かれた値の性質については何も言っていありません。

## 見つかった値を無効にして取り除く

秘密の値を網羅的に探す仕組みは、このリポジトリにまだありません。`.vite-hooks/pre-commit` が見ているのは、平文の環境変数ファイルと非公開ディレクトリの混入、決まった形をした資格情報、デプロイ用の秘匿値と同じ文字列だけです。誤って挙がった値の扱いを決めた項目が機能し始めるのは、探す仕組みを入れた時点です。

- 本物の資格情報がこのリポジトリに平文で入っていたと分かった場合は、その値を使えなくしたうえで、いまの内容からも公開済みの履歴からも取り除くこと。
  - 片方だけで済ませると、使える鍵か、読める記述のどちらかが残る
- 広い範囲を除外に指定して、探す仕組みを止めることは禁止です。
  - 指定した範囲は将来書かれる値にも機能し続けるので、広く取るほど探す仕組みが見ない領域が残る
- 探す仕組みが挙げた値が秘密でない場合は、その根拠を同じ変更に添えたうえで、挙がったその 1 件だけを対象から外すても構いません。

## 出力に秘密を通さない

このリポジトリの出力は、標準出力と標準エラー、HTTP の応答、Workers Observability へ送るイベントとログとトレース、`alchemy plan` が端末へ書く差分です。どれも人と機械が読む場所へ出るため、宣言に秘密の値が現れる形を作らありません。

- 秘密の値そのものを出力に載せることは禁止です。
- 個人を名指しできる値を出力へ流すことは禁止です。
  - 診断を厚くしたいという要求は、この一線の外側で満たす
- 値の存在や形だけを出力に残したい場合は、元へ復元できない形にしたものを出します。
- Alchemy の宣言で秘密の値を扱う場合は、次のとおりです。
  - secret として宣言し、`plan` の差分に平文が現れない形にします。
  - 値そのものを宣言の入力として書くことは禁止です。
- 出力の手前で機微な値を取り除く層を持ち込む場合は、次のとおりです。
  - 何を取り除くかの定義を 1 つに保ち、どの出力先へ届く前にも必ずそこを経由させること。
  - 機微な内容を運ぶキーを増やすときは、その同じ変更で定義の側にも載せること。
  - 出力先が増えるたびに、そこへ取り除く処理を書き足すことは禁止です。
- 中身をキーで分けられない塊を出力へ流したい場合は、塊そのものではなく、量や種別のような外形だけを出します。

## 読み出せる主体を、読んでよい主体に一致させる

保管先を分けても、その保管先を読める主体が広ければ守れていありません。読める主体の集合が、読んでよい主体の集合と一致していることまでを確かめる。

- 秘密の値の置き場所を選ぶ場合は、次のとおりです。
  - その置き場所から値を読み出せる主体をすべて数え上げること。
  - 置き場所を分けたことだけを根拠に、読める範囲が狭まったとみなすことは禁止です。
    - Worker の `secret_text` binding は API から値を返さありません。`plain_text` は Workers Scripts を読める主体なら誰でも読める
- 継承によって広い権限を持つ主体が、読んでよい主体に含まれていない場合は、次のとおりです。
  - 明示的な拒否でその主体を止めます。
  - 拒否の例外に入れるのを、読んでよい主体だけに限ること。
  - 拒否が実際に機能していることを、例外に入っている主体の資格情報で確かめます。
    - 確かめるまでは、例外の側も機能しているかどうかが分かっていない状態です
- 秘密の値の読み取りを記録する必要がある場合は、その保管先の読み取りの監査ログを有効にします。
- 値を読み出せない主体だけがその値を知っている場合は、次のとおりです。
  - その値を宣言の管理下に入れないこと。
  - 値を入れる主体と手順を、その領域を所有する文書に書きます。
- 宣言が、作成時にしか読み出せない資格情報を発行する場合は、次のとおりです。
  - その実値を保持している state store を、その資格情報そのものと同じ扱いで守ること。
  - state store を捨てる操作を、作り直せるものへの操作として扱うことは禁止です。
    - `alchemy provider cloudflare teardown` が state を消すと、発行済みトークンの実値はどこからも読み出せありません。復旧は、トークンを作り直して参照する側を差し替えることだけです

## 実行が持つ権限を宣言に限る

ここで言う実行は、CI で実行される確認と適用、Cloudflare Workers が動かすアプリ、手元で起動するコマンドです。どれも、何ができるかを宣言の側で決め、実行の側で足せないようにする。

- 実行の単位ごとに、その実行が要る権限だけを宣言します。
- 実行基盤が初めから渡してくる権限をそのまま受け取ることは禁止です。
  - 何も宣言していない状態が意味するのは、権限を確かめた結果ではなく、確かめていないことです
- 確認が通らないことを理由に、宣言する権限を広げることは禁止です。
- 外部サービスへ機械が接続する必要がある場合は、次のとおりです。
  - API トークンを持たずに済む方法を先に探すこと。
  - 探す順序を、OIDC による federation、サービスが提供する短命の資格情報、鍵なしの連携機構の順にします。
  - 判断を、記憶ではなく公式のドキュメントと実際の API の応答で確かめます。
  - どの方法も提供されていないことを確認した場合は、次のとおりです。
    - API トークンを使っても構いません。
    - そのトークンを、リポジトリの外の owner だけが読める場所に置き、その場所の指し方だけを設定として書きます。
  - 長期のトークンを最初の選択肢にしてはいけません。
  - トークンをリポジトリ・ワークフローの定義・環境変数ファイルに置くことは禁止です。
- 承認や隔離を迂回する仕組み、あるいは通常の手順では持たない能力を実行へ与える仕組みを用意する場合は、次のとおりです。
  - 既定を無効とし、起動の時点で確かめられる明示の指定があるときだけ有効にします。
  - その能力を常時有効な形で埋め込むことは禁止です。

## 変更を起こす口は、その地点で判定する

- 変更を起こす口を新しく開く、あるいは既にある口の受け口を広げる場合は、次のとおりです。
  - 変更が実際に起きる地点で、どの対象へ何をしようとしているのかを確かめます。
  - 判定は呼び出す側で済んでいるものとして省くことは禁止です。
    - 呼び出す側に置いた判定が覆うのは、それを書いた時点で存在していた手順だけで、後から加わる手順がそこを通る保証はありません
- 誰として要求したのかを確かめる仕組みを持ち込む場合は、そこを通過した事実だけで変更を認めることは禁止です。
- 判定が正しいことを機械で確かめられない手順が残る場合は、そこを人が読んで確かめる側へ回すこと。
- 保護された環境を、資格情報を持たない主体に開ける必要がある場合は、次のとおりです。
  - 保護そのものは残し、迂回する手順を主体ごとに分けて発行します。
  - 保護を外して代わりにしてはいけません。

## 確認を通っていないコードの手が届く範囲

CI が取り出すのはリビジョン 1 つで、それはまだこちらの確認を通っていないコードです。動き始めたときに、その実行の手元にあるものを読める。

- 取り出したリビジョンが動く場所に資格情報を置く必要がある場合は、次のとおりです。
  - 取り出す操作が、そのとき使った資格情報を作業ツリーに残さない設定であることを確かめます。
  - 置くものを、用途を絞ったうえで、選べる期限のうち最も短いものに限ること。
  - その資格情報を作る処理を、取り出したコードが動く場所の外で実行すること。
  - 期限の長い鍵を、取り出したコードの手が届く場所に残すことは禁止です。
- 差分を取るために、もう 1 つのリビジョンを並べて取り出す場合は、並べたそれぞれを、こちらの確認を通っていないコードとして扱います。
- 実行の途中で起動する処理に認証が要る場合は、次のとおりです。
  - どの資格情報を使うかを、その処理の呼び出しに書いて渡すこと。
  - 実行の周囲に残っているログイン済みの状態をあてにしてはいけません。

## 資格情報は目的ごとに分ける

- 外にあるサービスへ繋ぐ自動化を足す場合は、次のとおりです。
  - その処理が触る対象と、行う操作の範囲に収まる資格情報を使います。
  - 期限は、選べる選択肢のうち最も短いものにします。
- 相手が通してしまうことを理由に、発行した目的の外へ資格情報を回すことは禁止です。
  - Alchemy が管理 API を呼ぶためのキーと、アプリが機能のために使うキーは、同じサービスのものでも別に発行する
- 1 つの資格情報を複数の実行単位で共有しようとしている場合は、次のとおりです。
  - 失効させたときに止まる範囲を数え上げること。
  - 失効の影響が数え上げられないまま共有してはいけません。
- 人ではなく自動化がこのリポジトリを書き換える場合は、次のとおりです。
  - その自動化のために発行した資格情報を使います。
  - 個人に紐づく資格情報を、自動化の定常的な手段として使うことは禁止です。
    - 発行者が組織を離れると失効する種類のトークンは、この条件を満たさない
