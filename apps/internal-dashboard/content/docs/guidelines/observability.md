title: 観測性
description: 応答の状態コードと監視へ送る対象、記録の流れと深刻さ、送った記録の閉じ方、アラートの条件と宛先を決める判断基準
---

この文書が守るのは、Workers Observability と監視 Worker が運ぶ未解決の記録が、いま直すべきものの一覧と一致している状態です。一致していれば、届いている記録が空でないことがそのまま着手の理由になる。一致が崩れると、記録を開いた者はまず「これは自分たちが直すものか」を選り分けることになり、選り分けの手間が毎回かかる分だけ、記録そのものを見なくなる。

崩れ方は 2 つある。直せないものを送っていることと、直したものを閉じていないことです。前者は送る時点の判断で、後者は送った後の判断で、どちらも記録の側からは同じ「未解決」に見える。

このリポジトリで記録が生まれるのは、TanStack Start と Elysia が受ける HTTP、Cloudflare Workers、Alchemy の適用、開発サーバーです。出口は `@repo/observability` が OpenTelemetry (OTLP) で Workers Observability へ送る手順で、アラートは `infra/error-monitor`・`infra/budget-monitor`・`infra/health-monitor` と `libs/monitor` が持つ。ここにあるのは、記録と監視の形を決めるときに当てる基準です。

秘密の値と個人を特定できる値を出力から落とす判断は、この文書の基準より先に当てる。

## 監視へ送る対象を選ぶ

送ってよいのは、こちらの変更で挙動が変わるものだけです。利用者の入力が不正であることも、対応していない要求を仕様どおり拒否したことも、こちらが直せる不具合ではありません。

- 監視へ送る対象を選ぶ場合は、次のとおりです。
  - 直せる不具合を指しているイベントだけを送ります。
  - アプリが仕様どおりに応答した結果を不具合として計上してはいけません。
    - 入力の不備、存在しない URL への要求、対応していないプロトコルの版での要求、認証に失敗した要求がこれにあたる
- 仕様どおりの拒否や利用者の入力の誤りが監視に届いている場合は、次のとおりです。
  - 送らないように直すこと。
  - 監視の側で表示から外して済ませることは禁止です。
    - 送られた時点で quota を消費しており、表示から外しても消費は戻らない
- 送るかどうかの判定が、失敗の値が持つ状態コードに依っている場合は、次のとおりです。
  - 状態コードを持たない失敗が判定をすり抜けることを前提に置きます。
  - すり抜ける失敗の種別ごとに、判定へ乗せる方法を決めます。
    - 認証の失敗を表す値や、DB のドライバが投げる値が状態コードを持たないことがある
- 依存している外部のサービスが失敗した場合は、次のとおりです。
  - こちらの応答をどうするかを先に決め、その決定に従って送るかどうかを決めます。
  - 外部の失敗であることを理由に、送る対象から自動的に外すことは禁止です。
    - 外部が落ちたときにこちらが利用者へ何を返すかは、こちらが決められる

## 応答の状態コードを決める

状態コードの意味は [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) が定め、各コードの読みやすい説明は [MDN の一覧](https://developer.mozilla.org/ja/docs/Web/HTTP/Reference/Status) にある。どの場面でどれを選ぶかは、Google が [`google.rpc.Code`](https://github.com/googleapis/googleapis/blob/master/google/rpc/code.proto) で定める分類と、その HTTP への対応に従う。RFC はコードの意味を定めるが、実際に迷うのは「この失敗はどの意味に当たるか」であり、そこを場面ごとに言い切っているのが Google の分類です。以下の項目に添えた `INVALID_ARGUMENT` などは、その分類の名前を根拠として示したものであって、応答に載せる値ではありません。

自前の意味付けはしありません。ここに書くのは、規範だけでは選択が割れる場面と、選んだ結果が監視に何を載せるかです。このリポジトリは失敗の値が持つ状態コードを見て監視へ送るかどうかを決めているため、選び方がそのまま未解決の一覧の中身を決める。

応答の本体は [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html) の Problem Details に従い、`application/problem+json` で返す。

- 要求された資源が存在しない場合は、次のとおりです。
  - 404 を返す（RFC 9110 § 15.5.5）こと。
  - 500 を返すことは禁止です。
    - 見つからなかったことを表す値をそのまま描画へ渡すと、描画の途中で参照に失敗して 500 になる。資源が存在しないことは仕様の内側にあり、直せる不具合ではない
- 認証の資格が提示されていない、または提示された資格が無効である場合は、401 を返す（RFC 9110 § 15.5.2）こと。
- 利用者にその資源への権限が無い場合は、次のとおりです。
  - 資源が存在するかどうかを調べる前に権限を判定し、403 を返す（RFC 9110 § 15.5.4、[Google AIP-193](https://google.aip.dev/193)）こと。
  - 資源が存在すること自体を伏せなければならないなら 404 を返すても構いません。
    - RFC 9110 § 15.5.5 は、資源の存在を開示したくない場合にも 404 を使うと定めている。既定は 403 とし、伏せる必要を説明できるときだけ 404 にする。判定の順序を先に固定しておかないと、権限が無い利用者への応答が資源の有無で変わり、そこから存在を読み取れてしまう
- 要求の引数が、システムの状態に関わらず不正である場合は、400 を返す（`INVALID_ARGUMENT`）こと。
  - 不正な JSON、必須の項目の欠落、形式の制約の違反、符号化の誤りがこれにあたる
- 引数そのものは正しいが、システムが要求を実行できる状態にない場合は、400 を返す（`FAILED_PRECONDITION`）こと。
  - 先に済ませておくべき手続きが済んでいない場合がこれにあたる。同じ引数でも、状態が変われば通る
- 操作が有効な範囲を越えている場合は、400 を返す（`OUT_OF_RANGE`）こと。
- 作ろうとした対象が既に存在する、または並行する操作と競合して中断した場合は、409 を返す（`ALREADY_EXISTS` と `ABORTED`）こと。
- 利用者ごとの割り当てや資源を使い切った場合は、429 を返す（`RESOURCE_EXHAUSTED`）こと。
- その操作を実装していない、またはこのサービスで有効にしていない場合は、501 を返す（`UNIMPLEMENTED`）こと。
- 依存する外部のサービスが使えない場合は、次のとおりです。
  - 503 を返す（`UNAVAILABLE`）こと。
  - 復帰の見込みが分かるなら `Retry-After` を付けること。
  - `UNAVAILABLE` は一時的な状態を指し、間隔を空けた再試行で回復しうるものを表す
- 依存する外部のサービスが時間内に応答しなかった場合は、504 を返す（`DEADLINE_EXCEEDED`）こと。
- 502 を返すことは禁止です。
  - RFC 9110 § 15.6.3 の 502 は、中継として振る舞うサーバーが上流から無効な応答を受け取ったことを表す。外部の API を呼んで失敗したアプリは中継ではなく、依存が使えないサービスです。この場面は 503 が正確に表す。Google の分類にも 502 に対応するコードはありません
- どの 5xx も当てはまらない場合は、500 を返す（`INTERNAL` と `UNKNOWN`）こと。
  - 500 は他に適切な 5xx が無いときの受け皿であって、既定の選択肢ではない
- 使いたい状態コードが `@repo/observability` の `httpStatus`（失敗側は `@repo/runtime` の `FailureStatus`）に無い場合は、型に足してから使います。
- 依存する外部のサービスが失敗した場合は、次のとおりです。
  - その失敗があっても応答の目的を達せられるかを先に決めます。
  - 達せられない場合は、上の区別に従って 503 か 504 を返し、監視へ送ること。
  - 欠けた部分を除けば達せられる場合は、次のとおりです。
    - 成功として返します。
    - 欠けたことを `WARNING` で記録します。
    - 5xx を返して応答ごと落とすことは禁止です。
- 状態コードを決める場合は、決める箇所を境界の一つに保ちます。
- 同じ失敗に、出どころごとに違う状態コードを割り当てることは禁止です。

## 送った記録を閉じる

監視へ載せた記録の扱いと、コードの変更は同じ向きに動く。通知や判定状態だけを動かして変更を届けない操作は、届いていないのに届いたことにする操作です。

- 監視の判定状態を「直った」側へ進める場合は、次のとおりです。
  - その記録を生んだ変更が実稼働に届いていることを確かめてから行うこと。
  - 修正を届けたか、送信を止める変更を届けたかのどちらかを済ませています。
  - 通知を減らすためだけに判定状態を動かすことは禁止です。
- 送る対象から外した事象の記録を閉じる場合は、送らない仕組みを届けたうえで閉じます。
  - 送り続けたまま通知だけを止めてはいけません。送らない仕組みが止まって同じ事象が再び届いたとき、閉じ方が正しければ再発として浮かび上がる
- 直さないと決めた場合は、送らないように直したうえで閉じます。
- 未解決のまま残っている記録がある場合は、直すと決めたものとして扱います。
  - 直すと決めていないものがここに残っている状態は、記録が着手の理由として読めなくなっている状態です

## アラートの条件と宛先を決める

記録が届いても、誰も見ていない場所に届くなら届いていないのと変わらありません。

- アラートを足すか変える場合は、次のとおりです。
  - Alchemy の宣言と `infra/error-monitor`・`infra/budget-monitor`・`infra/health-monitor`・`libs/monitor` に書きます。
  - Cloudflare の管理画面だけで作ることは禁止です。
    - 画面で作ったものは宣言に現れず、`alchemy plan` が実体とのずれを見つけられなくなる
- 監視 Worker やアラートの届け先を新しく足した場合は、宛先と判定条件を宣言した状態で有効にすること。
  - 宛先が無いアラートは届いていないのと同じ
- アラートの宛先を決める場合は、次のとおりです。
  - その届け先の担当者が普段見ている場所にします。
  - 宛先を決めないまま有効なアラートを残すことは禁止です。
- アラートの対象を絞る場合は、次のとおりです。
  - production の環境に限ること。
  - production 以外の環境で起きた事象を通知に載せることは禁止です。
- 同じ事象が繰り返し発火しうる場合は、再通知の間隔を決めます。
- 動いているかを監視する場合は、落ちたことが通知へ届くところまで用意します。
  - 監視を置いただけでは、落ちたことは画面を見に行った者にしか分からない

## 記録の流れを一本に保つ

- 記録を出す発生源を足す場合は、次のとおりです。
  - 発生源の種別ごとに、流す先を一つ決めます。
  - 流す先を決めないまま出力先を増やすことは禁止です。
- 一つの発生源の記録を、複数の先へ重複して流すことは禁止です。
- 一つの発生源の記録が既に複数の先へ流れている場合は、流れを一本に寄せること。
- 記録を中継するためだけに存在する中間の処理を残すことは禁止です。
- 本番の記録を出す場合は、次のとおりです。
  - そのランタイム向けに用意された構造化の境界を通します。
  - 呼び出し側で logger の設定を作り直すか、サービス名や環境や送り先を上書きしてはいけません。
- 本番で動くコードの記録の出口に、素の `console` の呼び出しを置くことは禁止です。

## 記録の深刻さを選ぶ

深刻さは、復旧できるか、影響がどこまで及ぶか、業務として起こりうると分かっていたかで決める。失敗の型の名前だけでは決まらありません。

- 必要な資源、依存、設定値、必須の入力が欠けている場合は、`WARNING` より下で記録してはいけません。
- 捕まえた失敗が外部の依存の失敗である場合は、`ERROR` で記録し、どの依存かを構造化した欄に残します。
- 捕まえた失敗が入力の不正か業務規則の違反である場合は、`WARNING` で記録します。
- 捕まえた失敗が、対象が存在しないことか権限が無いことである場合は、`INFO` で記録します。
- 捕まえた失敗が状態の衝突である場合は、`WARNING` で記録します。
- 捕まえた失敗を分類できない場合は、上位の処理へ渡し、そこで `ERROR` として記録させること。
- 失敗した後に代替値で続行した場合は、置換が起きたことを `WARNING` 以上で記録します。

## 記録に何を残すか

原因まで辿れない失敗は、報告としては起きなかったのとほとんど変わらありません。

- 捕まえた失敗を記録する場合は、次のとおりです。
  - 失敗そのものと、`cause` で繋がった連なりを残します。
  - 文言だけを写して元を落とすことは禁止です。
- 記録する事象が識別子、処理の段階、引数を持つ場合は、秘密の値を落としたうえで、構造化した欄に載せること。
- 記録の文言を書く場合は、次のとおりです。
  - 文言を固定します。
  - 変わる値を構造化した欄に置きます。

## 出力先に収まらない内容

- 出してよいと判断した内容が、記録の出力先の容量に収まらない場合は、次のとおりです。
  - 出力先を分けるか、構造化した欄へ移します。
  - 収まる分量まで削って残りを捨てることは禁止です。
    - どの削り方を選んでも、削ったこと自体は残った記録に現れない
- どうしても内容を記録の本文から落とさざるを得ない場合は、次のとおりです。
  - 落とした事実を記録に残します。
  - 在り処として指すのを、その記録の読み手に開示が許されている場所だけにします。
- 秘密の値を落とした結果として内容が減った場合は、次のとおりです。
  - 落とした後の形を、出してよい内容の全体として扱います。
  - 完全さを満たすために、落とす前の複製をどこかに残すことは禁止です。
