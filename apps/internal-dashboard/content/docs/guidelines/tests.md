---

このリポジトリのテストは、実装が要求を満たしていることの唯一の証拠です。実装がそこに存在することは、それが要求どおりに動くことを意味しない（[強制の機構](/guidelines/enforcement)）ので、緑が何の証拠なのかが崩れた時点で、テストは何も保証しなくなる。

崩れ方は 3 つある。主張が契約ではなく実装に向いていること。緑が要求を満たしている証拠として読めなくなること。赤の原因が対象の振る舞いの外にあること。どれが起きても、テストの件数は減らず、検査も通り、見た目は緑のままです。

実行するのは root の `test` タスク（`vp test`）で、`.github/workflows/check.yml` が `premerge` の一部として起動する。PR に対する `prepr` は、その PR の差分を import するテストだけを `test:changed` タスク（`vp test --changed`）で走らせる。この文書が持つのは、テストを書くときに何を書くかの判断です。

## 機械が見ているのは形だけ

静的検査が判定できるのは、テスト本文に書かれた構文の形です。このリポジトリにはテスト本文を見る専用の lint ルールが無く、`tsc` が型として見る範囲だけが機械の判定にあたる。

形にならないものは判定できありません。期待値がどこから来たのか、ダブルの返す形が本物と合っているのか、そのアサーションが要求を拘束しているのかは、テスト本文を読んだ側にしか分からありません。以下はその側の判断基準です。

ここにはテスト特有の抜け道だけを書く。

- 期待値や対象を別名へ束縛して報告を消すことは禁止です。
- 弱いアサーションを複数に割り、部分一致のまま残して報告を消すことは禁止です。
- 未カバーの行やスナップショットの大きさへの指摘を、抑制ディレクティブと計測対象からの除外で黙らせることは禁止です。

## 何を主張するテストなのか

- assert する対象を選ぶ場合は、次のとおりです。
  - 外から観測できる結果・状態の変化・副作用・公開している契約に限ること。
  - 内部の呼び出し順序や、振る舞いを変えずに変わりうる内部のデータ形状を固定してはいけません。
- 期待値を決める場合は、次のとおりです。
  - 仕様や規則から導くこと。
  - 実装がいま返している値を書き写すことは禁止です。
- 対象を作った式そのものを期待値に置くことは禁止です。
  - 対象を期待値のオブジェクトへ展開して数個だけ上書きする形も同じで、上書きしなかった側は自分自身との比較になる
- 出力の一部だけを取り出す、または並べ替えや正規化を挟んでから比べることは禁止です。
- 振る舞いを変えない書き換えでテストが壊れた場合は、次のとおりです。
  - 観測できる契約に対して書き直すこと。
  - 期待値を実装の現状へ合わせて調整してはいけません。

## 主張の強さ

- 対象が構造を持つ値を返す場合は、欠けたフィールドと余計なフィールドの両方が出る厳密さで、対象の全体を比べること。
- 部分一致・存在確認・真偽・実行時の型だけを見るマッチャで済ませることは禁止です。
- 厳密に比べたい値が実行のたびに変わる場合は、次のとおりです。
  - 値を制御できないかを先に見ます。
    - 緩めてよいのは、制御しきれずに残った部分だけです
  - 値が外から与えられる形になっている場合は、次のとおりです。
    - 値の側を制御します。
    - アサーションを緩めることは禁止です。
  - 値が外部の依存から素通しされていて制御できない場合は、次のとおりです。
    - その部分だけを切り離して個別に絞り込むこと。
    - 残りを厳密なまま保ちます。
- 対象が大きい、または深くネストしていて、書き下した厳密な比較では確かめたい振る舞いが埋もれる場合は、スナップショットに切り替えるても構いません。
- 対象が小さく、書き下した厳密な比較でも読める場合は、スナップショットを使うことは禁止です。
- スナップショットを使う場合は、次のとおりです。
  - 同じ入力に対して意図を述べるアサーションを別に置きます。
    - 記録の一致は意図しない変更の検知には効くが、意図の記述にはならない
  - 記録を、それを固定しているアサーションの隣に置きます。
  - 隣に置くと周囲の仕様が読めなくなるほど記録が大きい場合は、その仕様専用の外部ファイルへ出すても構いません。
    - 外部ファイルへ出した記録はアサーションから見えないので、小さい値でこれをやると、何を確かめているのかがテスト本文から読めなくなる
- ある振る舞いが正しい証拠がスナップショットの一致しかない状態を、証明として受け取ることは禁止です。

## 本物をどこまで残すか

置き換えた対象について、そのテストは何も主張しなくなる。だから置き換えてよいのは、そのテストがもともと何も主張していない領域だけです。外部 I/O が何を指すかは [コードの書き方](/guidelines/writing-code) が持つので、ここでは定義しありません。

- 自分が所有する外部 I/O 境界を置き換える場合は、ダブルを入れても構いません。
- 入力を決定的にできない場合は、次のとおりです。
  - 取り込む側でも成立する注入境界として、外から与えられる形にします。
  - テストでは決まった値を渡しても構いません。
- 入力から出力が決まるプロセス内の依存を置き換えることは禁止です。
  - 入力から出力が決まるということは、それ自体を検証できるということです。置き換えれば検証対象がそこから消える
- 再現できない外部プロセスの失敗や通信の障害を作る場合は、次のとおりです。
  - 置き換える位置を同じ外部境界に留めること。
  - その内側へ踏み込むことは禁止です。
- 対象の依存をすべて置き換えた結果を、対象の振る舞いの証拠として扱うことは禁止です。

この規準を満たすのは、自分が所有する外部 I/O 境界と、決定的にできない入力の源の 2 つだけです。

ダブルは、本物の依存が公開している宣言を写し取ったものです。写し損ねてもこちらのアサーションは何も言わず、本番の経路だけが本物の分岐に入る。

- ダブルを入れた場合は、次のとおりです。
  - 成功したときに返すもの、失敗の伝え方、その中身を、本物の依存が公開している宣言と突き合わせること。
  - 成功や失敗の意味が本物とずれていると分かった場合は、直すまでそのテストを有効な証拠として扱うことは禁止です。
- ダブルの呼び出し記録を生で読み出して値として比べることは禁止です。
  - どう呼ばれたかは、その意図を表すアサーションで書く
- モジュールを差し替えた場合は、次のとおりです。
  - 差し替えたものを素通しに留め、どう呼ばれたかだけを記録させること。
  - 差し替えたモジュール由来のダブルに、返す値・解決値・棄却値・実装を設定してはいけません。
    - 設定した時点で、そのテストが読み戻すのは自分で書いた値になる。差し替えた側は一度も走らない
  - 設定しなければそのテストが書けない場合は、理由を伴う行ローカルの指示をその行の上に残します。
- 引数として渡すダブルを作る場合は、そのダブルに振る舞いを持たせるても構いません。
  - 引数として渡すダブルは置き換えではなくテストの入力であり、走らなくなる本物が存在しない

置き換えたい対象がこの範囲から外れたときは、実装の側を動かすほうを先に見る。ここでは、責務境界として正しい構造変更・テスト可能性・テストの書きやすさ、の順で優先する。

- 外部境界でも決定的にできない入力でもないものを置き換えたくなった場合は、実装の側の構造を変えて本物の依存を残せないかを先に見ます。
- テストの書きやすさと実装の設計が衝突する場合は、実装の設計を優先します。
- テストを書きやすくするためだけの変更を入れることは禁止です。
- ロジックを別のモジュールへ切り出す、または外部 I/O の注入境界を作る場合は、設計として正しい変更として行うこと。
- 注入境界を作った場合は、その周りのロジックを、独立に確かめられる大きさに保ちます。
- 構造を変えても本物を残せない例外がある場合は、オーナーの決定を待つ指摘として [レビューの指摘](/guidelines/review-findings) に載せること。

## 赤の原因を対象に閉じ込める

赤が出たときに原因を対象の振る舞いだと言い切れなくなる経路は 3 つある。テストの意味がテスト本文の外にあること、他のテストと状態を共有していること、実行のたびに入力が変わること。この順で塞ぐ。

- あるテストの意味を決める値を用意する場合は、そのテストの中に書きます。
  - 意味を決めるのは入力値・期待値・引数として渡すダブルの振る舞いの 3 つです
- モジュールスコープでダブルの振る舞いを組み立て、ファイル内の全テストにそれを暗黙に共有させることは禁止です。
- テストからしか使われない下ごしらえを、複数のテストファイルが取り込むモジュールとして置くことは禁止です。
- 同じファイルの中でセットアップを関数へ切り出す場合は、次のとおりです。
  - 各テストが渡した引数だけでそのテストの意味が決まる形に保ちます。
  - テストごとに違う期待値やダブルの振る舞いを、切り出した側に持たせることは禁止です。
- 独立した仕様どうしでセットアップが重複する場合は、その重複を残しても構いません。
  - ヘルパを辿らずに仕様単体で読めるほうが安い
- 重複の排除とテストの独立性が衝突する場合は、独立性を優先します。
- 各テストを、他のテストの実行順・後始末・可変なモジュール状態から切り離すこと。
- テストが外部の状態を変えた場合は、そのテスト自身が持つ後始末で戻すこと。
- 並列実行で外部の名前空間やリソースを共有する場合は、同時に走る他のテストと重ならない名前を取ること。
- 時刻や乱数に依存する場合は、その源を決定的にします。
- 状態の遷移を待つ場合は、次のとおりです。
  - 条件が満たされたことをポーリングします。
  - 固定時間の待機を置くことは禁止です。
- 実行するたびに結果が変わるテストがある場合は、次のとおりです。
  - 原因を取り除きます。
  - 再実行で通ったことを成功として扱うことは禁止です。

## どの層に第一の責任を置くか

層は失敗モードから決める。書きやすいから最小の層、不安だから通しの層、という決め方をしありません。

- 主な失敗モードが、変換・規則・計算・整形の結果を誤ることである場合は、最小の層で押さえること。
- 最小の層でテストを書く場合は、次のとおりです。
  - プロセスの外へ出る依存や、実行時にしか決まらない設定に依存させることは禁止です。
  - そこで扱う振る舞いが通信を行う場合は、次のとおりです。
    - 外部境界をプロセス内で横取りします。
    - URL が不活性なデータで、誰もそれを解決も検証もしない場合は、テストデータとして持っても構いません。
- 主な失敗モードが、隣り合う部品どうしの契約や、自分が所有する外部境界との契約が破れることである場合は、次のとおりです。
  - 統合の層で押さえること。
  - プロセス内の協調物を本物のまま使い、外部 I/O だけ置き換えること。
- 主な失敗モードが、部品を個別に見ても現れず、入口から出力まで通したときにだけ現れる配線・引数の解釈・状態コード・出力先の選択である場合は、次のとおりです。
  - 通しの層で押さえること。
  - 件数を小さく保ちます。
    - 通しの層は実行に時間がかかり、赤が出たときに原因を絞る手数も多い
- 同じ欠陥を複数の層で確実に検出できる場合は、次のとおりです。
  - 検出できる最も安い層に第一の責任を置きます。
  - 同じ証明を各層で繰り返すことは禁止です。
- 上位の層にテストを足す場合は、下位の層が押さえていない別の契約を押さえる場合に限ること。
- 取り込む側が固定して使う公開 API を変更する場合は、提供する側だけの変更でその契約が破れたことが落ちるテストを置きます。
- どの層に置くかを決められない場合は、オーナーの決定を待つ指摘として [レビューの指摘](/guidelines/review-findings) に載せること。

## カバレッジが答える問い

カバレッジを計測する仕組みはこのリポジトリにまだありません。この節が効き始めるのは、計測を持ち込んだ時点です。

カバレッジが数えているのは行が実行されたかどうかだけで、そこで何が主張されたかは数えていありません。

- カバレッジを計測する場合は、次のとおりです。
  - 出た数字を、どれだけの行が一度も動いていないかを示すものとしてだけ読みます。
  - 些末に見えるファイルも計測対象に残し、出た数字をそのまま受け取ること。
  - 数字が高いことを、そこで何かが主張された証拠として読むことは禁止です。
    - 実行された行の割合は、要求そのものが正しいかも、アサーションが要求を拘束しているかも、ダブルが本物と同じ振る舞いをしているかも見ていない
- 入口にテストしづらいロジックがある場合は、次のとおりです。
  - ロジックを別のモジュールへ切り出します。
  - 入口を配線だけの薄い境界にします。
- ロジックの切り出しや外部 I/O の注入境界でテスト可能にできる場合は、計測対象からの除外で片付けることは禁止です。
- カバレッジのゲートを通すことと構造の改善が衝突する場合は、構造の改善を先に取ること。
- カバレッジのゲートを置く場合は、次のとおりです。
  - ゲートを通すために閾値を下げることは禁止です。
  - 未カバーの行をインラインの無視ディレクティブで隠すことは禁止です。
- 上のどれを尽くしてもテスト不能である場合は、除外してよいかを、オーナーの決定を待つ指摘として [レビューの指摘](/guidelines/review-findings) に載せること。

## 振る舞いを足したときに満たすこと

- 振る舞いを追加または変更する場合は、次のとおりです。
  - 要求に対して落ちるテストを先に書きます。
  - そのテストが実際に落ちるのを見てから実装に触ること。
    - 赤を見ることだけが、そのテストに検出する力があることの証拠になる
- 条件によって結果が変わる振る舞いを扱う場合は、意味のある分岐先それぞれと、その境界の値を覆うこと。
  - 欠陥は規則が切り替わる場所に集まるので、同じ分岐の内側から例を増やしても証拠は強くならない
- 意味のある境界やエラーの経路が残っている場合は、成功する経路だけを覆った状態でその作業を完了としてはいけません。
- テスト可能な振る舞いを追加または変更した場合は、次のとおりです。
  - 選んだ層でその振る舞いを所有するテストを追加または更新します。
  - 「あとで足す」「別の変更で足す」を完了の理由にしてはいけません。
