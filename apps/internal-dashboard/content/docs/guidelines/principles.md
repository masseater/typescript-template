---
title: 中核原則
description: すべての主題別の基準に優先する、このリポジトリの判断の土台。
---

主題別の基準は、コードの書き方・テスト・文書・強制の機構のように、触っている対象ごとに分かれています。この文書はその手前にあり、どの対象を触っていても同じように当たる判断だけを持ちます。ここに置いた原則は主題別の基準に優先します。実装が速く終わること、差分が小さいこと、既存のコードと見た目が揃っていることは、いずれもこれらの原則を緩める理由にはなりません。

守ろうとしているのは「いま整合していること」ではなく、「整合しているかどうかを後から判定できること」です。このリポジトリは、Cloudflare Workers へ配るアプリと、外に残り続けるインフラの宣言を同じ木に持っています。指摘を出す側と直す側は同じエージェントで、判定を止める機構は各 workspace の lifecycle タスクと `alchemy plan` だけです。どれも、今日たまたま揃っている状態を明日の保証には変えられません。

節は、末尾の「優先順位」の並びに沿って置いてあります。

## 機械が挙げた一致の読み方

字面の一致を機械が挙げるのは、いまこのリポジトリでは Oxlint と knip の範囲に限られます。ここにあるのは、その範囲で出た報告をどう読むかです。

- 検出器が挙げた組は、候補として扱います。
- 検出器が挙げたこと自体を、統合すべき根拠にしてはいけません。本体が一致することは、同じ概念であることの証明にはなりません。
- 検出器が何も挙げないことを、意味的な重複が無い証拠にしてはいけません。
- 一致が、機械が書いた領域か、読み手に見せるために意図して反復している領域にしか無いときは、判定の対象から外します。後者に当たるのは、テストが並べる入力と、文書に載せた例です。
- 一致を外すためだけの書き換えで報告を消してはいけません。
- 両方の宣言を残したまま、抑制で報告を止めてはいけません。
- 報告が実態と食い違っていると考えているときは、食い違う理由を突き止めてから設定に例外を書きます。理由が分からないまま設定で除外してはいけません。`knip.ts` が持つ除外は、生成された `routeTree.gen.ts` や Vite / Vitest の設定の読み取りのように、使っているのに静的な解析からは見えない手順のためにあるものです。

## 人が判定する責務の重なり

機械が挙げられる範囲の外側に残るのは、責務が重なっているかどうかの判定と、重なっていたときに持ち主をどこへ置くかの判定です。どちらも機械が答えを出さないので、守りたいのは「構造上すべての利用箇所に当たる」という状態であって、見た目の重複が減ることではありません。

- 重複は「同じ責務を負う宣言が 2 か所以上にあり、そのどれもが他を取り込んでいない状態」として判定します。
- 字面の似ている宣言を見つけたときは、責務とふるまいの契約が一致することを確かめてから重複と呼びます。字面の一致だけを根拠に重複と呼んではいけません。
- 責務とふるまいの契約の一致を確かめられていないときは、分けたまま残します。
- 似ているが別の規則を担っており、今後それぞれ独立に変わることが見込まれるときは、統合してはいけません。
- 統合するかどうかを決めきれないときは、統合後の持ち主に責務を言い当てた狭い名前を付けられるかを試します。名前が出てこないなら、それは 2 つの責務である可能性が高いです。
- 確証が無いまま倒す先を決めるときは、重複を残す側に倒します。
- 持ち主を置く場所を選ぶときは、その責務を既に負っているワークスペースを再利用します。責務を負っていないワークスペースへ、依存の向きを逆にしてまで寄せてはいけません。
- その責務を負っているワークスペースが無いときは、責務を言い当てた狭い名前の持ち主を新しく作ります。
- 複数のワークスペースが同じ宣言を必要とし、その責務がどれにも属さないときは、双方が依存できる中立の置き場所を持ち主にします。その置き場所が何を受け入れて何を断るかを、置き場所自身の規範に書きます。中立の置き場所は主題では選べません。断る条件を持たないまま置くと、主題の違うものが集まって、次に持ち主を選ぶときの判断材料が消えます。
- 持ち主を迂回する書き方が機械的に検出できる形をしているときは、同じ変更でガードを入れます。

## 意図を所有する文書

コードの側だけを見ても、それがそうであるべきだったのかは分かりません。所有する文書が 1 つ決まっていて、そこが実装より先に動いていることだけが、後から意図を読める形になります。

- 変更が、文書化された意図・ふるまい・設計上の不変条件のいずれかを変えるときは、それを所有する規範文書を、同じ変更の中で実装より前に更新します。
- その意図を所有する文書がまだ無いときは、実装を変える前に作ります。
- 古いふるまいを説明したままの文書を残してはいけません。

## ずれうる設計を採らない

- 2 つの記述が同じ事実を表しているかは、片方を変えたときにもう片方が失敗するかで決めます。
- 2 つが別々の理由で別々に変わりうるときは、いま形が似ていることを根拠に 1 つへ寄せてはいけません。
- 1 つの事実の二重表現だと判定したときは、権威を持つ表現を 1 つ選び、残りをそこから導出します。両方を手で直し続ける運用を選んではいけません。
- どの表現も他方から導出できないときは、ずれた時点で機械的に検出されて落ちる形にします。
- 導出も検出もできない設計を採ってはいけません。
- 不正な組み合わせを「書かない」という約束で防いだことにしてはいけません。行き先は、表現できない形にするか、機械的に弾くかのどちらかです。

外部サービスの設定値について、管理 API から読み書きできるものを Alchemy の宣言に置き、宣言と実体のずれを `alchemy plan` に見つけさせることは、この原則を外の状態へ当てた形です。

## 確認が保証している範囲

- ある確認が通ったことを、その確認が見ていない性質の保証として扱ってはいけません。
- ある違反と同等の確認が、失敗を返す形で動いているときは、同じ違反をレビューで人が重ねて数えてはいけません。
- 同等の確認が動いていないときは、その項目を人が見る対象に戻します。報告されるだけで終了コードを動かさない確認は、ここでいう「動いている状態」には当たりません。
- 確認が届かない側の判断を、確認が動いていることを理由に省いてはいけません。確認が届かないのは、実装と規範文書のずれ、型が主張する契約と実行時に守らせている契約のずれ、宣言と外に残る状態のずれ、そして 2 つの側が出会う場所でだけ現れる食い違いです。

この文書自身も確認の外にあります。記法が揃っているかを読む機構はこのリポジトリにありません。

## 始めたことを閉じきる

統合を始めることと、失敗を成立させている条件を見つけることは、どちらもそこで止めると元より悪い状態を残します。持ち主だけが増えた木と、1 箇所だけ直った同型の欠陥は、次に読む側から見れば「済んでいる」ように見えます。

- 統合の完了は、責務を負う宣言が 1 つだけ残り、その責務を使うすべての場所が取り込みでそこへ届き、持ち主を迂回して同じ責務を書き直す手順が塞がれた時点とします。置き場所を作ったところで止めると、消し残した宣言がそのまま使われ続けます。
- 見つけた独立の宣言は、同じ変更の中ですべて消します。
- 不正な構造を残したまま、その上に回避策を足してはいけません。
- ファイルを変更するときは、そのファイル全体と、それが属する契約を読みます。契約に当たるのは、公開している型、ふるまいを説明している規範文書、呼び出し側が前提にしている形です。該当行の周辺だけを見て直してはいけません。
- レビューまたは機械の確認がある書き方を禁じたときは、その変更の中にある同型の箇所を残らず直します。

## 自動化が所有する変換を先に実行する

- これから触る出力を所有する自動化があるときは、先にその自動化を実行し、出力を全部読みます。終了コードだけを見て通ったとみなしてはいけません。
- 自動化が対応していないことを、不変条件を外してよい理由にしてはいけません。

## 同時に切り替えられない解釈者がいる契約

このリポジトリでこれが実際に起きるのは、state store の宣言と state のあいだです。宣言が main に入る前に手元から適用すると、state だけが先へ進みます。以後 main から preview した者には、その差分が自分の変更と無関係な削除として現れ、apply 全体が落ちます。止まるのは適用した本人ではなく、次にその stack を触る者です。デプロイ先の設定でも、暗号化した env を復号する鍵でも、Alchemy の stack のあいだで受け渡す出力でも、当てる問いは変わりません。

- 独立に更新される解釈者が現時点で 1 つもいないときは、契約として扱わなくても構いません。
- 解釈者が同じソースツリーにあるが、原子的には切り替えられないときは、契約として扱います。
- 相手がこちらと同時に追随することを前提に置いてはいけません。
- 変更する契約に、こちらの変更と同時には切り替えられない解釈者がいるときは、移行の全期間を通じて、どの解釈者から見ても契約が解釈できる状態を保ちます。どれか 1 つの解釈者が契約を解釈できなくなる期間を作ってはいけません。移行境界を同じ変更の中で言葉にします。言葉にするのは、どの順序で進めるか、どの中間状態を経由するか、いつ旧解釈を落とせるかの 3 つです。
- 旧解釈を落とすときは、すべての解釈者が新しい形へ移り終えたことを確かめてから出します。
- 書き出した導出結果の作り方を変えるときは、古い作り方で書かれた結果が読み捨てられるようにします。

## レビューの最初で見る問い

変更を出す前と、他人の変更を読み始めた最初に、差分に対してこれを当てます。各問いに添えてあるのは、その問いを規範として持っている節です。拘束しているのは指し先の規範であって、問いの文ではありません。

- 検出器の報告を、実装ではなく検出のされ方を変えることで消していないか（[機械が挙げた一致の読み方](#機械が挙げた一致の読み方)）
- この変更が触れた宣言と同じ責務を負う宣言が、他の場所に残っていないか。残っているなら、消費側はどちらを取り込んでいるか（[人が判定する責務の重なり](#人が判定する責務の重なり)）
- ふるまいや不変条件が変わったのに、それを所有する規範文書が同じ変更に入っていないか（[意図を所有する文書](#意図を所有する文書)）
- 導出も検出もできない形のまま、同じ事実が 2 か所に書かれていないか（[ずれうる設計を採らない](#ずれうる設計を採らない)）
- 通した確認は、いまここで主張したい性質を実際に見ているか（[確認が保証している範囲](#確認が保証している範囲)）
- 統合を含む変更なら、独立の宣言は消えきったか。共有の持ち主を用意したところで止まっていないか（[始めたことを閉じきる](#始めたことを閉じきる)）
- 直したのは報告された 1 行か、それを許した条件か（[レビューの指摘](/guidelines/review-findings)）
- 自動化が所有している出力を、その自動化を実行しないまま触っていないか（[自動化が所有する変換を先に実行する](#自動化が所有する変換を先に実行する)）
- この契約を、こちらと同時には切り替えられない誰かが読んでいるか。読んでいるなら、移行境界はどこに書かれているか（[同時に切り替えられない解釈者がいる契約](#同時に切り替えられない解釈者がいる契約)）

## 優先順位

1. 責務の境界を守ることが、字面の一致をなくすことに優先します。誤った統合は、無関係な変更どうしを 1 つの持ち主に結び付けます。
2. ずれうる設計を採らないことが、実装の速さ・差分の小ささ・既存との見た目の一貫性に優先します。
3. 失敗を成立させている条件を閉じきることと、始めた統合を終わらせることが、変更を小さく保つことに優先します。見つけた宣言を全部消しきれていないなら、その変更を統合とは呼びません。
4. 自動化が所有する変換を実行することが、手で編集することに優先します。
5. すべての解釈者が契約を解釈できることが、目指す最終形へ最短で到達することに優先します。移行境界を決めて並存する期間を有限に区切っているなら、2 つの形が並ぶことは 2 に反しません。
