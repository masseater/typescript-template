title: インフラ
description: 外に状態を残す資源を、リポジトリの宣言だけから変え続けるための判断基準
---

この文書が守るのは、リポジトリの宣言が、外に残り続ける状態について嘘をつかない状態です。外の状態はコードと違って合流しないため、宣言と現実のずれは、次の適用が片方を何も言わず上書きするまで観測されありません。

このリポジトリは、Worker を所有するパッケージの `alchemy.run.ts` と `infra/cloudflare` の共有 Stack で Cloudflare の状態を宣言から作っている。GitHub Environment にデプロイ先の値が揃っているとき、staging への適用は main への統合で自動的に行い、本番への適用は GitHub Environment の承認を経た昇格だけが行う。揃っていないときは適用を始めず、部分だけ揃っているときは失敗する。差分の確認は `alchemy plan` が受ける。

節は、資源について決めること、宣言について決めること、適用について決めることの順に並べてある。ここにあるのは、stack の分け方や外部サービスごとの認証方式といった個別の取り決めを決めるときに当てる基準です。

## 資源の持ち主と、変えられる口

- 外部の資源を宣言に取り込む場合は、それを自分が所有していることを先に確かめます。
- 自分が所有していない資源を、自分の宣言の中に所有物として書くことは禁止です。
  - 動いている基盤に組み込みで存在するもの、別の宣言が既に所有しているもの、別の担い手が管理しているものが当たる。Firebase が作ったサービスアカウントを取り込まないのがこの形にあたる
- 誰が所有しているかが曖昧な資源がある場合は、自分の所有としないこと。
- 自分が所有しているのに宣言の外にある資源を見つけた場合は、宣言の中へ入れます。
- 1 つの資源に対して、それを変更してよい宣言的な手順をちょうど 1 つに保ちます。
- 既にある手順の外側に、同じ資源を変えられる 2 つ目の手順を作ることは禁止です。
  - 別の宣言の仕組みも、提供元の CLI や API を直接呼ぶ手順も、管理画面での手作業も同じに数える
- 提供元が、宣言より優先される別の設定の口を持っている場合は、次のとおりです。
  - そちらの口を空にするのと、宣言へ書くのを同じ変更で行います。
  - 両方に値を残すことは禁止です。
    - 残すと、宣言側が何も言わず機能しなくなる
- 既に存在する資源を宣言の管理下に置く場合は、その資源の同一性を宣言の側へ取り込んでから変更します。
- 値を作成時にしか読み出せない資源を宣言の管理下に置く場合は、次のとおりです。
  - 新しく作り直して、値を必要とする側の参照を差し替えること。
  - 既存の資源を取り込んで、値が入っているものとして扱うことは禁止です。
- 複数の利用者から参照される実体が 1 つしか存在しえない場合は、次のとおりです。
  - 所有者をちょうど 1 つ決めます。
  - 他の利用者が、所有者の公開した出力を通してそれを使う形にします。
  - 利用する側の宣言に同じ実体を書くことは禁止です。

外部サービスの設定に触れるとき、まず IaC だけで表現できないかを調べることは `AGENTS.md` が決めている。

## 恒久と使い捨ての線

一時的な環境に置いてよいかは、危険でない証拠の側で決まる。危険かどうかの入力になる性質は 3 つある。一時的な側の実行から恒久的な側へ届く接続があること。恒久的な側がその実体の同一性を参照しており、複製がそれを奪うこと。隔離を用意して維持する費用が、一時的に持つことの利益に釣り合わないこと。閉じた一覧ではないので、扱う作用の種類が増えたときはその作用から導き直す。

このリポジトリは、本番と資源を共有しない恒久の staging を 1 つ持つ。Environment にデプロイ先が揃っているとき、main への統合は staging へ自動適用し、実利用者向けの本番への適用は GitHub Environment `production` の承認を経た昇格だけが行う。かつて置いていた一時的な preview は、本番と同じ手順でデータベースと外部サービスへ繋がる実体を持っていたため廃止した。

- 一時的な環境への配置を、危険な性質のいずれにも当たらないことの積極的な証拠が記録されている場合に限ること。
- 当たると確認できなかったことを、当たらないことの証拠として扱うことは禁止です。
- 当たるかどうかの判断が付かない場合は、恒久的な側に置きます。
- 隔離が機能していることを確かめられない場合は、機能していないものとして扱います。
- 恒久的な staging を置く場合は、次のとおりです。
  - 別の prefix・別の D1・別の origin・別の送信ドメインを持ち、本番の資源へ到達する接続が無いことの積極的な証拠を記録します。
  - Environment にデプロイ先が揃っているとき、main への統合が staging へ適用され、本番への適用は Environment 承認付きの昇格だけであること。
  - デプロイ先が無いときは適用を始めず、一部だけ揃っているときは失敗すること。
  - 本番とデータベース・外部サービス・送信ドメインを共有する staging を置くことは禁止です。
- 恒久的な側に置いていたものを一時的な環境へ移す場合は、次のとおりです。
  - 当たっていた危険な性質を消す隔離の手段を、移すより先に用意します。
  - 残った検知の手段と、影響の及ぶ範囲と、復旧の手段を変更の記録に残します。
  - 手段より先に移すことは禁止です。
- 一時的な環境が恒久的な側の資源へ届く場合は、次のとおりです。
  - その環境への到達そのものを制限します。
  - URL が知られていないことを制限の代わりにしてはいけません。

## 「これで全部」と言える範囲

宣言の仕組みは、宣言に書かれていないものを消してよいものとして扱う。

- 外部のアカウントや区画を他の所有者と共有している場合は、次のとおりです。
  - 自分の宣言が及ぶ範囲を、明示された区画に閉じること。
    - 区画の表し方は、名前の前置きでも、標識でも、状態の境界でもよい。明示されていることだけが要る
  - 共有している空間の全体を、自分にとってのあるべき状態とみなすことは禁止です。
- 複数の所有者が書き込む集まりを調停する場合は、次のとおりです。
  - 自分が持ち込んだ要素だけを対象にします。
  - 自分の宣言で全体を置き換えることは禁止です。
- 単位と対象の名前を、単位と対象から機械的に決まる形にします。
- 一時的な環境を作ってよい対象を決める場合は、次のとおりです。
  - 単一の許可リストへの登録だけで決まる形にします。
    - 許可リストなら、載せ忘れた対象は作られずに済む。除外の一覧では、書き忘れた対象がそのまま作られる
  - 除外のための一覧、離脱を表す印、別の場所にある対応表で可否を表すことは禁止です。
- 許可リストが持っている情報を、その外側に複製してはいけません。
- どの外部サービスのどのアカウントがこのリポジトリのものかを判断する場合は、次のとおりです。
  - 名前が似ていることを根拠に、そのアカウントを自分のものとみなすことは禁止です。
    - 外部サービスのアカウントは複数のリポジトリで共有されており、取り違えると他のリポジトリの資源を操作する
- 一括で撤去する操作が、宣言に書かれていない同種の資源まで列挙する場合は、次のとおりです。
  - 共有しているアカウントでその操作を使わないこと。
  - 宣言側に書いた保持の指定を、一括で撤去する操作に対する防御として数えることは禁止です。
    - `alchemy unsafe nuke` は送信サブドメインをアカウントの全ゾーンから列挙するので、他の所有者が登録したドメインも対象に載る

## 一度に動く単位

状態の境界は、1 回の適用と 1 回の切り戻しが届く範囲です。

- 1 つの単位にまとめる条件を、同じ権限で動き、同じ頻度で変わり、一緒に配備され、一緒に切り戻されることの 4 つが揃うこととします。
- 4 つのうち 1 つでも揃わないものがある場合は、単位を分けます。
- まとめるか分けるかを決めきれない場合は、分ける側に倒すこと。
- ある単位が、別の単位の作ったものに依存する場合は、次のとおりです。
  - 所有する側が公開した出力を消費する形にします。
  - 依存する先を、消費する側でも宣言し直すことは禁止です。
- 単位のあいだに依存がある場合は、適用の順序を自動化の側に明示します。
- 出力を作る側の変更が、消費する側がそれに依存し始めるより先に出ている状態を保ちます。

## 適用する主体が持つ権限

- 適用を行う主体の権限を、明示的に記述します。
- 管理している対象の種類から、権限の記述を機械的に生成してはいけません。
- 管理対象が必要とする権限と、主体が実際に持つ権限の突き合わせを機械的に行うこと。
- 新しく権限が必要になった場合は、次のとおりです。
  - その対象を既に含んでいる記述に足します。
  - 既存の記述の対象の範囲を広げて収めることは禁止です。
- 権限が足りているか確信を持てない場合は、足りていないものとして扱います。
- 権限が足りないために適用できない変更がある場合は、権限が実際に適用され、その証跡が残るまで統合しないこと。
- 検証のための試行が通ったことを、適用に要る権限が付与されている証拠として扱うことは禁止です。
  - 読み取りだけを許された主体でも、差分の計算までは通る。権限の不足は適用の段階で初めて表面化する
- 適用する主体が、自分自身の権限を書き換えられる範囲を持つ場合は、次のとおりです。
  - その単位の適用を、CI から実行しない判断を含めて検討します。

## 適用が済んだと言える条件

実行されなかった実行、承認を経ていない適用、途中で止まった撤去は、どれも結果だけを見れば通ったように見える。

- 認証・対象の同定・必要な設定のいずれかが欠けている、または妥当でない場合は、次のとおりです。
  - 閉じる側へ倒して失敗させること。
  - 何が欠けていたのかを結果の中から読める形にします。
- 欠けている前提を飛ばして成功扱いにしてはいけません。
- 実在の利用者に届く変更を適用する場合は、次のとおりです。
  - 明示的な人間の承認を経ること。
  - 承認された版であることを確定させてから適用します。
- 検証のための試行と、承認を経た適用を、対象も手順も分けて持ちます。
- 子を持ちうる階層の構造を置き換える、または削除する場合は、子の所有と移行の方針が決まるまで適用しないこと。
- 撤去を始める引き金が何であれ、行き着く状態を 1 つに揃えること。
  - 引き金になるのは、一定の期間動きが無いこと、対象そのものが閉じられたこと、求めていた側が意図の表明を下ろしたことです
- 環境を撤去したときに、それを求めていた意図の表明も同時に取り下げること。
- 既に無いものへの撤去の要求が来た場合は、成功として扱います。
  - 目的は無いことであって、今回の操作で消したことではない
- 同一性を変えると置き換えになる資源に、削除しない指定を付ける場合は、次のとおりです。
  - 古い実体が共有している空間に残ることを前提に、撤去の担い手と手順を先に決めます。
  - 同一性を決める値を、撤去の手順が無いまま変えることは禁止です。
    - `RemovalPolicy.retain` は置き換えで捨てられる旧世代にも当たるので、送信ドメインを変えると古い登録と DNS レコードがゾーンに残る

## 適用したものが動いていることを確かめる

適用が成功したことと、利用者から見て期待どおりに動くことは別です。宣言と実体が一致していても、その一致が意図した振る舞いを生むとは限らありません。

- インフラを変更して適用した場合は、次のとおりです。
  - 対象が実際に問題なく動いていることを、利用者から見える手順で確かめます。
  - 確かめる手段を、対象に応じて DNS の解決、HTTPS の応答、メールの届き方、API の応答のように選び、実際にコマンドを実行します。
  - workflow が成功したこと、差分がゼロであること、資源が存在することだけで完了と判断してはいけません。
- 適用と、それを前提に動く別の仕組みが並行して実行される場合は、次のとおりです。
  - 両方が終わった後の状態を確かめます。
  - 適用の側だけを見て完了としてはいけません。
- 適用の直後に失敗するものがあり、それが一度だけの競合による場合は、次のとおりです。
  - 競合が起きる条件と、解消する手順を記録に残します。
  - 再実行で通ったことだけを残すことは禁止です。
