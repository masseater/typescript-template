この文書が守るのは、確認を通った変更と、確認されていない変更が見分けられる状態です。判定するツールと、その判定が実行される手順の両方が要る。ツールを足しても実行される手順に入っていなければ設定に名前があるだけになり、手順を厚くしてもそこで実行されるものが何も判定しなければ通過の記録が増えるだけになる。

節は、実行されたか、落ちるか、何を守れるかの順に置いてある。守れる範囲がどれだけ広くても、実行されていない確認は何も見ていありません。

## 実行されなかった確認を成功と数えない

対象から外れた確認と、失敗が伝わらない確認は、どちらも実行されなかったのに成功として報告される。

- 通過条件として数える実行を条件で絞り込みたい場合は、次のとおりです。
  - 起動した後の階層で絞り込むこと。
  - 起動そのものの条件で絞り込むことは禁止です。
    - 起動しなかった実行は結果を持たありません。落ちたのか実行されなかったのかが、通過の記録から区別できなくなる
- その実行を通過条件として数えないと確定でき、起動そのものの条件でしか絞り込みを表現できない場合は、起動の条件で絞り込むても構いません。
- 確認や適用が失敗した場合は、次のとおりです。
  - 失敗のまま伝播させること。
  - 暗黙のスキップ・握り潰し・継続許可で成功に読み替えることは禁止です。
- 出力を別のコマンドへ渡す段を書く場合は、パイプの途中の失敗が終了コードに現れる設定であることを確かめます。
- パッケージ内で閉じる品質作業の対象を選ぶ場合は、次のとおりです。
  - 依存グラフとキャッシュを持つタスクランナーに選択を任せること。
  - その前段に別の絞り込みを重ねることは禁止です。
- 実行の段取りの記述だけが変わった場合は、対象の選択を広げることは禁止です。
- 依存構造そのものが変わり、影響範囲を局所化してよいかを判断できない場合は、対象の選択を広げます。
- 品質の通過条件の走査範囲を決める場合は、配布物に入るコードの実際の配置に追随させること。
- キャッシュ再利用の既定をまとめて切り替える設定を書く場合は、次のとおりです。
  - その切り替えが及ぶ定義を数え上げ、1 つずつ性質を確かめます。
  - 個々の定義を確かめずに、キャッシュ再利用の範囲を広げることは禁止です。
    - まとめて切り替える設定は、各 workspace の `vite.config.ts` の `tasks` と `package.json` の `scripts` のどちらにも及びうる
- ファイルを変更することが目的の定義を書く場合は、キャッシュ再利用の対象にしてはいけません。
- 常駐プロセスを起動する定義を書く場合は、次のとおりです。
  - キャッシュ再利用の対象にしてはいけません。
  - 常駐であることをランナーに宣言します。
- 既定の入力集合を、自分で書いた集合で置き換える場合は、そのタスクを実装するワークスペースの実際の入力をすべて数え上げること。

## ガードが落ちることを確かめる

設定に名前が出ることは、そのガードが実行されることを意味しありません。

- ガードを追加した場合は、次のとおりです。
  - 違反を仕込んだ入力で、実際に報告が出ることを確かめます。
  - 違反とみなさない入力で、報告が出ないことを確かめます。
  - 実装や設定に存在することをもって、検出できているとみなすことは禁止です。
- 不変条件に違反したコードがガードをすり抜けているのを見つけた場合は、次のとおりです。
  - コードを直します。
  - ガードの落ちるべき入力に、その抜け道を足します。
- ガードの報告に、破られた不変条件と直す方向の両方を含めます。
- 安全で決定的な直し方がちょうど 1 つに定まる場合は、自動修正を用意します。
- 有効な直し方が複数残る場合は、自動修正を用意してはいけません。
- 自動修正が安全に終えられない部分を、失敗するガードとして見える状態に残します。

## 何を守れる機構かで選ぶ

判定する側は 3 種類ある。**強制**は不正な状態を自動的に拒否するもので、各 workspace の `vite.config.ts` が `precommit`・`prepush`・`prepr`・`premerge`・`prerelease` に依存させたタスク（`.vite-hooks/` と `.github/workflows/check.yml`・`.github/workflows/prerelease.yml` がそれぞれを起動する）と、`infra/` の各適用単位の `plan` と `deploy` がこれにあたる。**記録**はなぜそう決めたかを保つもので、コミットログと、この `apps/internal-dashboard/content/docs/guidelines/` がこれにあたり、違反を止めません。**安定した基準**は、要求される状態と違反の境界の両方が決着しているもので、方向性だけあって境界が決まっていないものはここに入らなりません。

違反を判定するのに何を見る必要があるかで、載せられる機構がほぼ一意に決まる。1 ファイルの構文だけで決まるものは型と lint が、実行して初めて分かるものはテストが、複数のファイルや宣言をまたぐ突き合わせは検証コマンドが、宣言と外に残る状態の突き合わせは `alchemy plan` が受ける。どの材料も揃わないものだけが、規範の散文とレビューで見る項目に残る。

- 根拠を残したことをもって、その基準が強制されているとみなすことは禁止です。
- その不変条件の全体を確実に守れる機構を、主たるガードにします。
- 一部しか守れない機構を、主たるガードにしてはいけません。
- 複数の機構が同じだけ確実に守れる場合は、失敗が返るまでの距離が短いほうを採ります。
  - 平文の環境変数ファイルと秘密の値は `.vite-hooks/pre-commit` が手元で返し、`.vite-hooks/pre-push` の失敗は push まで返らない
- 不変条件が、ふるまいと実行時の境界を通る値の両方に掛かっている場合は、両方に届く機構を置きます。
  - 片方だけを置くと、覆えなかった側が未確認のまま残る
- 不変条件がどちらか一方だけに掛かっている場合は、その一方を見る機構を選びます。
- 既にその不変条件を表現できるガードがある場合は、次のとおりです。
  - それを設定するか拡張します。
  - 並行する新しい検出器を作ることは禁止です。
- 既存のガードがその不変条件を確実には表現できない場合は、確実に守れる機構を新しく置きます。
- どの機構もその基準を確実に評価できないと確認できた場合は、レビューで見る項目として残します。
- 安定した基準に対して機構を選んだ場合は、どの機構で止めたかと、選ばなかった候補では何を守りきれなかったかを、コミットログに残します。
- 選んだ機構を別の機構へ移した場合は、移した理由を同じ場所に残します。
- 機構の選択の根拠を、ガードの実装やその設定だけに残すことは禁止です。

## ガードを入れる時点

守るのは、基準が決まってからガードが入るまでの間に、その基準を破れる期間を作らないことです。

- 基準が決着していて、機械的に検出できる違反が予見できる場合は、その基準を導入する変更、または最初の違反を直す変更と同じ変更でガードを入れます。
- 二回目の発生を待つことは禁止です。
- 議論が決着していない場合は、次のとおりです。
  - 自動化してはいけません。
  - 拘束力のある散文として書くことは禁止です。
- レビューで人が毎回同じ判定をしている項目があり、その判定を機械が評価できる場合は、次のとおりです。
  - その項目をガードに置き換えること。
  - ガードを足したうえで、同じ判定をレビューで見る項目として残すことは禁止です。

## 強制度を落とすときの形

強制度を落とす操作は、落とした範囲をそのまま恒久の免除に変える。範囲を誰が決めたかが残っているかどうかが、免除と放置を分ける。

- 既存の違反があってすぐ全体を強制できない場合は、強制度を落とす範囲を、個別に名指しした既存のファイルに限ること。
- パターンの単位で強制度を落とす場合は、次のとおりです。
  - その判断と、何が守られなくなるかをコミットログに残します。
  - 記録を伴わないまま範囲を開くことは禁止です。
- 実行の段に継続許可を付ける場合は、次のとおりです。
  - その段を通過条件として数えないことと、代わりに何がその不変条件を見るのかを同じ変更で決めます。
  - 落ちるようになるまでの一時措置として付けたまま放置してはいけません。
- 解消済みの違反に残っている抑制を、違反そのものと同じ扱いで落とすこと。
- 抑制を、違反したその一行だけに掛かる形に限ること。
  - 無効化と再有効化を対で囲むと、その間に足されたコードが、誰にも意識されないまま免除に入る
- 一時的に強制度を落とした場合は、その違反が解消した変更と同じ変更で戻すこと。

## main に入る手順をすべて同じ確認に通す

main に変更が入る手順は、ブランチを転送して PR を merge する 1 つです。

- main に変更が入るすべての手順を、同じ確認のまとまりに通らせること。
- 手順ごとに実行する確認の集合を別に持つことは禁止です。
- 通過条件を迂回できる形が残っている場合は、迂回したことを出力で見える状態にします。
- 通過条件の有無が手元の設定に依存する場合は、次のとおりです。
  - その設定を、依存の導入手順が毎回書き込む形にします。
  - 手順を文書に書いただけで、設定されているとみなすことは禁止です。
- `--no-verify` で手元のフックを飛ばすことは禁止です。

## 実行の定義に書いてよいもの

このリポジトリの定義ファイルは、持ってよいものが違う。`package.json` の `scripts` は、コマンドの名前と、その名前が指す 1 本の呼び出しを持つ。各 workspace の `vite.config.ts` は、タスクどうしの依存とキャッシュの性質と入出力を持つ。`.vite-hooks/` の各スクリプトは、フックの起動口と、そこから呼ぶコマンドを持つ。このどれかで分岐・再試行・対象探索が育つと、そのコードは型も自動テストも持たないまま、その定義ファイルの上でしか実行されないものになる。手元と自動化で挙動が食い違い、失敗の原因調査が定義ファイルの評価順序まで降りていく。

- このいずれかに実行ブロックを書く場合は、次のとおりです。
  - 1 つのコマンド呼び出しに留めること。
  - 再試行・繰り返し・分岐・エラー処理・対象探索をそこに書くことは禁止です。
  - それらが必要になった時点で、型と自動テストを持つリポジトリ内のコードへ移します。
- 同じまとまりが定義ファイルの中で増えた場合は、単一のまとまりへの参照で解消します。
- 増えたものが順序を持つ手順の並びである場合は、再利用できるまとまりへの切り出しで解消します。
  - 参照で置き換えられるのは、そのまとまりが丸ごと同じ位置で使われる場合に限る。並びの一部だけを別の場所に置きたくなった時点で、まとまりとして切り出すことになる

この文書で要るのは、リポジトリのルートから呼べる起動口が委譲だけを持つ限り、定義ファイル側へ振る舞いが染み出す手順も塞がるという関係です。

## 源と生成物

このリポジトリが源から導いている成果物は、`pnpm-lock.yaml` と、Drizzle が生成する migration の SQL です。導出できるものを独立した表現として保守すると、1 つの事実が 2 か所で別々に動きはじめる。生成は、そこから手作業の入る余地を取り除く操作です。

- 真実の源から決定的に導ける成果物を、生成して得ること。
- 生成物に対する操作が 2 つ目の表現を作りうる場合は、次のとおりです。
  - 内容を変えたいときは、源を編集して生成し直すこと。
  - 生成物を直接編集してはいけません。
  - 1 つの生成物に 2 つ目の生成の手順を作ることは禁止です。
- 生成物をコミットしている場合は、次のとおりです。
  - 源の変更と生成された出力を、同じ変更に入れます。
  - 源から乖離したことを機械的に検出する手順を付けること。

## 機械だけが読み書きする成果物

読み手も保守する側も機械である成果物がある。このリポジトリでは `pnpm-lock.yaml`、`.vite-hooks/`、`node_modules/.cache/`、Alchemy の state がこれにあたる。

- 置かれているパスだけを根拠に、機械向けの成果物として分類してはいけません。
- 人も機械も読む文書である場合は、人間向けとして扱います。
- 人間に対して拘束力を持つ内容の基準を、この種の成果物に置くことは禁止です。
- 人間向けの規範文書が、基準としてこの種の成果物を指すことは禁止です。
- この種の成果物に人間向けの規範が一緒に入っているのを見つけた場合は、その主題を所有する規範文書へ移します。
- 機械にとっての有用性と、人間に対する拘束力の所在が衝突する場合は、拘束力のある内容を人間向けの文書に置く判断を先に取ること。
- この種の成果物を、機械にとっての有用性と構造の妥当性で評価します。
- この種の成果物の散文を、人間向けの文章としての質を理由に差し戻すことは禁止です。
- 形式を所有するツールがある場合は、次のとおりです。
  - 作成・更新・改名・削除を、そのツールを通して行うこと。
  - ツールの外で手編集してはいけません。
    - Alchemy の state を手で書き換えないことがこれにあたる。state は宣言と外の実体の対応を持っており、片方だけを動かすと次の適用が実体を作り直すか消す
- この種の成果物をいつ保守するか決める場合は、次のとおりです。
  - 使っている側が具体的な必要を検知した時点に任せます。
  - 固定の周期や、人間側の工程に紐づけることは禁止です。
  - リポジトリ全体に当たる安全性と正しさの制約を、その裁量の外側に置きます。

## 実行単位を分ける軸

- 自動化を新しい実行単位に分けるか既存に足すかを決める場合は、次のとおりです。
  - 起動のタイミングとライフサイクルを軸に分けること。
  - 機能名・パッケージ名・担当領域を軸に分けることは禁止です。
- 実行単位に名前を付ける場合は、起動のタイミングかライフサイクルが読み取れる名前にします。
- 起動のタイミングが独立していて、失敗したときに巻き込む先が他と揃わない自動化がある場合は、独立した実行単位に置きます。
  - 同居させると、一部の自動化のために宣言した広い権限を、残り全部が常時持つことになる
- 複数の実行単位から使うまとまりを作る場合は、次のとおりです。
  - 呼び出す側にトリガを持たせること。
  - まとまり自身にトリガを持たせることは禁止です。
- 互いの結果や出力を参照し合う処理がある場合は、次のとおりです。
  - 同一の実行単位の中に置きます。
  - 実行単位をまたいで結果を受け渡すことは禁止です。

## 外へ出す操作

このリポジトリの自動化は、外へ出る操作を実際に持っている。`infra/` の各適用単位の `deploy` は Cloudflare の状態を変え、Worker にアプリを配置する。公開されたものと適用された変更は取り消せありません。

- 外部状態を変える場合は、次のとおりです。
  - レビューを経たリビジョンから、自動化された手順で実行します。
  - 検証されていない手元の作業ツリーから実行してはいけません。
- 外部状態を変える操作が特定の成果物を前提にする場合は、外部状態を変える前にその成果物の同一性を確認します。
- 成果物の生成側と、それを前提に外部状態を変える消費側がある場合は、次のとおりです。
  - 生成から消費までを 1 つのまとまりとして扱います。
  - 消費側だけが対象に選ばれる手順を残すことは禁止です。
- 外部状態を変える操作、または外部に問い合わせる確認を実行する場合は、明示的な対象集合を与えること。
  - `alchemy` の呼び出しが `--stage` を明示しているのがこの形にあたる
- ある処理が品質作業か外部への副作用かを判別しづらい場合は、外部への副作用として扱います。
- 資格情報を実行単位に渡す場合は、次のとおりです。
  - ソースを取得する権限を、読める範囲を絞ったものにします。
  - 外部に書き込む権限を、実行単位が宣言した権限としてその実行に帰属させること。
- 自動化が報告を生成する場合は、次のとおりです。
  - 生成したコマンド自身が、単一の所有された手順で、決まった掲示先に出します。
  - 報告の生成と掲示を別の工程に分けることは禁止です。
  - 複数の先から同じ掲示先を書き換えることは禁止です。
- 実行の外側から取得される成果物を出力する場合は、プラットフォームの標準 API と標準 CLI から列挙・取得できる保管先に置きます。
- 外部から参照される成果物の集合を定義する場合は、次のとおりです。
  - 1 箇所で定義します。
  - 確認と文書、または複数の一覧に同じ集合を持たせることは禁止です。

この節が足すのは、外部へ出す操作の側でもその分離と宣言が同じように要るという条件だけです。

## 機械がどこまで判定するか

境目は重要度ではなく、判定に要る材料がどこにあるかです。材料がリポジトリの中に閉じていて、基準が構文の形か、2 つの表現を比べて決まるものは、機械が判定する。どの機構を主たるガードにしたか、選ばなかった候補を記録に残したか、置いたガードが違反を仕込んだ入力で実際に落ちるかは、材料が「なぜそう決めたか」の側にあるので残る。ある規律に対応する確認が有効かどうかは、そのつど設定の側を見て確かめる。

- レビューで見る項目を、その主題を所有する規範文書に置きます。
- 人が見る項目だけを横断的に集めた置き場所を作ることは禁止です。
  - 所有者の決まっていない項目の受け皿にもなり、何を入れてよいかに答えられない置き場所として膨らむ
- レビューで見る項目に出会うたびに、これは本当に機械化できないのかを問い直すこと。
