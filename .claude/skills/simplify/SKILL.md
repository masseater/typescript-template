---
name: simplify
description: このプロジェクトにおいて、複雑化したコードをシンプルに実装するための指針が書かれている。作業完了前に参照し、この指針通りに実装できているかを確認すること。
---

表面的な部分だけでなく、各 workspace の中まで含めて以下の基準に基づいてチェックすること。

- 全てはコロケーションすること。実装、ドキュメント、設定、テスト、その他全て、実際に使われる場所に近接して配置すること。
- パッケージを分離する粒度は再利用性の観点で決めること。分離するという行為はコロケーションの原則に反するため、本当に再利用する場合のみ分離すること。
- 型レベルでの安全性を確保すること。
- 既にあるものを活用すること。自前実装を最小限にすること。自前実装を避け、既存のライブラリやフレームワークを活用すること。es-toolkit を活用すること。
- 複雑な if, switch を避けてバリデーションライブラリを活用すること。
- 場当たり的な変更を避けて、設計レベルの変更をするべきでないかを検討すること。
- 後方互換性を残さないこと。
- ハードコードは避けること。同一概念を複数の場所に配置しないこと。どうしてもしなければいけない場合は、定数化して共有すること。
- package.json に無駄な export を増やさないこと。
- package.json の scripts に置いてよいのは、dev, preview, build のようなライフサイクルコマンドと、deploy, migrate, bootstrap のように人が手で実行する運用コマンドのみ。検査は workspace の scripts に置かず、ルート vite.config.ts の check タスクに統合すること。ルートに定義するコマンドは、リポジトリ全体や特定の workspace 単位全体に関わるコマンドのみ。
- 設定ファイルは基本的に大本の設定に従うこと。各 workspace ごとの設定は必要最小限にすること。
- ライフサイクルの外で手動実行を前提とする独自スクリプトを作成しないこと。準備は prepare に、検査は check に、成果物の生成は build に載せ、アプリの起動時や終了時、ビルド時など、ライフサイクルに自然に実行される形にすること。
- 関数・クラスの引数として呼び出すためだけの型・インターフェースを定義しないこと。
- 引数を軽く整形して一部のオブジェクトだけを抜き出したような、無駄な関数を定義しないこと。
- hooks, CI, ドキュメント、他のタスクから "vp run check:client", "vp run check:layers" のように個別の検査を列挙して呼ばないこと。列挙すると漏れる。呼び出し側は vp run check だけを呼び、個別の検査はルート vite.config.ts の check タスクの command 配列からのみ呼ぶこと。同じコマンド列を複数箇所に書かざるを得ない場合は、一致をテストで固定すること。
- node で直接ファイルを実行することは避けること。vp のタスクランナーに乗っかって実行すること。
