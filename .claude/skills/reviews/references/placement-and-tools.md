# 置き場所とツール

機械が見る分は `docs/lint-rules-by-guideline.md` の placement-and-tools の節にある。ここに書くのはその外だけ。区分の内側の配置は `./colocation.md`。

## 外に出る面

- 取り込まれるパッケージの責務は 1 つ。公開するサブパスはその責務の内側に収める。サブパスを分けたことを影響範囲が縮む根拠にしない。影響は workspace 間の依存の辺で判定される。
- 取り込まれるだけのパッケージにコマンドの起動口を足さない。責務の外の実行体が要るなら、起動口とその依存を実行体を所有する別の workspace へ移す。
- 1 つのパッケージに両方の面を持たせるなら、2 つの面が同じ責務の別の現れであること（`@repo/db` のスキーマと migration の適用）と、それぞれに実際の利用者がいることを示す。
- 薄いラッパーや別スクリプトを経由して、閉じている面に到達させない。

## 共有に踏み切る条件

- コードの切り出しは、実際に取り込む workspace が 2 つ以上になってから。取り込み元が 1 つに減ったら、残った 1 つの内側に畳み直す。
- 所有者も呼び出し元も 1 つの workspace に閉じるスクリプトはその内側に置いてよい。呼び出し元が 2 つ目になったら（CI から呼ばれ始めた時点を含む）workspace が所有するコマンドに移す。
- 取り決め（共有 tsconfig のプリセット、確認が読む語彙と閾値の既定値）に実行できる実装を入れない。取り決めはそれが記述している領域で束ねる（`tsconfig.base.json`）。
- 1 つの workspace にしか関係しない設定を共有の取り決めに置かない。既存のどの領域にも当てはまらない取り決めは、何を所有するかを名前にした新しい置き場所を作る。近いという理由で相乗りさせない。
- 取り込む側の 1 つだけが持つ制約のための回避策は、制約を持つ側に置く。供給側を全員ぶん変えない。

## 置き場所は届く相手で決める

誰に届くか、失敗したとき何が止まるか、単独で起動と停止ができるか、取り込まれるのか実行されるのか、で決める。実装の見た目（起動口を持つ、サーバーが立つ）で決めない。

順に照らし、最初に当てはまった区分で確定する。

1. パッケージが所有する Worker の Alchemy Stack。そのパッケージの `alchemy.run.ts`
2. 複数の適用単位が共有し、単独の Worker パッケージに属さない外部資源の宣言。`infra/`
3. デプロイされて外部の利用者からの要求を受ける実行対象。`apps/`
4. 複数の workspace が取り込む共有物。`libs/`
5. 上のどれでもないもの。それを使っている既存の workspace の内側

- Worker を所有するパッケージの Stack を `infra/` に移さない。
- 既存の区分に収まるものに並列のトップレベルを作らない。どの区分に入れても定義が偽になるときだけ区分を増やし、その前にどの区分も所有しないことをコミットログに残す。
- 中身の無い区分、整理されて見えることや今後増えそうなことを根拠にした区分を作らない。
- 残余の区分に置いたものは、所有者が未定の印として扱い、増えたら区分を増やすか所有者を決めて減らす。迷ったものの既定の行き先にしない。

## ツールは対象の構造で選ぶ

- ソースコードの書き換えは構文木の上でノードを編集し、整形を壊さない層を入力にする。読み取りは公式コンパイラの構文木を入力にする。行やパターンのテキストマッチで構文を判定しない。範囲が小さくても同じ。
- 依存に型付きの API があるならそれを使う。実行ファイルしか無いなら、自分が所有する型付きの薄い層で包み、出力を検証してから渡す。素の子プロセス呼び出しを呼び出し箇所に置かない。
- 外部サービスへのアクセスは、リトライ・応答の解釈・認証を 1 つの型付き境界に集める。
- 外部サービスの設定は Alchemy の宣言に書く。管理画面の手作業やその場限りの API 呼び出しで済ませない。公式ドキュメントに無い API しか無いなら dynamic provider を書く。

## 版の出どころ

- ツールの版は、宣言的に固定でき、プロセスの環境へ 1 度だけ注入できる機構に寄せる（`package.json` の `packageManager` と `devEngines`、`mise.toml`）。
- 活性化を所有する境界が既にあるかで、環境を用意する側か継いだ側かを決める。継いだ側は継いだ環境からそのまま呼び、活性化を重ねない。用意する側（対話的なシェル、フック、自動実行の準備）は 1 度だけ活性化する。

## 起動口とコマンドの単位

- 実行可能物は所有するパッケージを 1 つ決める。ルートから呼べるようにするときは所有パッケージへの薄い委譲だけを置く。
- 置き場所を外の仕組みが決める起動口（git フック）には、workspace が所有するコマンドの呼び出しだけを置く。確認の中身を実装しない。
- リポジトリのルート直下に自動化の実装本体を置かない。
- テストからしか到達しない口を作らない。
- 手元・フック・自動実行から同じ処理を呼ぶときは、同じ呼び方が通る状態を保つ。手元の確認と CI が同じまとまりを起動することを、片方からの導出か、ずれを機械的に落とす形で保つ。
- 個別に呼ぶコマンドは、落ちたときに守られていない不変条件と直す方向が 1 つに決まる単位にする。まとめて実行する起動口は個別のコマンドを並べたものにし、1 つに統合しない。

## 呼び出し側に選ばせる値

- オプションにするのは呼び出し側が本当に選ぶ値だけ。コマンドの目的から一意に決まる値をオプションにしない。
- 実行時の文脈から取れる値は、その文脈を読む境界で受ける。手元と自動実行の差も文脈から導き、モードのフラグや自動実行専用の複製したスクリプトで表現しない。
- 別の戦略を選ばせるなら目的ごとのサブコマンドにする。
- 秘密の値は保管先のキーやパスという参照で受け、値そのものをオプションで受けない。

## 使い方の記述

- 受け付ける引数と表示される使い方を同じ変更で揃え、変えたら実際に実行して確認する。
- 値を取るオプションは、値の形と指定しなかったときの実際の値を読める形にする。
- コマンドの説明は目的を述べる 1 文。手順や環境の説明を詰め込まない。

## 標準出力と診断

- 別のプログラムや AI が消費する標準出力は結果だけで構成する。途中経過・デバッグ・進捗は別の系統に出す。
- 子プロセスを包むコマンドが自動実行の中で動くなら、子の出力を捨てずに記録へ流す。
