---
name: simplify
description: このプロジェクトにおいて、不要な複雑さを減らし、既存の仕組みを活用してシンプルに実装するための指針。
---

表面的なコードだけでなく、各 workspace 内のコード・設定・タスク構成まで確認する。

## 基準

- 型で表現できる安全性を、実装時の分岐や手動チェックで代替しない。
- 既存のライブラリ・フレームワーク・リポジトリの仕組みを優先し、自前実装を増やさない。ユーティリティには `es-toolkit` を活用する。
- 複雑な `if` / `switch` を増やさず、既存のバリデーションライブラリや型で表現する。
- 場当たり的な修正で複雑さを増やさず、必要なら設計・責務・データ構造から変更する。
- 後方互換性のためだけの分岐・ラッパー・旧 API を残さない。
- 単一コマンドにまとめる。check:hoge, check:fuga -> check。選択肢は不要。
- ファイルパスや正規表現による脆弱なマッチングを避け、より直接的に対象を識別する。
- 同じ概念や値を複数箇所に定義しない。共有する必要があるものは一箇所を正とする。
- 引数の受け渡しや一部の値の抽出だけを目的とした関数・型・インターフェースを増やさない。
- workspace 固有の export・コマンド・設定を必要以上に増やさない。リポジトリ全体で扱う処理はルートに集約する。
- workspace の設定は既存の共通設定を継承し、固有設定は必要最小限にする。設定・構成管理については [関連 skill] を参照する。
- 手動実行を前提とする独自スクリプトを増やさず、起動・終了・ビルドなど自然なライフサイクルに組み込む。
- 個別の検査タスクを列挙して実行せず、既存の集約された check タスクを利用する。
- `node` で直接ファイルを実行せず、`vp` のタスクランナーに乗せる。
- 同じコミットの品質判定が、作業コピーや実行ホストの状態によって変わらないようにする。

## 判断

**変更によって複雑さが減るか、既存の仕組みで置き換えられないかを確認する。**

同じ概念を複数箇所に持つ、既存機能を再実装する、例外のための分岐を増やす、手動操作を増やす変更を避ける。
