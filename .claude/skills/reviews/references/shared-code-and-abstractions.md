# 共通化と抽象化

## 共通化してよい条件

- 共通化するのは、目的が同じで、片方を変えたらもう片方も同じに変えるべきものだけ。コードの形が同じでも目的が違えば別々に書く。
- 関数・型・コンポーネント・基底クラスの共通化は、同じ目的で使う 2 つ目の呼び出し元が今あるときに行う。将来の再利用を見込んで先に作らない。
- 共通化した側には、目的を言い当てた名前を付ける。`common`・`utils`・`helpers`・`shared`・`base`・`manager` のようにしか呼べないなら、目的の違うものが混ざっている。

## 過剰な共通化の兆候

- 値が呼び出し元の名前や用途に対応している引数がある（`isAdmin`、`fromCheckout`、`type: "invoice" | "receipt"`、特定の呼び出し元だけが渡すオプション）。
- 特定の呼び出し元のためだけの分岐や早期 return がある。
- 1 つの呼び出し元の要件のために共通の側を変えると、他の呼び出し元の振る舞いやテストが変わる。
- 基底クラス・共通の hook・共通のコンポーネントに、一部の利用者だけが使う処理がある。
- 共通の側のテストが、どの呼び出し元も使っていない引数の組み合わせを検証している。

## 直し方

- 兆候を見つけたら、中身を各呼び出し元へ戻し、その呼び出し元が通らない枝と使わない引数を消す。残った一致のうち目的が同じものだけを寄せ直す。
- 引数・オプション・分岐を足して共通の側を延命しない。
- 継承を処理の使い回しに使わない。
- 共通化を解くときは、共通の側にだけあったテストを、各呼び出し元の観測できる振る舞いのテストに移す。
