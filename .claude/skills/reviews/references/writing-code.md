# コードの書き方

ここに書くのは lint が判定できないものだけ。

## 外部 I/O とその境界

外部 I/O は、値がこのリポジトリのロジックの外側で決まる入出力。所有者は `libs/config` の環境変数スキーマと `libs/runtime` の HTTP / Worker 契約。それ以外の依存はプロセス内の決定的な振る舞いとして扱う。

- ロジックから外部 I/O を直接呼ばない。このリポジトリが所有する注入境界を経由する。
- 注入境界は、外部 I/O の位置にあるか、テストではない呼び出しが今あるときだけ足す。
- 外部 I/O の注入境界は、向こう側を差し替えたときにこちらの分岐を全部通せる大きさに保つ。
- 存在が任意のパスは読む前に不在を判定する。読み取りの失敗をすべて不在として扱わない。
- 存在が任意のディレクトリの下に書くときは、書く前にディレクトリを用意する。
- 環境変数は `libs/config` の型付きの `env` を経由する。`process.env` を直接参照しない。

## 外から入った値

- 外から来た値は、入ってくる境界で内側の型に移す。使う場所ごとに形を確かめない。
- 境界で形が合わなければ失敗にする。
- 1 つの判定を 2 つの概念に使わない。今構造が一致していても概念ごとに判定を定義する。
- 判定を通った形の静的型と、フィールドの意味は、判定の定義から導出する。
- 省略可能にするフィールドには、実際に欠ける場面を挙げる。挙げられないなら必須にする。文脈ごとに形が変わるなら文脈を決める値を先に読み、全文脈を 1 つの判定に畳まない。
- 判定を書く手段はリポジトリで 1 つに保つ（`libs/config` が使う Effect Schema）。その外で条件を並べた確認を書かない。

## 型が言えること

- その場で使える中で最も精密で健全な型を保つ。不正な状態は型で表現不能にし、呼び出し側の規律に頼らない。
- 引数と戻り値の契約はシグネチャを唯一の出所とし、外で要る型はそこから導出する。構造だけ同じ型を並行させない。
- 型チェックが導けない型として扱うときは、値を実際に確かめる確認を同じ境界に置き、通った値だけを主張の対象にする。中身が値を見ないアサーション・型述語・表明で拒否を消さない。
- 実行時のモジュールとして取り込む依存は、モジュール形式が消費側と噛み合うことを確かめる。型解決が通ったことを実行時に読める証拠にしない。

## 既にある定義の上に書く

- 振る舞い・ルール・値に所有者がいるなら再利用するか拡張する。等価なものをその場に作らない。
- 既製のライブラリにある処理を自前実装しない。既製の関数を包み直すだけのラッパーを作らない。
- 欠陥は、それを所有している境界で原因を直す。外側の分岐や迂回を修正として残さない。
- 同じ規約を複数の書き方で表現できる状態を見つけたら、型・境界・自動の確認を締めて通る書き方を 1 つにする。文書に書いて終わりにしない。

## 失敗

- 予期した失敗と予期しない失敗を、呼び出し側がコードから区別できる形にする。失敗の伝わり方をリポジトリで 2 通り持たない。
- 予期した失敗と外へ出す報告の同一性は安定した識別子（報告の識別子、実行環境が付ける `code`）が持つ。メッセージ本文の一致で判定しない。
- 下位の失敗を包むときは元を `cause` に保持する。文言だけ取り出して元を捨てない。
- 捕まえた失敗を書き出したら、止めるか、失敗したと分かる値を戻す。別の綴りへ移したり包む関数を挟んだりして、握り潰しの検出から外さない。

## 名前

- 受け付ける形を呼び出し側へ伝える位置には、形が判別できる情報を置く。名前の言い換えを置かない。
- 有限の語彙は型で表す。散文だけで伝えない。
- 綴りを外で決められた値（外部サービスの識別子、環境変数の名前）は、決めた側を名前に含め、決められた綴りのまま参照する。言い換えた語を発明しない。決めた側を特定できるまで名前を付けない。

## 取り込まれる面

`tools/ai-native`・`tools/ai-native-telemetry`・`tools/dont-review-it` は npm へ公開する形（`publishConfig`）を保つ。workspace 間の import 面も同じ重さで扱う。

- 既に公開しているものと取り込み側が依存している契約から導出できるものを足さない。
- 公開エクスポートを変えるときは、エントリと消費側を同じ変更で更新する。
- インターフェースに口を足すときは、テストではない呼び出しを今示す。将来の見込みは利用者ではない。
- テストからしか import されない export は消す。消せなければ、利用者が通る呼び出し越しに検証する形へ書き換える。

## 実行が外へ出す面

- 特定の利用者向けの面は、載せる事実と粒度を選んでよい。利用者側の見せ方までは決めない。見せ方を契約に載せない。
- 終了コード・状態コード・報告の書式・利用者向け文言への変換は、ちょうど 1 箇所の境界で行う。失敗そのものに外向きの表現を持たせない。
- 解決に利用者から到達できない状態が要る値は、解決した後の値を載せる。

## コードの傍に残したい記述

- 現在の姿は識別子・型・テストで表す。どれでも表現できない不変条件は、それを所有する reference に置く。
- 判断の根拠は、その判断と同じ変更の単位に入れる。複数の判断の根拠を 1 箇所へまとめない。作業中に分かったことは、分かった制約の側を書き、どう気付いたかは書かない。
- なぜそうしているか分からない記述は `git log` と `git blame` を読む。意図を推測したまま変えない。

## 生成器が吐くコード

- 生成器には意味のある出力だけを担わせ、体裁の正規化はフォーマッタに任せる。
- 再生成した出力とコミット済みの出力を比べる前に、両方を同じ整形で正規化する。

## 判断が割れたとき

- 拡張点を先に用意したい要求より、今の呼び出し元を示す規則を採る。
- 失敗を表に出すことと代替値で続けることでは、表に出す側を採る。
- 単一の定義とテストの読みやすさでは、独立した仕様どうしに単一の定義を当てない側を採る。
- 記録の完全性と機微な値を落とすことでは、落とす側を採る。
- 記録の流れを一本に保つことと記録を増やすことでは、一本に保つ側を採る。
- 決められないときは後から戻せる側へ倒す。検証を足す、名前を付けずに保留する、注入境界を足さない、必須にする、公開面に載せない。
