# 外部 I/O の境界と型

## 外部 I/O とその境界

- 外部 I/O として扱うのは、値がこのリポジトリのロジックの外側で決まる入出力だけ。それ以外の依存は、プロセス内の決定的な振る舞いとして扱う。
- ロジックから外部 I/O を直接呼ばない。このリポジトリが所有する注入境界を経由する。
- 注入境界を足すのは、外部 I/O の位置にあるか、テストではない呼び出しが今あるときだけ。
- 外部 I/O の注入境界は、向こう側を差し替えたときにこちらの分岐をすべて通せる大きさに保つ。
- 存在するとは限らないパスは、読む前に不在を判定する。読み取りの失敗をすべて不在として扱わない。
- 存在するとは限らないディレクトリの下に書くときは、書く前にディレクトリを作る。
- 環境変数は `libs/config` の型付きの `env` を経由する。`process.env` を直接参照しない。

## 外から入った値

- 外から来た値は、入ってくる境界で内側の型に変換する。使う場所ごとに形を確かめない。
- 境界で形が合わなければ失敗にする。
- 1 つのスキーマを 2 つの概念に使わない。今は構造が一致していても、概念ごとにスキーマを定義する。
- スキーマを通った値の静的型と、フィールドの意味は、スキーマの定義から導出する。
- フィールドを省略可能にするときは、実際に欠ける場面を挙げる。挙げられないなら必須にする。文脈ごとに形が変わるなら、文脈を決める値を先に読み、全文脈を 1 つのスキーマに畳まない。
- スキーマは Effect Schema だけで書く。その外で条件を並べたチェックを書かない。

## 型が言えること

- その場で使える中で最も精密で健全な型を保つ。不正な状態は型で表現できない形にし、呼び出し側の規律に頼らない。
- 引数と戻り値の契約はシグネチャに書き、外で要る型はそこから導出する。構造だけ同じ型を並行して持たない。
- 型チェックが導けない型として扱うときは、値を実際に確かめるチェックを同じ境界に置き、通った値だけを対象にする。中身が値を見ないアサーション、型述語、表明で拒否を消さない。
- ランタイムのモジュールとして取り込む依存は、モジュール形式が消費側とかみ合うことを確かめる。型解決が通ったことを、ランタイムで読める証拠にしない。
