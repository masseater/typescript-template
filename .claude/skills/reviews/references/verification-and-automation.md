# 検証と自動化

## 実行されなかったチェックを成功に数えない

- 通過条件として数える実行は、起動した後の段階で絞り込む。起動そのものの条件で絞り込むと、落ちたのか実行されなかったのかを通過の記録から区別できない。数えないと確定できた実行だけ、起動の条件で絞ってよい。
- チェックや適用の失敗はそのまま伝播させる。暗黙のスキップ、握り潰し、継続許可で成功に読み替えない。
- パイプの途中の失敗が終了コードに現れる設定であることを確かめる。
- パッケージ内で閉じる品質作業の対象は、依存グラフとキャッシュを持つタスクランナー（`vp run`）に選ばせる。その前段に別の絞り込みを重ねない。
- 段取りの記述だけが変わったときに対象を広げない。依存構造そのものが変わり、局所化してよいか判断できないときは広げる。
- 走査範囲は、配布物に入るコードの実際の配置に追随させる。
- キャッシュ再利用のデフォルトをまとめて切り替える設定（各 workspace の `vite.config.ts` の `tasks` と `package.json` の `scripts` に及ぶ）は、及ぶ定義を数え上げて 1 つずつ確かめてから書く。
- ファイルを変更するタスクと常駐プロセスを起動するタスクを、キャッシュ再利用の対象にしない。常駐はランナーに宣言する。
- デフォルトの入力集合を自分で書いた集合で置き換えるときは、その workspace の実際の入力をすべて数え上げる。

## ガードが落ちることを確かめる

- ガードを足したら、違反を仕込んだ入力でレポートが出ること、違反でない入力で出ないことを確かめる。設定に存在することを、検出できている証拠にしない。
- ガードをすり抜けた違反を見つけたら、コードを直し、落ちるべき入力にその抜け道を足す。
- レポートには、破られた不変条件と直す方向の両方を含める。
- 自動修正を用意するのは、安全で決定的な直し方がちょうど 1 つに定まるときだけ。自動修正が安全に終えられない部分は、失敗するガードとして残す。

## 何を守れる仕組みかで選ぶ

- 1 ファイルの構文で決まるものは型と lint、実行して分かるものはテスト、複数ファイルの突き合わせは検証コマンド、宣言と外の状態の突き合わせは `alchemy plan` で見る。どれにも載らないものだけレビューで見る。
- 根拠を残したことを強制とみなさない。
- 不変条件の全体を確実に守れる仕組みを主たるガードにする。一部しか守れない仕組みを主にしない。同じだけ守れるなら、失敗が返るまでの距離が短いほうを採る。
- 不変条件が振る舞いと実行時の境界を通る値の両方に掛かるなら、両方に届く仕組みを置く。
- 既に表現できるガードがあれば、設定するか拡張する。並行する検出器を作らない。
- 仕組みを選んだ理由と、選ばなかった候補で守りきれなかったものをコミットログに残す。ガードの実装や設定だけに残さない。

## チェックが保証している範囲

- チェックが通ったことを、そのチェックが見ていない性質の保証にしない。
- チェックが届かない側の判断を省かない。届かないのは、実装と文書のずれ、型の契約と実行時の契約のずれ、宣言と外の状態のずれ、2 つの側が出会う場所だけに現れる食い違い。

## ガードを入れる時点

- 基準が決まっていて、機械的に検出できる違反が予見できるなら、基準を導入する変更か最初の違反を直す変更でガードを入れる。2 回目を待たない。
- 議論が決着していないものは自動化せず、拘束力のある散文としても書かない。
- レビューで人が毎回同じ判定をしている項目を機械が評価できるなら、ガードに置き換え、レビュー項目からは消す。

## 強制度を落とすときの形

- 既存の違反があってすぐに全体を強制できないときは、落とす範囲を個別に名指しした既存のファイルに限る。パターン単位で落とすなら、その判断と何が守られなくなるかをコミットログに残す。
- 継続許可を付けるときは、その段階を通過条件として数えないことと、代わりに何が見るのかを同じ変更で決める。一時措置のまま放置しない。
- 解消済みの違反に残った抑制は、違反と同じ扱いで落とす。
- 一時的に落とした強制度は、違反が解消した変更で戻す。

## main に入る手順

- main に変更が入る手順は、ブランチを push して PR を merge する 1 つだけ。手順ごとに別のチェックの集合を持たない。
- 通過条件を迂回できる形が残るなら、迂回したことを出力で見える状態にする。
- 通過条件の有無が手元の設定に依存するなら、依存のインストール手順（`package.json` の `prepare`）が毎回書き込む形にする。
- `--no-verify` で手元のフックを飛ばさない。

## 実行の定義に書いてよいもの

- `package.json` の `scripts` にはコマンド名と 1 本の呼び出し、各 workspace の `vite.config.ts` にはタスクの依存、キャッシュ、入出力、`.vite-hooks/` にはエントリポイントと呼ぶコマンドだけを書く。
- 実行ブロックは 1 つのコマンド呼び出しに留める。再試行、繰り返し、分岐、エラー処理、対象探索が要るなら、型と自動テストを持つリポジトリ内のコードへ移す。
- 同じまとまりが定義ファイルの中で増えたら、単一のまとまりへの参照で解消する。順序を持つ手順の並びなら、再利用できるまとまりへ切り出す。

## 源と生成物

- 源から決定的に導ける成果物は生成して得る。生成物を直接編集しない。1 つの生成物に 2 つ目の生成手順を作らない。
- コミットする生成物は、源の変更と同じ変更に入れ、ずれを機械的に検出する手順を付ける。
- 触る出力を所有する自動化があるなら、先に実行して出力を全部読む。終了コードだけで通ったとみなさない。
- 自動化が対応していないことを、不変条件を外す理由にしない。
- 生成器には意味のある出力だけを担わせ、体裁の正規化はフォーマッタに任せる。
- 再生成した出力とコミット済みの出力を比べる前に、両方を同じ整形で正規化する。

## 機械だけが読み書きする成果物

- パスだけを根拠に機械向けと分類しない。人も読む文書は人間向けとして扱う。
- 人間に対して拘束力を持つ内容をここに置かない。人間向けの規則がここを基準として指さない。同居していたら、主題を所有する reference へ移す。
- 機械にとっての有用性と構造の妥当性で評価する。散文の質を理由に差し戻さない。
- 形式を所有するツールがあるなら、作成、更新、改名、削除をそのツールで行う。Alchemy の state を手で書き換えない。
- 保守の時点は使っている側の必要に任せる。固定の周期や人間側の工程にひも付けない。

## ワークフローとジョブを分ける軸

- 自動化を分ける軸は、起動のタイミングとライフサイクルにする。機能名、パッケージ名、担当領域で分けない。名前も、タイミングかライフサイクルが読める名前にする。
- 起動のタイミングが独立していて、失敗したときに巻き込む先が他と揃わない自動化は、独立したワークフローに置く。同居させると、一部のために宣言した広い権限を全部が常に持つ。
- 複数のワークフローから使うまとまりは、呼び出す側にトリガを持たせる。
- 互いの結果を参照し合う処理は、同じジョブに置く。

## 外へ出す操作

- 外部状態は、レビューを経たリビジョンから自動化された手順で変える。手元の作業ツリーから実行しない。
- 特定の成果物を前提にする操作は、変える前に成果物の同一性を確認する。生成から消費までを 1 つのまとまりとして扱い、消費側だけが選ばれる手順を残さない。
- 外部状態を変える操作と外部に問い合わせるチェックには、明示的な対象集合を与える。
- 品質作業か外部への副作用か判別しづらいものは、副作用として扱う。
- ソースを取得する権限は読める範囲を絞り、外部に書き込む権限はジョブが宣言した権限としてその実行に帰属させる。
- レポートは、生成したコマンド自身が単一の手順で、決まった報告先に出す。生成と報告を分けない。複数の先から同じ報告先を書き換えない。
- 実行の外側から取得される成果物は、プラットフォームの標準 API と CLI から列挙・取得できる保管先に置く。
- 外部から参照される成果物の集合は、1 か所にまとめて宣言する。

## 機械がどこまで判定するか

- レビューで見る項目は、その主題を所有する reference に置く。人が見る項目だけを横断的に集めた置き場所を作らない。
- レビューで見る項目に出会うたびに、機械化できないかを問い直す。

## 変更量を理由にした例外

- 変更量、ファイル数、変更範囲を理由に、lint、typecheck、test、build、security check の対象を減らさない。「変更が多い場合はスキップ」「大量変更は対象外」といった allowlist、denylist、しきい値を作らない。
- 特定のファイル、workspace、feature を、変更量や対応コストを理由にチェックの対象から外さない。
- 既にある allowlist や例外は必要性を確かめ、不要なら削除する。必要でも、変更量を理由にした恒久的な回避にしない。
- 検証量が問題なら、対象を削らずに task graph、依存関係、cache、並列実行で効率化する。大規模な変更自体がボトルネックなら、計測して原因を特定してから改善する。
- 判断は「その例外がなければ、どのチェックを本来実行すべきか」で決める。変更量以外に仕様上の理由がない例外は削除する。

## 設定の上書きと除外

- 設定を変えるときは、その上位や共通の設定と比べる。
- `include` より `exclude` を基本にし、新しい対象を追加したときに意図せずチェックの対象から漏れる構成を避ける。
- 既存の設定を上書き、無効化、緩和、除外する設定を残すのは、なければどの制約が破れるかを言えるときだけ。説明できないものは削除し、既存の制約を維持するようにコードや設定を直す。
- 適用範囲はできる限り狭くする。共通設定で解決できるものを、workspace 固有の設定で上書きしない。
- 緩和のために別の設定や例外を足して帳尻を合わせない。
- デフォルト値と同じ値を書かない。
- 直した後、関連するチェックを実行する。

## 実行段階の分担

- precommit: 毎回実行しても負担にならない静的解析。重いテストやビルドを載せない。
- prepush: 変更とその影響を受けるテスト、typecheck、build。影響範囲は task graph と依存関係から求め、全体を毎回実行しない。
- prepr: PR の変更と影響範囲に対する lint、typecheck、test、build。`.github/workflows` の `paths` / `paths-ignore` で制御せず、task graph から影響範囲を求める。全体の重い統合テストを PR ごとに実行しない。
- premerge: 統合後でなければ検証できないもの（integration、E2E、全体回帰）。必須チェックとして扱える構成にする。
- 各段階で同じ検証を重ねてよい。CI 上で独立して品質を保証できる構成にする。
- task cache、dependency cache、remote cache で不要な処理を繰り返さない。独立した task は並列実行する。
- 高速化のためにチェックの対象を削らない。同じコミットの品質判定が、作業コピーや実行ホストの状態で変わらないようにする。
- 改善するときは、実行時間と実行量を計測してボトルネックを特定してから手を入れ、改善後に再計測する。ボトルネックでない処理を推測で最適化しない。

## 判断が割れたとき

- 自動化が所有する変換を実行することと手で編集することでは、実行する側を採る。
