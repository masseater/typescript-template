# 秘密と権限

秘密は、持っていること自体が「誰かとして振る舞ってよい」根拠になる値。接続先のアカウントを名指しする識別子も同じに扱う。機械が見る分は `docs/lint-rules-by-guideline.md` の secrets-and-permissions の節と、`.vite-hooks/pre-commit` が起動する `precommit` の確認（平文の環境変数ファイル、非公開ディレクトリの混入、決まった形の資格情報、デプロイ用の秘匿値と同じ文字列）にある。ここに書くのはその外だけ。

秘密が動く場所は、開発者の手元（`apps/<app>/.dev.vars`）、Workers の実行環境（secret binding）、Cloudflare の Secrets Store、Alchemy の state store の 4 つ。

## リポジトリに置かない

- 資格情報は、実行を起こした側から実行時に渡ってくる形にする。
- 秘密の値を平文で追跡ファイルに書かない。一度コミットに入れば履歴から読める。
- 開発用の値は追跡しない `apps/<app>/.dev.vars` に生成し、生成を実行できる形で持つ。暗号化したものも追跡ファイルに置かない。
- 設定に書き留めるのは保管先の指し方だけ。
- 文書やテストに資格情報の形をした値が要るなら、どの相手にも通らないと読み取れる値を選ぶ。
- 本物の資格情報が平文で入っていたと分かったら、値を使えなくしたうえで、いまの内容からも公開済みの履歴からも取り除く。
- 探す仕組みを広い範囲の除外で止めない。誤検知は根拠を同じ変更に添えて、その 1 件だけ外す。

## 出力に通さない

出力は標準出力と標準エラー、HTTP の応答、Workers Observability へ送るもの、`alchemy plan` の差分。

- 秘密の値そのものと、個人を名指しできる値を出力に載せない。存在や形だけ残したいなら復元できない形にする。
- Alchemy の宣言では secret として宣言し、`plan` の差分に平文が現れない形にする。値そのものを宣言の入力に書かない。
- 機微な値を取り除く層は定義を 1 つに保ち、どの出力先へ届く前にも経由させる。機微なキーを増やすときは同じ変更で定義に載せる。出力先ごとに取り除く処理を書き足さない。
- キーで分けられない塊は、量や種別のような外形だけを出す。

## 読める主体を、読んでよい主体に一致させる

- 置き場所を選ぶときは、そこから読み出せる主体をすべて数え上げる。置き場所を分けたことだけで狭まったとみなさない。Worker の `secret_text` binding は API から値を返さず、`plain_text` は Workers Scripts を読める主体なら誰でも読める。
- 継承で広い権限を持つ主体が読んでよい側に無いなら、明示的な拒否で止め、例外は読んでよい主体だけに限り、拒否が機能していることを例外側の資格情報で確かめる。
- 読み取りを記録する必要があるなら、保管先の監査ログを有効にする。
- 読み出せない主体だけが知っている値は宣言の管理下に入れず、入れる主体と手順をその領域を所有する文書に書く。
- 作成時にしか読み出せない資格情報を宣言が発行するなら、実値を持つ state store をその資格情報と同じ扱いで守る。`alchemy provider cloudflare teardown` で state を消すと実値はどこからも読み出せない。

## 実行が持つ権限を宣言に限る

- 実行単位ごとに要る権限だけを宣言する。実行基盤が初めから渡す権限をそのまま受け取らない。確認が通らないことを理由に広げない。
- 外部サービスへ機械が接続するときは、OIDC の federation、短命の資格情報、鍵なしの連携の順に探し、公式ドキュメントと実際の API の応答で確かめる。どれも無いと確認したときだけ API トークンを使い、リポジトリの外の owner だけが読める場所に置いて指し方だけを設定に書く。トークンをリポジトリ・ワークフロー定義・環境変数ファイルに置かない。
- 承認や隔離を迂回する仕組みは既定を無効にし、起動時に確かめられる明示の指定があるときだけ有効にする。

## 変更を起こす口は、その地点で判定する

- 口を新しく開く、または広げるときは、変更が実際に起きる地点で対象と操作を確かめる。呼び出す側で済んでいるものとして省かない。
- 誰として要求したかを確かめる仕組みを通過した事実だけで変更を認めない。
- 判定の正しさを機械で確かめられない手順は、人が読んで確かめる側へ回す。
- 保護された環境を資格情報を持たない主体に開けるときは、保護を残し、迂回する手順を主体ごとに分けて発行する。

## 確認を通っていないコードの手が届く範囲

- CI が取り出したリビジョンが動く場所に置く資格情報は、用途を絞り、選べる期限のうち最短にする。作る処理はそのコードが動く場所の外で実行する。取り出す操作が資格情報を作業ツリーに残さない設定であることを確かめる。期限の長い鍵を残さない。
- 差分のために並べて取り出したリビジョンも、確認を通っていないコードとして扱う。
- 途中で起動する処理に認証が要るなら、どの資格情報を使うかを呼び出しに書いて渡す。周囲のログイン済み状態をあてにしない。

## 資格情報は目的ごとに分ける

- 触る対象と操作の範囲に収まる資格情報を、最短の期限で使う。
- 相手が通してしまうことを理由に、発行した目的の外へ回さない。Alchemy が管理 API を呼ぶキーと、アプリが機能のために使うキーは別に発行する。
- 複数の実行単位で共有するときは、失効させたときに止まる範囲を数え上げる。数え上げられないまま共有しない。
- 自動化がリポジトリを書き換えるときは、その自動化のために発行した資格情報を使う。個人に紐づくトークンを定常的な手段にしない。
