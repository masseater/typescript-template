# 拘束力のある文書

## 書く前にオーナーを探す

- コード、型、設定を読めば確かめられることを文書に書かない。
- workspace、依存、コマンド、パスの一覧は、それを所有する定義を参照させる。手で並べない。
- 機械が判定できることは、判定する側をオーナーにし、その判定と直し方を文書にコピーしない。判定できる部分と意味的な境界が同居する規則は、判定できる部分をチェックに移し、残りだけを文書に置く。
- まだない仕組みを前提にする規則は、いつ機能し始めるかを冒頭に書く。対象がないことを隠さない。
- どの仕組みを持ち込んでも判断を変えない一般論を書かない。
- 繰り返し起きる誤りは、機械が判定できるならチェックを実装する。最後の一線を機械が判定できないときだけ書く。

## 1 つの概念にオーナーは 1 つ

- 同じ概念を定める記述が 2 つの文書にあるなら、所有する文書を 1 つ選び、他方は消すかリンクだけ残す。別の文書が所有する概念を、言い回しを変えて書き直さない。
- 別々に書かれた 2 つの条件をまとめる前に、一方だけが成立する場面を挙げられるか試す。挙がったら別のまま残す。
- 文書どうしの対応を、手で維持する識別子や対応表で作らない。
- 広い規則の一部にだけ別の行動を取らせるときは、どちらにも当たる入力が残らないところまで条件を分け、狭い側を先に読ませる。広い側を先に置いて例外で打ち消さない。

## コードのそばに残したい記述

- 現在の姿は識別子、型、テストで表す。どれでも表現できない不変条件は、それを所有する reference に置く。
- 判断の根拠は、その判断と同じ変更の単位に入れる。複数の判断の根拠を 1 か所にまとめない。作業中に分かったことは、分かった制約の側を書き、どう気付いたかは書かない。
- なぜそうしているか分からない記述は、`git log` と `git blame` で経緯を確かめてから変える。意図を推測したまま変えない。
