# 強制の機構

判定するツールと、それが実行される手順の両方が要る。機械が見る分は `docs/lint-rules-by-guideline.md` の enforcement の節にある。ここに書くのはその外だけ。変更量を理由にした例外は `./verification-bypass.md`、設定の上書きは `./config-cleanup.md`、実行段階の分担は `./ci-efficiency.md`。

## 実行されなかった確認を成功と数えない

- 通過条件として数える実行は、起動した後の階層で絞り込む。起動そのものの条件で絞り込むと、落ちたのか実行されなかったのかが通過の記録から区別できない。数えないと確定できた実行だけ、起動の条件で絞ってよい。
- 確認や適用の失敗はそのまま伝播させる。暗黙のスキップ・握り潰し・継続許可で成功に読み替えない。
- パイプの途中の失敗が終了コードに現れる設定であることを確かめる。
- パッケージ内で閉じる品質作業の対象は、依存グラフとキャッシュを持つタスクランナー（`vp run`）に選ばせる。その前段に別の絞り込みを重ねない。
- 段取りの記述だけが変わったときに対象を広げない。依存構造そのものが変わり、局所化してよいか判断できないときは広げる。
- 走査範囲は、配布物に入るコードの実際の配置に追随させる。
- キャッシュ再利用の既定をまとめて切り替える設定（各 workspace の `vite.config.ts` の `tasks` と `package.json` の `scripts` に及ぶ）は、及ぶ定義を数え上げて 1 つずつ確かめてから書く。
- ファイルを変更する定義と常駐プロセスを起動する定義をキャッシュ再利用の対象にしない。常駐はランナーに宣言する。
- 既定の入力集合を自分で書いた集合で置き換えるときは、その workspace の実際の入力をすべて数え上げる。

## ガードが落ちることを確かめる

- ガードを足したら、違反を仕込んだ入力で報告が出ること、違反でない入力で出ないことを確かめる。設定に存在することを検出できている証拠にしない。
- ガードをすり抜けた違反を見つけたら、コードを直し、落ちるべき入力にその抜け道を足す。
- 報告には、破られた不変条件と直す方向の両方を含める。
- 安全で決定的な直し方がちょうど 1 つに定まるときだけ自動修正を用意する。自動修正が安全に終えられない部分は、失敗するガードとして残す。

## 何を守れる機構かで選ぶ

強制は、各 workspace の `vite.config.ts` が `precommit`・`prepush`・`prepr`・`premerge`・`prerelease` に依存させたタスク（`.vite-hooks/` と `.github/workflows/check.yml`・`.github/workflows/prerelease.yml` が起動する）と、`infra/` と Worker を所有するパッケージの `alchemy.run.ts` の `plan` と `deploy`。コミットログとこの references は記録であり、違反を止めない。

- 1 ファイルの構文で決まるものは型と lint、実行して分かるものはテスト、複数ファイルの突き合わせは検証コマンド、宣言と外の状態の突き合わせは `alchemy plan`。どれにも載らないものだけレビューで見る。
- 根拠を残したことを強制とみなさない。
- 不変条件の全体を確実に守れる機構を主たるガードにする。一部しか守れない機構を主にしない。同じだけ守れるなら、失敗が返るまでの距離が短いほうを採る。
- 不変条件がふるまいと実行時の境界を通る値の両方に掛かるなら、両方に届く機構を置く。
- 既に表現できるガードがあれば設定するか拡張する。並行する検出器を作らない。
- 機構を選んだ理由と、選ばなかった候補で守りきれなかったものをコミットログに残す。ガードの実装や設定だけに残さない。

## ガードを入れる時点

- 基準が決着していて機械的に検出できる違反が予見できるなら、基準を導入する変更か最初の違反を直す変更でガードを入れる。二回目を待たない。
- 議論が決着していないものは自動化せず、拘束力のある散文としても書かない。
- レビューで人が毎回同じ判定をしている項目を機械が評価できるなら、ガードに置き換え、レビュー項目からは消す。

## 強制度を落とすときの形

- 既存の違反があってすぐ全体を強制できないときは、落とす範囲を個別に名指しした既存のファイルに限る。パターン単位で落とすなら、その判断と何が守られなくなるかをコミットログに残す。
- 継続許可を付けるときは、その段を通過条件として数えないことと、代わりに何が見るのかを同じ変更で決める。一時措置のまま放置しない。
- 解消済みの違反に残った抑制は、違反と同じ扱いで落とす。
- 一時的に落とした強制度は、違反が解消した変更で戻す。

## main に入る手順

- main に変更が入る手順は、ブランチを転送して PR を merge する 1 つだけ。手順ごとに別の確認の集合を持たない。
- 通過条件を迂回できる形が残るなら、迂回したことを出力で見える状態にする。
- 通過条件の有無が手元の設定に依存するなら、依存の導入手順（`package.json` の `prepare`）が毎回書き込む形にする。
- `--no-verify` で手元のフックを飛ばさない。

## 実行の定義に書いてよいもの

`package.json` の `scripts` はコマンド名と 1 本の呼び出し、各 workspace の `vite.config.ts` はタスクの依存・キャッシュ・入出力、`.vite-hooks/` は起動口と呼ぶコマンドだけを持つ。

- 実行ブロックは 1 つのコマンド呼び出しに留める。再試行・繰り返し・分岐・エラー処理・対象探索が要るなら、型と自動テストを持つリポジトリ内のコードへ移す。
- 同じまとまりが定義ファイルの中で増えたら、単一のまとまりへの参照で解消する。順序を持つ手順の並びなら、再利用できるまとまりへ切り出す。

## 源と生成物

`pnpm-lock.yaml` と `libs/db/migrations/` の SQL が源から導いた生成物。

- 源から決定的に導ける成果物は生成して得る。生成物を直接編集しない。1 つの生成物に 2 つ目の生成手順を作らない。
- コミットする生成物は、源の変更と同じ変更に入れ、乖離を機械的に検出する手順を付ける。

## 機械だけが読み書きする成果物

`pnpm-lock.yaml`、`.vite-hooks/`、`node_modules/.cache/`、Alchemy の state がこれにあたる。

- パスだけを根拠に機械向けと分類しない。人も読む文書は人間向けとして扱う。
- 人間に対して拘束力を持つ内容をここに置かない。人間向けの規範がここを基準として指さない。混ざっていたら主題を所有する reference へ移す。
- 機械にとっての有用性と構造の妥当性で評価する。散文の質を理由に差し戻さない。
- 形式を所有するツールがあるなら、作成・更新・改名・削除をそのツールで行う。Alchemy の state を手で書き換えない。
- 保守の時点は使っている側の必要に任せる。固定の周期や人間側の工程に紐づけない。

## 実行単位を分ける軸

- 自動化を分ける軸は起動のタイミングとライフサイクル。機能名・パッケージ名・担当領域で分けない。名前もタイミングかライフサイクルが読める名前にする。
- 起動のタイミングが独立していて、失敗したときに巻き込む先が他と揃わない自動化は、独立した実行単位に置く。同居させると一部のために宣言した広い権限を全部が常時持つ。
- 複数の実行単位から使うまとまりは、呼び出す側にトリガを持たせる。
- 互いの結果を参照し合う処理は同一の実行単位に置く。

## 外へ出す操作

`deploy` は Cloudflare の状態を変え、取り消せない。

- 外部状態は、レビューを経たリビジョンから自動化された手順で変える。手元の作業ツリーから実行しない。
- 特定の成果物を前提にする操作は、変える前に成果物の同一性を確認する。生成から消費までを 1 つのまとまりとして扱い、消費側だけが選ばれる手順を残さない。
- 外部状態を変える操作と外部に問い合わせる確認には、明示的な対象集合を与える（`alchemy` の `--stage`）。
- 品質作業か外部への副作用か判別しづらいものは副作用として扱う。
- ソースを取得する権限は読める範囲を絞り、外部に書き込む権限は実行単位が宣言した権限としてその実行に帰属させる。
- 報告は、生成したコマンド自身が単一の手順で決まった掲示先に出す。生成と掲示を分けない。複数の先から同じ掲示先を書き換えない。
- 実行の外側から取得される成果物は、プラットフォームの標準 API と CLI から列挙・取得できる保管先に置く。
- 外部から参照される成果物の集合は 1 箇所で定義する。

## 機械がどこまで判定するか

- レビューで見る項目は、その主題を所有する reference に置く。人が見る項目だけを横断的に集めた置き場所を作らない。
- レビューで見る項目に出会うたびに、機械化できないかを問い直す。
