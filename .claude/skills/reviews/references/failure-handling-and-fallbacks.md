# 失敗の扱いとフォールバック

## 失敗の伝え方

- 予期した失敗と予期しない失敗を、呼び出し側がコードから区別できる形にする。失敗の伝わり方をリポジトリで 2 通り持たない。
- 予期した失敗と外へ出す報告の同一性は安定した識別子（報告の識別子、実行環境が付ける `code`）が持つ。メッセージ本文の一致で判定しない。
- 下位の失敗を包むときは元を `cause` に保持する。文言だけ取り出して元を捨てない。
- 捕まえた失敗を書き出したら、止めるか、失敗したと分かる値を戻す。別の綴りへ移したり包む関数を挟んだりして、握り潰しの検出から外さない。

## サイレントフォールバック

- 失敗・利用不能・不正な入力・不完全な結果を、成功したように見える結果へ暗黙に変換しない。アプリケーションコードだけでなく、CI・ビルドツール・デプロイ設定・feature flag・コマンド・エージェントやツールの選択にも当てる。
- 意味の異なる「もっともらしい結果」を返すより、明示的に失敗させる。
- 失敗を `null`、`undefined`、`""`、`[]`、`{}`、`0`、デフォルト設定、その他もっともらしい値に置き換えない。
- エラーを捕捉して、より低品質・部分的・無関係な実装へ警告なしに切り替えない。
- 利用できない機能を成功した no-op として扱わない。欠落・不正・切り詰め・部分的なデータを完全で有効な結果として扱わない。
- プライマリ成功、フォールバック成功、機能低下した成功、部分結果、失敗を区別できるようにする。
- 代替値で続行するのは、明示的な仕様があり、確認される対象と報告される箇所の集合が変わらず、受け取る側がその値で成立し、置換が呼び出し元・ログ・メトリクス・テストから成功と区別できる、の 4 つを示せたときだけ。
- 環境変数・外部 API の応答・DB の必須値・認証情報・課金や権限の判定に代替値を置かない。

## 判断が割れたとき

- 失敗を表に出すことと代替値で続けることでは、表に出す側を採る。
