# テスト

ここに書くのは lint が判定できないものだけ。

## 何を主張するか

- assert するのは、外から観測できる結果・状態の変化・副作用・公開している契約だけ。内部の呼び出し順序や、振る舞いを変えずに変わりうる内部のデータ形状を固定しない。
- 期待値は仕様や規則から導く。実装が今返している値を書き写さない。
- 振る舞いを変えない書き換えでテストが落ちたら、観測できる契約に対して書き直す。期待値を現状に合わせない。
- 厳密に比べたい値が実行のたびに変わるなら、値の側を制御する。制御できない部分だけを切り離して絞り込み、残りは厳密なまま保つ。
- スナップショットは、書き下した厳密な比較では確かめたい振る舞いが埋もれる大きさのときだけ使い、同じ入力に対して意図を述べるアサーションを別に置く。一致しか証拠が無い状態を証明として受け取らない。

## 本物をどこまで残すか

- 置き換えてよいのは、自分が所有する外部 I/O 境界と、決定的にできない入力の源だけ。決定的にできない入力は、取り込む側でも成立する注入境界として外から与える形にする。
- 外部プロセスの失敗や通信の障害を作るときも、置き換える位置は同じ外部境界に留める。
- 依存をすべて置き換えた結果を、対象の振る舞いの証拠にしない。
- ダブルを入れたら、成功時に返すもの・失敗の伝え方・その中身を、本物の依存が公開している宣言と比べる。ずれていると分かったら、直すまでそのテストを証拠として扱わない。
- 引数として渡すダブルには振る舞いを持たせてよい。
- この範囲の外を置き換えたくなったら、実装の側の構造を変えて本物を残せないかを先に見る。優先は、責務境界として正しい構造変更、テスト可能性、テストの書きやすさの順。テストを書きやすくするためだけの変更を入れない。
- 構造を変えても本物を残せないときは、オーナーの決定を待つ指摘にする。

## 赤の原因を対象に閉じ込める

- テストの意味を決める値（入力値、期待値、引数として渡すダブルの振る舞い）は、そのテストの中に書く。
- 独立した仕様どうしでセットアップが重複するなら残す。重複の排除と独立性が衝突したら独立性を採る。
- 各テストを、他のテストの実行順・後始末・可変なモジュール状態から切り離す。外部の状態を変えたテストは自分の後始末で戻す。並列実行で共有する名前空間やリソースは重ならない名前を取る。
- 時刻や乱数は源を決定的にする。状態の遷移は条件をポーリングして待ち、固定時間の待機を置かない。
- 実行するたびに結果が変わるテストは原因を取り除く。再実行で通ったことを成功にしない。

## どの層に置くか

層は失敗モードで決める。書きやすいから最小の層、不安だから通しの層、とは決めない。

- 変換・規則・計算・整形の誤りは最小の層。プロセスの外へ出る依存や実行時にしか決まらない設定に依存させない。通信する振る舞いは外部境界をプロセス内で横取りする。
- 隣り合うコンポーネントどうしの契約、自分が所有する外部境界との契約は統合の層。プロセス内の協調物は本物のまま使い、外部 I/O だけ置き換える。
- 通したときにだけ現れる配線・引数の解釈・状態コード・出力先の選択は通しの層。件数を小さく保つ。
- 同じ欠陥を複数の層で検出できるなら、最も安い層に第一の責任を置く。上位の層には、下位が押さえていない別の契約を押さえるときだけ足す。
- 取り込む側が固定して使う公開 API を変えるときは、提供側だけの変更で契約が破れたことが落ちるテストを置く。
- 層を決められないときは、オーナーの決定を待つ指摘にする。

## カバレッジ

- 数字は、どれだけの行が一度も動いていないかとしてだけ読む。高いことを何かが主張された証拠にしない。
- 受け口にテストしづらいロジックがあれば、ロジックを切り出して受け口を配線だけの薄い境界にする。切り出しや注入境界でテスト可能にできるものを、計測対象からの除外で片付けない。
- 通過条件と構造の改善が衝突したら構造の改善を先に取る。
- どれを尽くしてもテスト不能なら、除外してよいかをオーナーの決定を待つ指摘にする。

## 振る舞いを足したとき

- 要求に対して落ちるテストを先に書き、実際に落ちるのを見てから実装に触る。
- 条件で結果が変わる振る舞いは、意味のある分岐先それぞれと境界の値を覆う。成功する流れだけを覆って完了にしない。
- テスト可能な振る舞いを足したら、選んだ層でそれを所有するテストを同じ変更で足す。「あとで足す」を完了の理由にしない。

## 消すテスト

現在の実装ではなく、維持したい仕様・振る舞い・制約をテストする。

- 削除した機能・実装・概念が存在しないことを確認するだけのテストは削除する。「再び追加されないように」という理由だけで残さない。不在が明示的な仕様・制約である場合を除き、不在を検証するテストを足さない。
- テストのためだけに、存在しないことを保証する概念や制約を増やさない。
- 実装詳細の存在・不在を固定するだけのテストは削除する。コマンドの具体的な文字列を固定せず、外から見える契約や維持すべき依存関係をテストする。

```ts
expect(appRun.tasks.build.dependsOn).toEqual(expect.arrayContaining(["check:effect"]));
```

- 変更で不要になった fixture・mock・helper も削除する。
- 残す判断は、そのテストが失敗したときにどの仕様・振る舞い・制約が破れたか説明できるかで決める。「現在こう書かれている」しか説明できないなら不要。互換性・不変条件・意図的な禁止のように、その状態の維持自体が仕様なら残す。
- カバレッジ不足だけを理由に、実装詳細を固定するテストを足さない。
