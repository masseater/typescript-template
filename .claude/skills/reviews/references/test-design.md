# テストの設計

## 何を assert するか

- assert するのは、外から観測できる結果、状態の変化、副作用、公開している契約だけ。内部の呼び出し順序や、振る舞いを変えずに変わりうる内部のデータ形状を固定しない。
- 期待値は仕様や規則から導く。実装が今返している値を書き写さない。
- 振る舞いを変えない書き換えでテストが落ちたら、観測できる契約に対して書き直す。期待値を現状に合わせない。
- 厳密に比べたい値が実行のたびに変わるなら、値の側を制御する。制御できない部分だけを切り離して絞り込み、残りは厳密なまま保つ。
- スナップショットを使うのは、書き下した厳密な比較では確かめたい振る舞いが埋もれる大きさのときだけ。同じ入力に対して意図を述べる assert を別に置く。一致しか証拠がない状態を証明として受け取らない。

## 本物をどこまで残すか

- 置き換えてよいのは、自分が所有する外部 I/O の境界と、決定的にできない入力の源だけ。決定的にできない入力は、import する側でも成立する注入境界として外から与える形にする。
- 外部プロセスの失敗や通信の障害を作るときも、置き換える位置は同じ外部境界に留める。
- 依存をすべて置き換えた結果を、対象の振る舞いの証拠にしない。
- テストダブルを入れたら、成功時に返すもの、失敗の伝え方、その中身を、本物の依存が公開している宣言と比べる。ずれていると分かったら、直すまでそのテストを証拠として扱わない。
- 引数として渡すテストダブルには振る舞いを持たせてよい。
- この範囲の外を置き換えたくなったら、実装側の構造を変えて本物を残せないかを先に見る。優先順位は、責務境界として正しい構造変更、テスト可能性、テストの書きやすさの順。テストを書きやすくするためだけの変更を入れない。
- 構造を変えても本物を残せないときは、オーナーの決定を待つ指摘にする。

## 失敗の原因を対象に閉じ込める

- テストの意味を決める値（入力値、期待値、引数として渡すテストダブルの振る舞い）は、そのテストの中に書く。
- 独立した仕様どうしでセットアップが重複するなら、そのまま残す。重複の排除と独立性が衝突したら、独立性を採る。
- 各テストを、他のテストの実行順、後始末、可変なモジュール状態から切り離す。外部の状態を変えたテストは、自分の後始末で戻す。並列実行で共有するネームスペースやリソースは、重ならない名前を取る。
- 時刻や乱数は源を決定的にする。状態の遷移は条件をポーリングして待ち、固定時間の待機を置かない。
- 実行するたびに結果が変わるテストは、原因を取り除く。再実行で通ったことを成功にしない。
- 要求に対して落ちるテストを先に書き、実際に落ちるのを見てから実装に触る。
- 条件で結果が変わる振る舞いは、意味のある分岐先それぞれと境界の値を覆う。成功する流れだけを覆って完了にしない。
- テスト可能な振る舞いを足したら、選んだ層でそれを所有するテストを同じ変更で足す。「あとで足す」を完了の理由にしない。

## 消すテスト

- 現在の実装ではなく、維持したい仕様、振る舞い、制約をテストする。
- 削除した機能、実装、概念が存在しないことを確認するだけのテストは削除する。「再び追加されないように」という理由だけで残さない。不在が明示的な仕様や制約である場合を除き、不在を検証するテストを足さない。
- テストのためだけに、存在しないことを保証する概念や制約を増やさない。
- 実装詳細の存在や不在を固定するだけのテストは削除する。コマンドの具体的な文字列を固定せず、外から見える契約や維持すべき依存関係をテストする。

```ts
expect(appRun.tasks.build.dependsOn).toEqual(expect.arrayContaining(["check:effect"]));
```

- 変更で不要になった fixture、mock、helper も削除する。
- 残すかどうかは、そのテストが失敗したときにどの仕様、振る舞い、制約が破れたかを説明できるかで決める。「現在こう書かれている」としか説明できないなら不要。互換性、不変条件、意図的な禁止のように、その状態の維持自体が仕様なら残す。
- カバレッジ不足だけを理由に、実装詳細を固定するテストを足さない。

## 書き方の例

書く前に、対象の契約から確かめたいことを文で決める。`openPullRequestOf` なら次の 2 つになる。

- 開いている PR について `gh pr view` が成功したら、その PR の番号、URL、base、merge 状態を返す。
- `gh pr view` が失敗したら何も返さない。

1 つの文が 1 つの `describe` になり、文の前半の状況を fixture が作り、後半の観測できる結果を `it` が確かめる（`tools/ai-native/src/features/ai-native/sync-base/read-open-pr.test.ts`）。

```ts
import { describe, expect, test } from "vite-plus/test";

import { openPullRequestOf } from "./read-open-pr.ts";

describe("openPullRequestOf", () => {
  describe("a successful gh pr view of an open pull request", () => {
    const it = test.extend("thePullRequest", () =>
      openPullRequestOf("/work", () => ({
        status: 0,
        stdout:
          '{"baseRefName":"main","mergeStateStatus":"BEHIND","number":3,"url":"https://example.com/3"}',
      })),
    );

    it("returns the parsed pull request", ({ thePullRequest }) => {
      expect(thePullRequest).toStrictEqual({
        baseRefName: "main",
        mergeStateStatus: "BEHIND",
        number: 3,
        url: "https://example.com/3",
      });
    });
  });

  describe("a gh pr view that fails", () => {
    const it = test.extend("thePullRequestWhenGhFails", () =>
      openPullRequestOf("/work", () => ({ status: 1, stdout: "no pull requests found" })),
    );

    it("returns nothing", ({ thePullRequestWhenGhFails }) => {
      expect(thePullRequestWhenGhFails).toBe(undefined);
    });
  });
});
```
