# 秘密と権限

## リポジトリに置かない

- 持っていること自体が「誰かとして振る舞ってよい」根拠になる値を、秘密として扱う。接続先のアカウントを名指しする識別子も同じに扱う。
- 資格情報は、実行を起こした側から実行時に渡ってくる形にする。
- 秘密の値を平文で追跡ファイルに書かない。一度コミットに入れば履歴から読める。
- 開発用の値は、追跡しない `apps/<app>/.dev.vars` に生成し、生成を実行できる形で持つ。暗号化したものも追跡ファイルに置かない。
- 設定に書き留めるのは、保管先の指し方だけ。
- 文書やテストに資格情報の形をした値が要るなら、どの相手にも通らないと読み取れる値を選ぶ。
- 本物の資格情報が平文で入っていたと分かったら、値を使えなくしたうえで、いまの内容からも公開済みの履歴からも取り除く。
- 探す仕組みを、広い範囲の除外で止めない。誤検知は根拠を同じ変更に添えて、その 1 件だけ外す。

## 変更を起こすエンドポイントは、その地点で判定する

- エンドポイントを新しく開く、または広げるときは、変更が実際に起きる地点で対象と操作を確かめる。呼び出す側で済んでいるものとして省かない。
- 誰として要求したかを確かめる仕組みを通過した事実だけで、変更を認めない。
- 判定の正しさを機械で確かめられない手順は、人が読んで確かめる側へ回す。
- 保護された環境を資格情報を持たない主体に開けるときは、保護を残し、迂回する手順を主体ごとに分けて発行する。

## 資格情報は目的ごとに分ける

- 触る対象と操作の範囲に収まる資格情報を、最短の期限で使う。
- 相手が通してしまうことを理由に、発行した目的の外へ回さない。Alchemy が管理 API を呼ぶキーと、アプリが機能のために使うキーは別に発行する。
- 複数のジョブで共有するときは、失効させたときに止まる範囲を数え上げる。数え上げられないまま共有しない。
- 自動化がリポジトリを書き換えるときは、その自動化のために発行した資格情報を使う。個人にひも付くトークンを定常的な手段にしない。
