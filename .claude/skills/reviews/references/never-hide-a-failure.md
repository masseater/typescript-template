# 失敗の扱いとフォールバック

## 失敗の伝え方

- 予期した失敗と予期しない失敗は、呼び出し側がコードで区別できる形にする。失敗の伝え方をリポジトリ内で 2 通りにしない。
- 予期した失敗や外へ出すレポートが同じものかどうかは、安定した識別子（レポートの ID、ランタイムが付ける `code`）で判定する。メッセージ本文が一致するかで判定しない。
- 下位の失敗をラップするときは、元の失敗を `cause` に残す。メッセージだけ取り出して元を捨てない。
- 捕まえた失敗をログに出したら、処理を止めるか、失敗したと分かる値を返す。別の名前に移したりラップ関数を挟んだりして、握り潰しの検出をすり抜けさせない。

## サイレントフォールバック

- 失敗、利用できない状態、不正な入力、不完全な結果を、暗黙のうちに成功に見える結果へ変えない。アプリケーションコードだけでなく、CI、ビルドツール、デプロイ設定、feature flag、コマンド、エージェントやツールの選択にも同じ規則を当てる。
- 意味の違う「もっともらしい結果」を返すくらいなら、明示的に失敗させる。
- 失敗を `null`、`undefined`、`""`、`[]`、`{}`、`0`、デフォルト設定などのもっともらしい値で置き換えない。
- エラーを catch して、質の低い実装、部分的な実装、無関係な実装へ警告なしに切り替えない。
- 使えない機能を、成功した no-op として扱わない。欠けたデータ、不正なデータ、切り詰められたデータ、部分的なデータを、完全で有効な結果として扱わない。
- 本来の成功、フォールバックでの成功、機能を落とした成功、部分的な結果、失敗を、それぞれ区別できるようにする。
- 代替値で処理を続けてよいのは、次の 4 つをすべて示せるときだけ。明示的な仕様がある。チェックされる対象とレポートされる箇所が変わらない。受け取る側がその値で正しく動く。呼び出し元、ログ、メトリクス、テストのどれからも、置き換えたことを成功と区別できる。
- 環境変数、外部 API のレスポンス、DB の必須の値、認証情報、課金や権限の判定には代替値を使わない。
