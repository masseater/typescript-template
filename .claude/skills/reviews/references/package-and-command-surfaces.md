# パッケージとコマンドが外に出すインターフェース

## import されるインターフェース

- npm へ公開するパッケージのインターフェースと、workspace 間の import のインターフェースを同じ重さで扱う。
- 既に公開しているものや、import 側が依存している契約から導出できるものを足さない。
- 公開する export を変えるときは、エントリと消費側を同じ変更で更新する。
- インターフェースに新しい項目を足すときは、テストではない呼び出しを今示す。将来の見込みは利用者ではない。
- テストからしか import されない export は消す。消せなければ、利用者が通る呼び出し越しに検証する形へ書き換える。
- import されるパッケージの責務は 1 つにする。公開するサブパスはその責務の内側に収める。サブパスを分けたことを、影響範囲が縮む根拠にしない。影響は workspace 間の依存の辺で判定される。
- import されるだけのパッケージに、コマンドのエントリポイントを足さない。責務の外の実行体が要るなら、エントリポイントとその依存を、実行体を所有する別の workspace へ移す。
- 1 つのパッケージに両方のインターフェースを持たせるなら、2 つが同じ責務の別の現れであることと、それぞれに実際の利用者がいることを示す。
- 薄いラッパーや別スクリプトを経由して、閉じているインターフェースに到達させない。

## 実行が外へ出すインターフェース

- 特定の利用者向けのインターフェースは、載せる事実と粒度を選んでよい。利用者側の見せ方までは決めない。見せ方を契約に載せない。
- 終了コード、ステータスコード、レポートの書式、利用者向け文言への変換は、ちょうど 1 か所の境界で行う。失敗そのものに外向きの表現を持たせない。
- 解決に利用者から到達できない状態が要る値は、解決した後の値を載せる。

## エントリポイントとコマンドの単位

- 実行可能なコマンドは、所有するパッケージを 1 つ決める。ルートから呼べるようにするときは、所有パッケージへの薄い委譲だけを置く。
- 置き場所を外の仕組みが決めるエントリポイント（git フック）には、workspace が所有するコマンドの呼び出しだけを置く。チェックの中身を実装しない。
- リポジトリのルート直下に、自動化の実装本体を置かない。
- テストからしか到達しないエントリポイントを作らない。
- 手元、フック、自動実行から同じ処理を呼ぶときは、同じ呼び方が通る状態を保つ。手元のチェックと CI が同じまとまりを起動することを、片方からの導出か、ずれを機械的に落とす形で保つ。
- 個別に呼ぶコマンドは、落ちたときに守られていない不変条件と直す方向が 1 つに決まる単位にする。まとめて実行するエントリポイントは個別のコマンドを並べたものにし、1 つに統合しない。

## 呼び出し側に選ばせる値

- オプションにするのは、呼び出し側が本当に選ぶ値だけ。コマンドの目的から一意に決まる値をオプションにしない。
- 実行時の文脈から取れる値は、その文脈を読む境界で受け取る。手元と自動実行の差も文脈から導き、モードのフラグや自動実行専用にコピーしたスクリプトで表現しない。
- 別の戦略を選ばせるなら、目的ごとのサブコマンドにする。
- 秘密の値は保管先のキーやパスという参照で受け取り、値そのものをオプションで受け取らない。

## 使い方の記述

- 受け付ける引数と表示される使い方を同じ変更で揃え、変えたら実際に実行して確かめる。
- 値を取るオプションは、値の形と、指定しなかったときの実際の値を読める形にする。
- コマンドの説明は目的を述べる 1 文にする。手順や環境の説明を詰め込まない。

## 標準出力と診断

- 別のプログラムや AI が消費する標準出力は、結果だけで構成する。途中経過、デバッグ、進捗は別の系統に出す。
- 子プロセスをラップするコマンドが自動実行の中で動くなら、子の出力を捨てずにログへ流す。

## 判断が割れたとき

- 拡張点を先に用意したい要求より、今の呼び出し元を示す規則を採る。
- 決められないときは、公開インターフェースに載せない。
