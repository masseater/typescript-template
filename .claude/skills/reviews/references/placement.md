# 置き場所とツール

ここに書くのは lint が判定できないものだけ。

## 共有に踏み切る条件

- コードの切り出しは、実際に取り込む workspace が 2 つ以上になってから。取り込み元が 1 つに減ったら、残った 1 つの内側に畳み直す。
- 所有者も呼び出し元も 1 つの workspace に閉じるスクリプトはその内側に置いてよい。呼び出し元が 2 つ目になったら（CI から呼ばれ始めた時点を含む）workspace が所有するコマンドに移す。
- 取り決め（共有 tsconfig のプリセット、確認が読む語彙と閾値の既定値）に実行できる実装を入れない。取り決めはそれが記述している領域で束ねる。
- 1 つの workspace にしか関係しない設定を共有の取り決めに置かない。既存のどの領域にも当てはまらない取り決めは、何を所有するかを名前にした新しい置き場所を作る。近いという理由で相乗りさせない。
- 取り込む側の 1 つだけが持つ制約のための回避策は、制約を持つ側に置く。供給側を全員ぶん変えない。
- 持ち主は、その責務を既に負っている workspace に置く。依存の向きを逆にしてまで寄せない。無ければ狭い名前の持ち主を新しく作る。
- 複数の workspace が要り、どれにも属さない宣言は、双方が依存できる中立の置き場所に置き、その置き場所が何を断るかを決める。

## 置き場所は届く相手で決める

誰に届くか、失敗したとき何が止まるか、単独で起動と停止ができるか、取り込まれるのか実行されるのか、で決める。実装の見た目（起動口を持つ、サーバーが立つ）で決めない。

順に照らし、最初に当てはまった区分で確定する。

1. パッケージが所有する Worker の Alchemy Stack。そのパッケージの `alchemy.run.ts`
2. 複数の適用単位が共有し、単独の Worker パッケージに属さない外部資源の宣言。`infra/`
3. デプロイされて外部の利用者からの要求を受ける実行対象。`apps/`
4. 複数の workspace が取り込む共有物。`libs/`
5. 上のどれでもないもの。それを使っている既存の workspace の内側

- Worker を所有するパッケージの Stack を `infra/` に移さない。
- 既存の区分に収まるものに並列のトップレベルを作らない。どの区分に入れても定義が偽になるときだけ区分を増やし、その前にどの区分も所有しないことをコミットログに残す。
- 中身の無い区分、整理されて見えることや今後増えそうなことを根拠にした区分を作らない。
- 残余の区分に置いたものは、所有者が未定の印として扱い、増えたら区分を増やすか所有者を決めて減らす。迷ったものの既定の行き先にしない。

## 区分の内側の配置

- 同じ feature・責務に属するもの、一緒に変更・理解されるものを近くに置く。feature 固有のコード・型・utility・定数・hook・テスト・設定はその feature にコロケーションする。
- `shared` / `common` / グローバルには、実際に複数箇所から共有されるものだけを置く。将来使うかもしれないという理由で共有・抽象化・分離しない。
- package は実際に再利用する境界として必要な場合だけ分ける。分離しても再利用性が増えないものを package 化しない。
- feature / package の境界の外から内部実装を直接使わない。依存の向きは `tools/dont-review-it` の `dependency-cruiser.ts` が制約する。境界を守るために lint の無効化や個別の例外を足さない。
- 既存の構成・命名・境界に合わせて置く。

## ツールは対象の構造で選ぶ

- ソースコードの書き換えは構文木の上でノードを編集し、整形を壊さない層を入力にする。読み取りは公式コンパイラの構文木を入力にする。行やパターンのテキストマッチで構文を判定しない。範囲が小さくても同じ。
- 依存に型付きの API があるならそれを使う。実行ファイルしか無いなら、自分が所有する型付きの薄い層で包み、出力を検証してから渡す。素の子プロセス呼び出しを呼び出し箇所に置かない。
- 外部サービスへのアクセスは、リトライ・応答の解釈・認証を 1 つの型付き境界に集める。
- 外部サービスの設定は Alchemy の宣言に書く。管理画面の手作業やその場限りの API 呼び出しで済ませない。公式ドキュメントに無い API しか無いなら dynamic provider を書く。

## 版の出どころ

- ツールの版は、宣言的に固定でき、プロセスの環境へ 1 度だけ注入できる機構に寄せる。
- 活性化を所有する境界が既にあるかで、環境を用意する側か継いだ側かを決める。継いだ側は継いだ環境からそのまま呼び、活性化を重ねない。用意する側（対話的なシェル、フック、自動実行の準備）は 1 度だけ活性化する。
