# 持ち主と重複

## 重複と持ち主

- Oxlint と knip が挙げた一致は候補として扱う。挙げたこと自体を統合の根拠にせず、挙げないことを重複が無い証拠にしない。
- 一致を外すためだけの書き換えや、両方を残したままの抑制で報告を消さない。
- 報告と実態が食い違うと考えるなら、理由を突き止めてから `knip.ts` に例外を書く。
- 重複と呼ぶのは、同じ責務を負う宣言が 2 か所以上にあり、どれも他を取り込んでいない状態だけ。字面の一致だけで重複と呼ばない。
- 責務と契約の一致を確かめられないもの、今後別々に変わる見込みのものは分けたまま残す。迷ったら重複を残す側に倒す。
- 統合後の持ち主に責務を言い当てた狭い名前を付けられないなら、それは 2 つの責務。
- 持ち主を迂回する書き方が機械的に検出できるなら、同じ変更でガードを入れる。

## 既にある定義の上に書く

- 振る舞い・ルール・値に所有者がいるなら再利用するか拡張する。等価なものをその場に作らない。
- 既製のライブラリ・フレームワーク・リポジトリの仕組みにある処理を自前実装しない。ユーティリティは `es-toolkit`。既製の関数を包み直すだけのラッパーを作らない。
- 欠陥は、それを所有している境界で原因を直す。外側の分岐や迂回を修正として残さない。
- 同じ規約を複数の書き方で表現できる状態を見つけたら、型・境界・自動の確認を締めて通る書き方を 1 つにする。文書に書いて終わりにしない。

## ずれうる設計を採らない

- 2 つの記述が同じ事実かは、片方を変えたときにもう片方が失敗するかで決める。
- 別々の理由で変わりうるものを、形が似ているという理由で 1 つに寄せない。
- 同じ事実の二重表現には権威を 1 つ選び、残りを導出する。導出できないなら、ずれた時点で機械的に落ちる形にする。導出も検出もできない設計を採らない。
- 不正な組み合わせを「書かない」約束で防がない。表現できない形にするか、機械的に弾く。

## 業務の判断と状態の持ち主

- DB スキーマ・マイグレーション・キャッシュ・画面の状態・運用手順まで含めて、判断がどこで下され、どこへ複製されているかを確かめる。
- 不変条件ごとに守らせる持ち主（集約）を 1 つ決める。複数の handler・画面・ジョブが別々に判定しない。
- 判定の優先順位（プラン、例外措置、停止など）を呼び出し側ごとに書かない。持ち主が理由付きの判断を返し、呼び出し側はそれを使う。
- 過去に観測した事実と現在の判断を別の値として持つ。過去の検証結果を現在の判断に再利用しない。
- 導出した値（集計、キャッシュ、画面の boolean、検索用の複製）は報告に使ってよいが、書き戻して判断の根拠にしない。人やジョブが導出値を直接書き換える手段を作らない。
- 永続化した状態は、現在の契約へ正規化・移行してから判断に使う。古い版の値をそのまま復元して分岐しない。
- 1 つの status や boolean の組で、意味の違う複数の事実（業務上の失敗、一時的な外部失敗、リトライ上限、運用者の停止）を表さない。
- 状態を足すのは、その状態で受け付ける操作が変わるときだけ。計算の途中を永続化する状態にしない。
- 業務の判断は純粋な関数に置き、永続化・通知・外部呼び出しはその結果を受けて行う。
- 別ドメイン・外部サービス・別 workspace との境界では、相手の語彙を内側の語彙へ翻訳する。保存形式や外部 API の名前をドメインの名前として使わない。
- 1 つの語が複数の意味で使われていたら、用語集（`apps/internal-dashboard/content/docs/glossary/`）で分けて別の名前にする。
- モジュールは、契約・テスト・計測の記録から短期間で書き直せる大きさと結合度に保つ。書き直せない理由が隠れた不変条件や共有状態なら、それを境界へ出す。
- 直した結果、消せる状態・フラグ・例外分岐・運用手順は同じ変更の中で消す。

## シンプルさ

- コードだけでなく、各 workspace の設定・タスク構成にも当てる。
- 型で表現できる安全性を、実装時の分岐や手動チェックで代替しない。複雑な `if` / `switch` を増やさず、バリデーションライブラリや型で表現する。
- 場当たり的な修正で複雑さを増やさず、必要なら設計・責務・データ構造から変える。
- 後方互換性のためだけの分岐・ラッパー・旧 API を残さない。
- ファイルパスや正規表現による脆弱なマッチングではなく、バリデーションライブラリで対象を識別する。
- 引数の受け渡しや一部の値の抽出だけを目的とした関数・型・インターフェースを増やさない。
- workspace 固有の export・コマンド・設定を必要以上に増やさない。リポジトリ全体で扱う処理はルートに集約する。workspace の設定は共通設定を継承し、固有設定は最小にする。
- 手動実行を前提とする独自スクリプトを増やさず、起動・終了・ビルドなどのライフサイクルに組み込む。個別の確認タスクを列挙して実行せず、lifecycle の集約を使う。
- `node` で直接ファイルを実行せず、`vp` のタスクランナーに乗せる。
- 変更で複雑さが減るか、既存の仕組みで置き換えられないかを確認する。

## 判断が割れたとき

- 責務の境界を守ることと字面の一致をなくすことでは、境界を守る側を採る。
- ずれうる設計を採らないことと、実装の速さ・差分の小ささ・既存との見た目の一致では、ずれない側を採る。
