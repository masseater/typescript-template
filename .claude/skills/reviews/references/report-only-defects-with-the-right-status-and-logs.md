# 監視、ログ、ステータスコード

## 監視へ送る対象

- 監視へ送るのは、こちらの変更で挙動が変わる不具合だけ。入力の不備、存在しない URL、対応していないプロトコルのバージョン、認証の失敗など、仕様どおりのレスポンスを不具合として数えない。
- 仕様どおりの拒否が監視に届いているなら、送らないように直す。監視側で表示から外して済ませない。送った時点で quota を消費している。
- 送るかどうかをステータスコードで判定しているなら、ステータスコードを持たない失敗（認証の失敗、DB ドライバの例外）がすり抜ける前提で、種別ごとに判定へ乗せる方法を決める。
- 外部サービスの失敗は、こちらのレスポンスをどうするかを先に決め、それに合わせて送るかどうかを決める。外部の失敗だからという理由で自動的に外さない。

## レスポンスのステータスコード

- ステータスコードは RFC 9110 の意味で使い、場面ごとの選択は Google の `google.rpc.Code` の分類と HTTP への対応で決める。本体は RFC 9457 の Problem Details（`application/problem+json`）にする。
- 使いたいコードが `@repo/config` の `httpStatus`（失敗側は `@repo/runtime` の `FailureStatus`）にないなら、型に足してから使う。
- リソースが存在しない: 404。見つからなかった値を描画へ渡して 500 にしない。
- 資格情報がない、または無効: 401。
- 権限がない: 存在を調べる前に権限を判定して 403。存在自体を隠す必要を説明できるときだけ 404。
- 引数が状態に関わらず不正: 400（`INVALID_ARGUMENT`）。引数は正しいが状態が実行できない: 400（`FAILED_PRECONDITION`）。範囲外: 400（`OUT_OF_RANGE`）。
- 既に存在する、または並行操作と競合: 409。割り当てを使い切った: 429。未実装か無効化: 501。
- 外部サービスが使えない: 503。復帰の見込みが分かれば `Retry-After` を付ける。時間内にレスポンスがない: 504。
- 502 を返さない。外部 API を呼んで失敗したアプリはプロキシではない。
- どの 5xx も当てはまらないときだけ 500。デフォルトの選択肢にしない。
- 外部サービスが失敗しても、欠けた部分を除けばレスポンスの目的を達せられるなら、成功として返し、欠けたことを `WARNING` でログに残す。5xx でレスポンスごと落とさない。達せられないなら 503 か 504 を返して監視へ送る。
- ステータスコードを決める箇所は 1 つの境界に保ち、同じ失敗に出どころごとに違うコードを割り当てない。

## 送ったレポートを閉じる

- 監視の状態を「直った」へ進めるのは、修正か送信を止める変更が本番に届いたことを確かめてから。通知を減らすためだけに動かさない。
- 直さないと決めたものは、送らないように直したうえで閉じる。送り続けたまま通知だけ止めない。
- 未解決のまま残っているレポートは、直すと決めたものとして扱う。

## アラート

- アラートは Alchemy の宣言と `infra/*-monitor`、`libs/monitor` に書く。Cloudflare の管理画面だけで作らない。
- 宛先と判定条件を宣言した状態で有効にする。宛先は担当者が普段見ている場所にする。宛先のない有効なアラートを残さない。
- 対象は production に限る。他の環境の事象を通知に載せない。
- 繰り返し発火しうる事象には、再通知の間隔を決める。
- 動いているかどうかの監視は、落ちたことが通知へ届くところまで用意する。

## ログの流れ

- 発生源の種別ごとに流す先を 1 つ決める。1 つの発生源を複数の先へ重複して流さない。既に複数へ流れているなら一本に寄せる。中継するためだけの中間処理を残さない。
- 本番のログは、そのランタイム向けの構造化の境界を通す。呼び出し側で logger を作り直したり、サービス名、環境、送り先を上書きしたりしない。本番で動くコードの出口に素の `console` を置かない。
- ログを増やしたい要求より、ログの流れを一本に保つ側を採る。

## ログレベル

- 必要なリソース、依存、設定値、必須の入力の欠落: `WARNING` 以上。
- 外部の依存の失敗: `ERROR`。どの依存かを構造化したフィールドに残す。
- 入力の不正、業務規則の違反、状態の衝突: `WARNING`。
- 対象が存在しない、権限がない: `INFO`。
- 分類できない失敗は上位へ渡し、そこで `ERROR` としてログに残させる。
- 代替値で処理を続けた置き換え: `WARNING` 以上。

## ログに何を残すか

- 秘密と個人を特定できる値を落とす判断を、何を残すかの判断より先に当てる。
- 捕まえた失敗は、失敗そのものと `cause` の連なりを残す。メッセージだけコピーして元を落とさない。
- 識別子、処理の段階、引数は、秘密の値を落としたうえで構造化したフィールドに載せる。メッセージは固定し、変わる値はフィールドに置く。
- 出力先の容量に収まらないなら、出力先を分けるか構造化したフィールドへ移す。削って残りを捨てない。どうしても落とすなら、落とした事実をログに残し、在りかは読み手に開示が許された場所だけを指す。
- 秘密を落とした後の形を、出してよい内容の全体として扱う。落とす前のコピーを残さない。
